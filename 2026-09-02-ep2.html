Ep2 — Track B: HALO, a hierarchical autoregressive model for synthetic high-dimensional EHR

Theodorou B, Xiao C, Sun J. (2023). Synthesize high-dimensional longitudinal electronic health records via hierarchical autoregressive language model. Nature Communications.

Full text retrieved (PMC10471716). HALO (Hierarchical Autoregressive Language mOdel) generates synthetic longitudinal EHR data at the same native, high-dimensional granularity as real EHRs — roughly 10,000 disease codes, ~1,000,000 within-visit code co-occurrence probabilities, and ~5,000,000 across-visit conditional probabilities — instead of the aggregated, dimensionality-reduced representations every prior method (MedGAN, SynTEG, ehrMGAN, EVA) relied on. A coarse visit-level transformer module (12 decoder blocks) and a fine code-level masked-linear module work together autoregressively. Synthetic code-occurrence probabilities correlate above 0.9 with real data; downstream disease-phenotyping classifiers trained on synthetic data reach AUC 0.938 versus 0.943 for real-data-trained models; membership-inference privacy attacks succeed only at chance level (~50%). Code ships on GitHub. Lands on the AI-tooling/career-development priority as a template for a scaled-down synthetic-data generator for registry-style structured longitudinal data.

Plain-English glossary

  • Synthetic EHR — an artificially generated patient dataset statistically resembling a real population's records, with no row corresponding to an actual identifiable person.（中文：人工生成的患者数据集，在统计上与真实人群记录相似，但没有任何一行对应真实可识别的个人。）
  • High-dimensional (EHR context) — modeling a patient record's full native complexity (~10,000+ distinct codes per visit-sequence) rather than aggregating down to a small fixed set of variables.（中文：以患者记录的完整原生复杂度（每个就诊序列可达一万种以上不同代码）建模，而非聚合压缩为少数固定变量。）
  • Autoregressive — a generative approach where each new piece of data is generated conditioned on everything generated before it, as in next-word prediction in language models.（中文：一种生成式方法，每一条新数据的生成都以之前生成的全部内容为条件，类似语言模型中的下一词预测。）
  • Hierarchical (visit-level / code-level) — modeling an EHR's two structural levels — the sequence of visits, and the codes within each visit — with two coupled modules instead of one flat sequence model.（中文：用两个相互耦合的模块分别建模电子健康记录的两个结构层级——就诊序列，以及每次就诊内部的代码——而非用单一扁平序列模型处理。）
  • Membership inference attack — a privacy-risk test that tries to determine whether a specific real record was used to train a model or generate a synthetic dataset; chance-level (~50%) success indicates no meaningful privacy leakage.（中文：一种隐私风险测试，试图判断某条特定真实记录是否被用于训练模型或生成合成数据集；约 50% 的随机猜测水平成功率表示没有明显的隐私泄露。）
  • Discretized continuous variables (bucketing) — converting a continuous value (e.g. a lab result) into a set of binary range-membership indicators for generation, then reconstructing a continuous value by uniform sampling within the generated bucket's range.（中文：将连续值（如化验结果）转换为一组二元区间归属指标以便生成，再通过在生成的区间范围内做均匀采样来还原为连续值。）

Methods / tools to lift

  • HALO (Hierarchical Autoregressive Language mOdel) — open-source (GitHub) two-module transformer architecture generating native-dimensionality synthetic longitudinal EHR data.
  • Discretized-bucket continuous-variable modeling — approach for including lab values and inter-visit time gaps in an otherwise binary-code generative framework.
  • Membership-inference / attribute-inference / nearest-neighbor adversarial accuracy — the paper's battery of privacy-risk evaluation methods for synthetic data.

Where it lands + buildable artifact

Priority served: AI applied to registry/bioinformatics, tool-development lens, career-aligned (the only priority named this episode). Tool sketch: a scaled-down, single-level autoregressive generator (skip the full 12-block visit-history transformer) trained on a narrow slice of de-identified, structured longitudinal encounter data (visit timing + a few variables; external methods only, no CFFPR internals) to produce synthetic data for pipeline testing, including deliberately injected synthetic errors as ground truth for validating outlier-detection logic. python halo_lite_synth_generator.py --input encounters.csv --n-synthetic 10000 --inject-errors known_error_profile.json (MVP sketch). Difficulty: Large for anything close to HALO's full architecture at native dimensionality; Medium for a narrow single-level prototype.

What to verify first

  • Whether HALO's privacy guarantees (membership/attribute inference near chance level) hold on a much smaller, rare-disease-scale cohort where records are inherently less anonymous among peers — evaluated here only on large, heterogeneous populations (MIMIC-III, broad claims data).
  • The paper's own acknowledged limitation that individual sampled records may not be clinically coherent, requiring a clinical-rule postprocessing layer the paper doesn't build or test.
  • Whether the GitHub repository is actively maintained, its dependencies/license, and whether it reproduces the paper's numbers on a small test run before adopting it.
  • Whether the "relatively large training datasets" HALO is stated to need is compatible with the likely much smaller scale of CF-relevant longitudinal data versus MIMIC-III or a national claims dataset.

ALEX Today's Track B pick is Theodorou and colleagues, published in Nature Communications in 2023: "Synthesize high-dimensional longitudinal electronic health records via hierarchical autoregressive language model." 今天 Track B 的选题是 Theodorou 及其同事在 2023 年发表于《自然通讯》（Nature Communications）上的论文：《通过分层自回归语言模型合成高维纵向电子健康记录》。 It ships open-source code on GitHub, which is exactly the bar Track B holds tools to, and it tackles a problem any registry-adjacent AI-tooling effort eventually runs into: how do you generate or share realistic patient-level longitudinal data without generating a privacy liability? 它在 GitHub 上开源了代码，这正是 Track B 对工具的一贯要求，而且它解决的是任何与登记处相关的 AI 工具开发工作迟早都会遇到的问题：如何在不制造隐私风险的前提下，生成或共享真实感强的患者层面纵向数据？ We got the full text this time, via PMC.这次我们通过 PMC 拿到了全文。

JORDAN Before we get into the model, what actually is a "synthetic EHR," and why would anyone want one instead of just using the real records they already have? 在讲模型之前，"合成电子健康记录"（synthetic EHR）到底是什么，为什么会有人想要它，而不是直接用手头已有的真实记录？

ALEX A synthetic EHR is an artificially generated patient dataset built to statistically resemble a real population's records — same kinds of diagnoses, procedures, medications, and visit patterns, same aggregate statistics — without any of the rows corresponding to an actual identifiable person. 合成电子健康记录是一个人工生成的患者数据集，在统计上与真实人群的记录相似——同类型的诊断、操作、用药、就诊模式，聚合统计量也相似——但其中没有任何一行对应一个真实可识别的个人。 The motivation is that de-identifying real EHR data by stripping obvious identifiers like name and birth date doesn't actually eliminate re-identification risk, because rare combinations of diagnoses, procedures, and visit timing can still uniquely fingerprint a person, especially in a small or rare-disease cohort. 这样做的动机是，仅仅通过去掉姓名、出生日期等明显标识符来对真实电子健康记录做去标识化处理，实际上并不能真正消除重新识别的风险，因为诊断、操作和就诊时间的罕见组合仍然可能唯一地"指纹式"标记出一个人，在小规模或罕见病队列中尤其如此。 A good synthetic dataset lets you share data more freely for tool development, methods testing, or collaboration, without exposing any real patient to that risk. 一个好的合成数据集能让你更自由地共享数据，用于工具开发、方法测试或合作，而不会让任何真实患者暴露在这种风险之下。

JORDAN And "high-dimensional" and "hierarchical autoregressive" — what work are those two words doing in the title? 那标题里的"高维"（high-dimensional）和"分层自回归"（hierarchical autoregressive）这两个词又是什么意思？

ALEX An EHR is naturally a sequence of visits, and each visit can carry any combination of over 10,000 distinct diagnosis, procedure, and medication codes, plus lab values — so a full patient record is a genuinely enormous, sparse, structured object, not a small fixed-length feature vector. 电子健康记录本质上是一系列就诊记录的序列，每次就诊可能携带超过一万种不同诊断、操作和用药代码中的任意组合，再加上化验值——所以一份完整的患者记录其实是一个非常庞大、稀疏、结构化的对象，而不是一个固定长度的小型特征向量。 "High-dimensional" just means the authors are modeling that full native complexity rather than shrinking it down to a manageable handful of variables. "高维"指的正是作者在建模这种完整的原生复杂度，而不是把它压缩成少数几个便于处理的变量。 "Autoregressive" means the model generates each new piece of data conditioned on everything generated before it, the same way a language model predicts the next word given the previous words. "自回归"（autoregressive）意味着模型在生成每一条新数据时，都以之前生成的所有内容为条件，就像语言模型根据前面的词来预测下一个词一样。 "Hierarchical" is the specific trick for handling the EHR's two natural levels of structure at once: which visits happened in what order, and which specific codes occurred within each visit — modeling both levels with one flat sequence model would either lose the fine-grained code detail or blow up computationally, so they split it into two coupled modules instead. "分层"（hierarchical）则是专门用来同时处理电子健康记录中两个天然结构层级的技巧：哪些就诊按什么顺序发生，以及每次就诊内部具体出现了哪些代码——如果用单一的扁平序列模型同时处理这两个层级，要么会丢失精细的代码细节，要么计算量会爆炸，所以他们把模型拆成了两个相互耦合的模块。

JORDAN What was the actual gap in prior synthetic-EHR methods that HALO is responding to? 之前的合成电子健康记录方法到底存在什么缺口，是 HALO 要回应的？

ALEX Every prior generative approach the authors compare against had to shrink the problem to make it tractable: MedGAN modeled 615 disease categories with no visit-level timing at all; SynTEG aggregated codes up to higher-level phenotypes and dropped rare ones, landing at 1276 variables; ehrMGAN reduced dimensionality to under 100 variables; and EVA modeled only frequent co-occurrence patterns as one-hot vectors, which caps its ability to generate novel but plausible combinations. 作者所比较的每一种此前的生成方法，都不得不缩小问题规模才能让计算可行：MedGAN 只建模了 615 个疾病类别，完全没有就诊层面的时间信息；SynTEG 把代码聚合到更高层级的表型并剔除了罕见代码，最终只剩 1276 个变量；ehrMGAN 把维度压缩到不足 100 个变量；而 EVA 只把频繁共现的模式建模为独热向量（one-hot vector），这就限制了它生成新颖但合理组合的能力。 That aggressive dimensionality reduction is fine if your downstream use case only needs those specific reduced variables, but it makes the resulting synthetic data unusable for anything requiring the full native code space — comprehensive statistical analysis, fine-grained phenotyping, billing-level detail, or general-purpose data sharing where you don't know in advance which specific codes a future user will need. 如果下游应用场景只需要那些经过缩减的特定变量，这种激进的降维处理完全没问题，但这会导致生成的合成数据无法用于任何需要完整原生代码空间的场景——全面的统计分析、精细的表型分析、账单级别的细节，或者事先不知道未来使用者具体需要哪些代码的通用数据共享场景。 That's the specific gap HALO is built to close: generate synthetic data at the same native granularity as the real EHR, without picking and choosing which codes matter in advance. 这正是 HALO 要填补的具体缺口：以与真实电子健康记录相同的原生粒度生成合成数据，而无需事先挑选哪些代码是重要的。

JORDAN Walk through the architecture itself — what are the two modules actually doing? 具体讲讲这个架构本身——这两个模块到底在做什么？

ALEX The coarse, visit-level module is a stack of twelve transformer decoder blocks using masked self-attention, the same mechanism that powers most modern large language models, and its job is to read a patient's visit history so far and produce a compact embedding summarizing everything relevant about that history at each point in time. 粗粒度的就诊层模块是由十二个使用掩码自注意力（masked self-attention）机制的 Transformer 解码器块堆叠而成的——这正是驱动大多数现代大语言模型的核心机制——它的任务是读取患者到目前为止的就诊历史，并在每个时间点生成一个紧凑的嵌入向量（embedding），概括该历史中所有相关信息。 The fine, code-level module then takes that visit-history embedding and, for the current visit being generated, predicts each individual code's presence one at a time using masked linear layers with an upper-triangular masking pattern, so each code prediction can see both the full prior visit history and the codes already placed earlier in the same visit, but not codes that haven't been generated yet. 而精细的代码层模块则接收这个就诊历史嵌入，对于正在生成的当前这次就诊，使用带有上三角掩码模式（upper-triangular masking）的掩码线性层，逐一预测每个具体代码是否出现，这样每次代码预测都能看到完整的既往就诊历史，以及同一次就诊中已经生成的代码，但看不到尚未生成的代码。 That upper-triangular masking trick is what lets the code-level module scale to modeling roughly a million within-visit code co-occurrence probabilities and about five million across-visit conditional probabilities without needing a heavier sequential architecture that would run out of memory at that scale. 正是这种上三角掩码技巧，让代码层模块能够扩展到建模大约一百万种同一就诊内代码共现概率，以及约五百万种跨就诊条件概率，而不需要在这个规模下会耗尽内存的更重型的序列架构。 If I'm pushing on a design choice here, it's the paper's own limitation, stated plainly in its discussion: HALO generates records through a probabilistic sampling process, and there's no guarantee any single sampled record is clinically coherent — you could, in principle, sample a combination of codes that's individually plausible at the population level but nonsensical for one patient, and the authors' proposed fix is postprocessing with clinical rules that they don't actually build or test in this paper. 如果要对这里的一个设计选择提出质疑，那正是论文自己在讨论部分坦白承认的局限性：HALO 通过概率采样过程生成记录，无法保证任何单一采样出的记录在临床上是自洽的——原则上你完全可能采样出一种在人群层面上单独看都合理、但放在同一个患者身上却说不通的代码组合，而作者提出的解决方案是用临床规则做后处理，但他们在这篇论文里并没有真正构建或测试这一步。

JORDAN What data did they train and test it on? 他们用什么数据来训练和测试模型？

ALEX Two datasets: a comprehensive outpatient claims dataset built on the CMS/SynPUF structure, and the MIMIC-III inpatient EHR dataset, both split 0.8/0.2 for training and test with a further 0.9/0.1 training/validation split, trained with the Adam optimizer for 50 epochs on a single NVIDIA V100 GPU. 使用了两个数据集：一个基于 CMS/SynPUF 结构构建的综合门诊理赔数据集，以及 MIMIC-III 住院电子健康记录数据集，两者都按 0.8/0.2 划分为训练集和测试集，训练集内部再按 0.9/0.1 进一步划分为训练和验证集，使用 Adam 优化器在单张 NVIDIA V100 GPU 上训练 50 个周期（epoch）。 They kept the original ICD codes without aggregating or removing rare ones, which is the whole point given what they're trying to demonstrate. 他们保留了原始的 ICD 编码，没有做聚合，也没有剔除罕见编码，这正是他们想要证明的重点所在。

JORDAN And the results — did it actually deliver realistic, high-fidelity data? 那么结果如何——它是否真的生成了真实感强、高保真度的数据？

ALEX On statistical similarity, code-occurrence probabilities in the synthetic data correlated above 0.9 with the real data across roughly 10,000 individual codes and over a million code pairs — a strong quantitative match on the aggregate distribution. 在统计相似性方面，合成数据中的代码共现概率与真实数据在大约一万个独立代码和超过一百万个代码对上的相关系数超过了 0.9——这是在聚合分布层面上一个很强的定量吻合结果。 On the language-modeling evaluation, HALO beat both compared baselines, with a 4% reduction in binary cross-entropy loss and a 17% increase in F1 score over the HALO-Coarse ablation — the same architecture but without the fine code-level module — on the inpatient dataset specifically, showing the two-level hierarchy is doing real work rather than just adding complexity for its own sake. 在语言建模评估方面，HALO 在两个基线上都表现更好，在住院数据集上，相比 HALO-Coarse 消融版本（同一架构但没有精细代码层模块），二元交叉熵损失降低了 4%，F1 分数提高了 17%，这说明这个两层架构确实在发挥实际作用，而不只是徒增复杂度。 On downstream utility, classifiers trained on HALO's synthetic data to predict chronic disease phenotypes reached accuracy close to classifiers trained on real data — an AUC of 0.938 for HALO-trained models versus 0.943 for real-data-trained models across a battery of chronic disease labels — and combining real with HALO-generated synthetic data pushed accuracy even higher than real data alone. 在下游应用效果方面，用 HALO 合成数据训练出的、用于预测慢性病表型的分类器，其准确率接近用真实数据训练出的分类器——在一系列慢性病标签上，HALO 训练模型的 AUC 为 0.938，而真实数据训练模型的 AUC 为 0.943——而将真实数据与 HALO 生成的合成数据结合使用，其准确率甚至超过了单独使用真实数据。 On a deliberately imbalanced rare-condition test — 50,000 records without a cancer label against just 1000 with it — augmenting the imbalanced set with HALO-generated positive records approached the performance of a fully balanced real-data set, which matters directly for anything CF-scale, since CF is itself a rare, imbalanced condition relative to a general population dataset. 在一个刻意构造的不平衡罕见病测试中——5 万条无癌症标签记录对上仅 1000 条有癌症标签的记录——用 HALO 生成的阳性记录对这个不平衡数据集做增强，其效果接近于完全平衡的真实数据集，这一点对任何 CF 规模的数据都直接相关，因为相对于一般人群数据集而言，CF 本身就是一种罕见、不平衡的病种。 Finally, on privacy, a membership-inference attack — trying to determine whether a specific real record was used in training — succeeded only about 50% of the time on both the model and the synthetic dataset itself, which is chance-level performance, meaning the attack learned essentially nothing. 最后，在隐私方面，一种成员推断攻击（membership-inference attack）——试图判断某条特定真实记录是否被用于训练——无论针对模型本身还是合成数据集，成功率都只有大约 50%，这属于随机猜测水平的表现，意味着这种攻击几乎没有学到任何有用信息。 So yes, on essentially every metric the paper set out to evaluate — statistical fidelity, downstream classifier utility, rare-condition augmentation, and privacy — it delivered on its stated aim. 所以，在这篇论文所设定要评估的几乎每一个指标上——统计保真度、下游分类器效用、罕见病数据增强，以及隐私保护——它都达成了自己设定的目标。

JORDAN Where does this land for what Runyu's actually building toward? 这和 Runyu 实际的建设方向有什么关系？

ALEX This is the AI-applied-to-registry/bioinformatics, tool-development, career-aligned priority — that's the one to name here, not the Karen collaboration or the Liz-assigned data-quality work, since HALO's contribution is a general-purpose data-generation architecture, not a domain-specific finding. 这属于"AI 应用于登记处/生物信息学、工具开发导向、职业发展相关"这一优先事项——这是这里应该点名的那一个，而不是 Karen 合作方向，也不是 Liz 分配的数据质量工作，因为 HALO 的贡献是一个通用的数据生成架构，而不是一个特定领域的发现。 It ships code on GitHub, has a published, reproducible architecture, and solves a problem that comes up constantly in registry-adjacent tooling work: how do you build, test, and demo a pipeline against realistic longitudinal structured data before — or without ever — touching the real thing. 它在 GitHub 上开源了代码，拥有一个已发表、可复现的架构，并且解决了一个在登记处相关工具开发工作中经常出现的问题：如何在接触真实数据之前——或者根本不接触真实数据的情况下——针对真实感强的纵向结构化数据构建、测试和演示一个流水线。 The tool sketch: a scaled-down, single-level version of HALO's autoregressive approach — skip the full twelve-block visit-history transformer at first — trained on a narrow slice of de-identified, structured longitudinal encounter data (visit timing plus a handful of variables, external methods only, never CFFPR internals) to produce a synthetic dataset useful for testing a pipeline's behavior, including deliberately injecting known synthetic errors into it the way growthcleanr's successors have used Monte Carlo simulation to validate outlier-detection logic against ground truth that a real dataset can never fully provide. 工具原型构想是：HALO 自回归方法的一个缩小版、单层版本——先跳过完整的十二层就诊历史 Transformer——在一小部分去标识化的结构化纵向就诊数据（就诊时间加上少数几个变量，仅使用外部方法，绝不涉及 CFFPR 内部细节）上训练，生成一个可用于测试流水线行为的合成数据集，包括刻意向其中注入已知的合成错误，就像 growthcleanr 的后继方法曾用蒙特卡洛模拟来验证异常值检测逻辑一样，用真实数据集永远无法完全提供的已知真值来做验证。 Difficulty: Large for anything close to HALO's full two-module architecture at native EHR dimensionality;
