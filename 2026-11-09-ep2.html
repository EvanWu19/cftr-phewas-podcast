Ep2 (Track B — AI tooling): WESkit and standardized workflow execution

Schneider-Lunitz and colleagues at Charité Berlin and DKFZ (Bioinformatics, 2026) describe WESkit, an open-source implementation of the GA4GH Workflow Execution Service (WES) API that handles the execution, monitoring, and documentation of computational workflows. It supports both Snakemake and Nextflow, deploys via Docker Compose or Kubernetes/Helm, runs on HPC schedulers (LSF, SLURM) or container orchestration, and authenticates via OpenID Connect. It was built as the backend for the data-management system One-Touch-Pipeline (OTP) at DKFZ and Charité, where it processed roughly 20,000 cancer and research samples across 660,000 workflow runs between October 2024 and 2025, with linear scaling as API instances and workers are added. This is not a research study — it's a systems/infrastructure report — and it's read for the AI-tooling/career track rather than for any genomics finding. The transferable pattern is standardizing how a pipeline gets executed, monitored, and audited at scale, which maps directly onto giving any registry-QC flagging pipeline the same kind of unified, queryable run history. Buildable artifact: a minimal WES-compliant execution wrapper around an existing Snakemake/Nextflow anthropometric-flagging pipeline.

Plain-English glossary

  • GA4GH (Global Alliance for Genomics and Health) — An international standards body that writes interoperability specifications so genomic and health-data tools built by different institutions can work together.（中文：一个国际标准组织，负责制定互操作性规范，使不同机构开发的基因组与健康数据工具能够相互协作。）
  • WES (Workflow Execution Service) — A GA4GH API specification defining a standardized way to submit a workflow, check its status, and retrieve results, regardless of the underlying workflow engine.（中文：GA4GH的一项API规范，定义了提交工作流、查询状态、获取结果的统一方式，不依赖具体的底层工作流引擎。）
  • Workflow management system (WfMS) — Software such as Snakemake or Nextflow that lets a multi-step data-processing pipeline be described as one reproducible unit and executed in the correct order with the right resources.（中文：如Snakemake或Nextflow这类软件，能将多步骤的数据处理流程描述成一个可复现的整体，并按正确顺序、用正确资源执行。）
  • FAIR principles — Findable, Accessible, Interoperable, Reusable: a widely adopted framework for managing research data, software, and workflows so others can later find, access, understand, and reuse them.（中文：可查找、可访问、可互操作、可重用——一套被广泛采纳的框架，用于管理研究数据、软件和工作流，使他人日后能够找到、访问、理解并重用它们。）
  • RO-Crate — A packaging format that records, in a structured machine-readable way, exactly which workflow, inputs, and configuration produced a given set of results.（中文：一种打包格式，以结构化、机器可读的方式记录是哪个工作流、哪些输入、哪种配置产生了某组结果。）
  • OIDC / JWT (OpenID Connect / JSON Web Token) — A federated authentication standard (OIDC) in which the user authenticates once and presents a signed token (JWT) proving their identity, so a service can act on their behalf without managing passwords itself.（中文：OIDC是一种联合身份认证标准，用户完成一次认证后出示一个签名令牌（JWT）证明身份，使服务无需自行管理密码即可代表用户执行操作。）
  • TES / DRS / TRS (Task Execution Service / Data Repository Service / Tool Registry Service) — Related GA4GH cloud-work-stream specifications: TES runs individual compute tasks across federated infrastructure, DRS locates datasets by a stable identifier regardless of physical location, and TRS publishes and discovers workflows (e.g. via WorkflowHub).（中文：GA4GH云端工作流生态中的相关规范：TES负责在联邦化基础设施上运行计算任务，DRS负责通过稳定标识符定位数据集，TRS负责发布和发现工作流。）

Full citation

Schneider-Lunitz V, Kensche PR, Kraatz L, Strubel P, Borufka S, Parala G, Kanitz A, Eils R, Buchhalter I, Twardziok S. "Managing workflow executions with WESkit." Bioinformatics (Oxford, England). 2026. PMID: 41734277 | PMCID: PMC13032820 | DOI: 10.1093/bioinformatics/btag091

Methods / tools to lift

  • GA4GH WES API as a universal execution interface — one stable API that decouples a data-management system from needing to know the internals of every workflow engine or cluster backend it submits to.
  • Celery + MongoDB execution-tracking architecture — asynchronous job submission/status-checking workers backed by a persistent, queryable run-metadata store.
  • RO-Crate-extensible execution logging — structured, machine-readable provenance records (workflow, inputs, config) extended with WESkit's own run logs.

Where it lands + buildable artifact

Lands on AI-tooling/career (not Karen, Liz, or colocalization directly). Buildable artifact — Registry-QC WES Execution Wrapper: a minimal WES-compliant layer (run-submission endpoint, status-check endpoint, MongoDB-backed run log recording config/timestamp/input scope) placed in front of an existing Snakemake or Nextflow anthropometric-flagging pipeline, giving every nightly flagging batch a unified, queryable audit trail. Difficulty: M (medium) — the spec is well documented; correctly wiring persistent run metadata and deciding what counts as "the config" worth recording is the real design work.

What to verify first

  • Which identity provider / authentication setup would be organizationally appropriate for anything touching registry-adjacent data — a governance question, not a claim about CFFPR's actual infrastructure.
  • Whether the full Celery-plus-MongoDB stack is proportionate for a single nightly pipeline versus DKFZ's multi-team, 660,000-runs-a-year scale, or whether something lighter would serve as well.
  • Whether an MIT-licensed open-source dependency like WESkit would clear the applicable software-approval process in this setting.
  • That the 660,000-run production number runs alongside still-migrating legacy workflows (the paper's own first Nextflow-based FASTQC run through WESkit is explicitly described as preproduction), so it is not yet a complete replacement of prior execution methods.

ALEX GA4GH is the Global Alliance for Genomics and Health, an international standards body for genomic and health data — think of it as the group that writes the interoperability specs so that different institutions' tools can talk to each other. GA4GH（基因组学与健康全球联盟）是一个国际性的基因组与健康数据标准组织（中文：负责制定互操作性规范，让不同机构的工具能够相互对接的国际组织）——可以把它理解成那个负责制定互操作规范的团体，这样不同机构的工具才能彼此对接。 WES is the Workflow Execution Service, one of GA4GH's API specifications: a standardized way to submit a computational workflow, check its status, and retrieve its results, regardless of which underlying workflow engine is actually running it. JORDAN And "workflow engine" here means things like Snakemake and Nextflow? "工作流引擎"在这里指的就是Snakemake和Nextflow这类东西？

ALEX Right — those are workflow management systems, or WfMS, that let you describe a multi-step data-processing pipeline — align reads, call variants, annotate, and so on — as a single reproducible unit, and then actually execute each step in the right order with the right resources. 没错——这些叫工作流管理系统（Workflow Management System，简称WfMS），能让你把一个多步骤的数据处理流程——比对、变异检测、注释等等——描述成一个可复现的整体，然后按正确的顺序、用正确的计算资源真正执行每一步。 WESkit doesn't replace Snakemake or Nextflow; it sits on top of both, as a standardized execution and monitoring layer. WESkit并不是要取代Snakemake或Nextflow；它是架在这两者之上的一层标准化执行和监控层。

JORDAN Two more terms I saw in the abstract — FAIR and RO-Crate. 我在摘要里还看到两个术语——FAIR和RO-Crate。

ALEX FAIR stands for Findable, Accessible, Interoperable, Reusable — a widely adopted set of principles for how research data and, increasingly, research software and workflows should be managed so that someone else can actually find, access, understand, and reuse them later. FAIR指的是可查找（Findable）、可访问（Accessible）、可互操作（Interoperable）、可重用（Reusable），（中文：一套被广泛采纳的原则，用来规范研究数据乃至研究软件和工作流的管理方式，使别人日后能够真正找到、访问、理解并重用它们）是一套被广泛采纳的原则，规定了研究数据——以及越来越多的研究软件和工作流——应该如何被管理，才能让别人日后真正找到、访问、理解并重用它们。 RO-Crate is a specific packaging format that implements that idea for workflow outputs — it records, in a structured, machine-readable way, exactly which workflow, which inputs, and which configuration produced a given set of results. RO-Crate是一种具体的打包格式，把这个理念落实到了工作流输出上（中文：以结构化、机器可读的方式记录是哪个工作流、哪些输入、哪种配置产生了某组结果）——它以结构化、机器可读的方式记录下究竟是哪个工作流、用了哪些输入、配置了什么参数，才产生了这组结果。 WESkit is explicitly built to extend RO-Crate packaging with its own execution logs. WESkit明确设计成要用自己的执行日志去扩展RO-Crate的打包内容。

JORDAN So what problem were they actually trying to solve? 那他们实际想解决的是什么问题？

ALEX At a place like DKFZ or Charité, you're not running one pipeline once — you're running many different pipelines, with different parameters, different input files, and sometimes different workflow engines, across many different research projects, year after year. 在像DKFZ或夏里特这样的机构里，你不是只跑一次某一个流程——你是在许多不同的研究项目中，年复一年地运行许多不同的流程，用不同的参数、不同的输入文件，有时甚至用不同的工作流引擎。 That creates real problems for scalability, reproducibility, and collaboration: if every project's workflow submission and monitoring is done by hand, or through a one-off script, you lose track of what ran, with what configuration, and whether two "the same" runs were actually the same. 这会给可扩展性、可复现性和协作带来真正的问题：如果每个项目的工作流提交和监控都是靠手工操作或一次性脚本来完成的，你就会搞不清楚到底跑了什么、用了什么配置，以及两次"相同"的运行是不是真的完全一样。 Before WESkit, the data-management system One-Touch-Pipeline, or OTP, handled this itself — submitting and monitoring workflows directly — which meant OTP needed intimate knowledge of every workflow engine and every cluster backend it talked to. 在WESkit出现之前，数据管理系统One-Touch-Pipeline（简称OTP）自己处理这件事——直接提交和监控工作流——这意味着OTP必须对它所对接的每一种工作流引擎、每一种计算集群后端都了如指掌。 That's a tight coupling problem: every time you want to add a new workflow engine or move to a new cluster system, you have to modify OTP's own internals. 这是一个紧耦合问题：每次你想添加一种新的工作流引擎，或者迁移到一套新的集群系统，你都得去改动OTP自身的内部代码。

JORDAN And GA4GH's WES spec exists specifically to break that coupling? 而GA4GH的WES规范，存在的目的就是为了打破这种耦合？

ALEX Exactly — it defines one stable interface that any data-management system can talk to, and any workflow engine can be plugged in behind, so you only have to solve "how do I submit and monitor a workflow" once, rather than once per engine, per data-management system, per institution. 正是如此——它定义了一个稳定的接口，任何数据管理系统都可以对接它，而任何工作流引擎都可以插在它背后，这样你只需要解决一次"如何提交和监控一个工作流"的问题，而不必针对每种引擎、每个数据管理系统、每个机构都重新解决一次。 WESkit is one concrete, open-source implementation of that interface, purpose-built to be the backend for OTP, but designed to be reusable as a standalone WES service for anyone else too. WESkit就是这个接口的一个具体、开源的实现，最初是为OTP量身定制的后端，但设计上也能作为一个独立的WES服务被其他任何人复用。

JORDAN Walk me through the architecture. 说说它的架构。

ALEX It's a Flask and uWSGI web service in Python, implementing WES API version 1.1.0, built with an object-oriented design so that variable pieces — the workflow engine, the container system, the database, the cluster scheduler — are each encapsulated behind an internal API and can be swapped independently. 它是用Python写的Flask和uWSGI网络服务，实现了WES API 1.1.0版本，采用面向对象设计，这样可变的部分——工作流引擎、容器系统、数据库、集群调度器——都被封装在各自的内部API之后，可以独立替换。 Requests are handled asynchronously through Celery workers, which manage submitting runs to the compute infrastructure and checking job status, and run metadata and job states are persisted in a MongoDB database. 请求是通过Celery工作进程异步处理的，由它们负责向计算基础设施提交任务并查询状态，而运行的元数据和任务状态则持久化存储在一个MongoDB数据库里。 Authentication runs on OpenID Connect, or OIDC — users authenticate client-side and send their job request with a JWT, a signed token that proves who they are, so the server can act on a user's behalf without managing passwords itself. 身份认证基于OpenID Connect（简称OIDC）——用户在客户端完成认证，然后把带有JWT（JSON Web Token，中文：一种签名令牌，用来证明用户身份）的任务请求发送给服务器，这样服务器就能代表用户执行操作，而不需要自己管理密码。 It deploys via Docker Compose or Kubernetes with Helm charts, and submits workflows to HPC schedulers like LSF and SLURM or to container orchestration clusters. 它可以通过Docker Compose或者带Helm charts的Kubernetes来部署，并能把工作流提交给LSF、SLURM这类高性能计算（HPC）调度系统，或者提交到容器编排集群。

JORDAN Anything you'd push back on in that design? 这个设计里有什么你会质疑的地方吗？

ALEX One choice stands out: "files generated as job results are generally not managed by WESkit but rather by different processes." 有一个设计选择很突出："任务结果生成的文件通常不由WESkit管理，而是由其他流程来负责。" That's a deliberate separation of concerns — WESkit tracks execution and metadata, not data products — and it keeps the service lightweight and focused. 这是刻意的职责分离——WESkit追踪的是执行过程和元数据，而不是数据产物本身——这样能让这个服务保持轻量和专注。 But it also means WESkit's "unified documentation of workflow executions" doesn't actually give you a unified view of where the output data physically lives or whether it's still there; you need a separate data-management layer for that, and the paper doesn't say how tightly that separate layer is expected to stay in sync with WESkit's own run records. 但这也意味着WESkit所说的"工作流执行的统一文档记录"，并不能真正告诉你输出数据物理上存放在哪里、它是否还存在；你需要一个独立的数据管理层来解决这个问题，而论文并没有说明这个独立层应该在多大程度上与WESkit自身的运行记录保持同步。 For an audit trail, that's a real gap worth naming. 从审计追溯的角度看，这确实是一个值得指出的真实缺口。

JORDAN Before we get to scale — is this actually running in production yet, or still a pilot? 在我们谈规模之前——这个系统是不是已经真正投入生产使用了，还是还处于试点阶段？

JORDAN Does it actually work at scale? 它在规模化场景下真的管用吗？

JORDAN The discussion also mentions TES, DRS, and TRS — more GA4GH alphabet soup? 讨论部分还提到了TES、DRS和TRS——又是一堆GA4GH缩写？
