Track A — Variant Interpretation & Harmonization

Blurb

The same genetic variant can be written as HGVS or SPDI, against different transcripts, the chromosome or the gene, on GRCh37 or GRCh38, and left-, right- or fully justified, and none of those versions is wrong. Dolin and colleagues (JAMIA, 2025) show how they put clinical-grade normalization into FHIR Genomics Operations, a public, open-source reference implementation. It handles genetic variants, HLA alleles and annotation terminology. We follow how their variant pipeline changed over about five years: first a ClinGen registry lookup, then NCBI's SPDI web service, and now a fully local biocommons/hgvs + seqrepo + uta stack that converts everything to chromosome-level, fully justified SPDI. Patient data and incoming queries go through the same normalization. We also go through their candid failure-mode table. Then we connect the paper to CFTR variant-notation harmonization and propose a small local CFTR normalizer that flags every notation it can't resolve, so nothing gets dropped without notice.

Glossary

  • biocommons/hgvs — Open-source Python package that parses, validates and converts HGVS variant expressions between transcript and chromosomal coordinates.（中文：用于解析、校验和转换HGVS变异表示的开源Python库）
  • Canonical form — The single agreed representation that all synonymous notations of a variant are converted into before storage or comparison.（中文：规范形式，所有同义表示统一转换成的约定表示）
  • Categorical variant — A class that subsumes many underlying variants (e.g., "BRAF Class 2 Mutation"); not yet formally standardized.（中文：类别变异，涵盖一组具体变异的类别，尚未正式标准化）
  • ClinGen Allele Registry — Registry assigning identifiers to known variants; usable for synonym lookup but cannot normalize novel variants.（中文：ClinGen维护的等位基因注册库，可做同义词查找但无法处理新变异）
  • ConceptMap — Standard FHIR resource that records mappings between codes in different terminologies.（中文：FHIR中用于跨术语体系映射的标准资源）
  • FHIR / FHIR Genomics — HL7's healthcare data-exchange standard and its genomics component, which also has formalisms for representing variants.（中文：快速医疗互操作性资源标准及其基因组学部分）
  • GA4GH VRS — Global Alliance for Genomics and Health Variant Representation Specification, a computable variant-representation standard.（中文：全球基因组与健康联盟制定的变异表示规范）
  • GRCh37 / GRCh38 — Human reference genome builds (hg19, 2009; hg38, 2013); the same variant has different coordinates on each.（中文：人类参考基因组的两个版本，同一变异在两者中坐标不同）
  • HGVS — Human Genome Variation Society nomenclature; text notation of the form reference:type.position change, e.g., NC_000019.9:g.11200236G>A, using 1-based positions.（中文：人类基因组变异学会制定的变异命名规范，采用从1开始的坐标）
  • HLA — Human leukocyte antigen region on chromosome 6, one of the most complex and diverse regions of the genome.（中文：人类白细胞抗原，位于6号染色体的高度多样的免疫相关基因区域）
  • Interbase (0-based) coordinates — Coordinates that count the gaps between bases; the reason SPDI positions are one lower than HGVS positions.（中文：碱基间坐标，从零开始计数碱基之间的间隙）
  • Justification — The convention for placing an indel inside a repeat: left (first base), right (last base) or full (the whole repeat).（中文：对齐方式，决定重复序列中插入/缺失位置的约定）
  • LRG — Locus Reference Genomic, a stable gene-level reference sequence identifier (e.g., LRG_130); not supported by the paper's pipeline.（中文：基因座参考基因组序列标识）
  • MAC code — Compressed HLA ambiguity code; e.g., DRB1*13:AKBAR stands for five specific alleles.（中文：压缩表示多个候选HLA等位基因的歧义编码）
  • NCBI — US National Center for Biotechnology Information, which maintains the NM_/NC_/NG_ reference sequences and the SPDI service.（中文：美国国家生物技术信息中心）
  • Normalization — Converting synonymous representations of the same genomic fact into one canonical form.（中文：规范化，把同义表示转换成统一规范形式的过程）
  • Pre-/post-coordination — Expressing a clinical concept as one combined code versus a combination of several codes.（中文：预组配与后组配，用单个编码或多个编码组合表达同一概念）
  • py-ard — National Marrow Donor Program Python library for normalizing HLA nomenclature against the IPD-IMGT/HLA Database.（中文：美国国家骨髓捐赠计划开发的HLA命名规范化Python库）
  • Reference genome build — A versioned assembly of the human genome against which coordinates are measured.（中文：参考基因组版本）
  • Reference sequence — The sequence a variant is described against (chromosome NC_, transcript NM_, gene NG_, or LRG).（中文：参考序列，描述变异时所依据的序列）
  • seqrepo — biocommons local repository of reference sequences used by biocommons/hgvs.（中文：存放参考序列的本地仓库）
  • SPDI — NCBI's Sequence-Position-Deletion-Insertion format, e.g., NC_000019.9:11200235:G:A, using 0-based interbase positions.（中文："序列-位置-删除-插入"四段式变异表示格式）
  • Structural variant — Large deletion, duplication or translocation, often with imprecise endpoints that SPDI cannot represent.（中文：结构变异，常有不精确的断点）
  • Transcript — An RNA product of a gene (NM_ accession); "c." HGVS coordinates are relative to a transcript.（中文：转录本，"c."坐标相对于它定义）
  • uta — Universal Transcript Archive; biocommons database of transcript-to-chromosome alignment metadata.（中文：存储转录本与染色体比对关系的元数据库）
  • VCF — Variant Call Format, the standard text file format for variant calls from sequencing pipelines.（中文：变异调用格式，测序流程输出变异的标准文件格式）

Methods/tools to lift

  • biocommons/hgvs: local Python HGVS parser, validator and converter between HGVS, SPDI and chromosomal coordinates.
  • biocommons/seqrepo: local reference-sequence store, so normalization doesn't depend on calling NCBI.
  • biocommons/uta: transcript-to-chromosome alignment metadata that makes transcript-relative ("c.") notation resolvable.
  • Chromosome-level, fully justified SPDI canonical form: one representation that supports range-based search and removes justification ambiguity.
  • Dual-point normalization pattern: the same pipeline runs on ingested data, ingested knowledge and incoming query parameters.
  • Raw + normalized in responses: return both forms so rule writers can target the canonical form while keeping provenance.
  • py-ard: HLA nomenclature normalization against the IPD-IMGT/HLA Database.
  • FHIR ConceptMaps: standard cross-terminology mapping resource, used for single-best-match code translation.
  • Table 4 failure-mode list: ready-made edge-case test checklist (HGVS syntax gaps, LRG notation, missing local transcripts, structural variants, HLA string formats, terminology hierarchy).
  • Code and demo: https://github.com/FHIR/genomics-operations and https://fhir-gen-ops.herokuapp.com/

Where it lands + buildable artifact

Priority: Karen Raraigh collaboration — CFTR variant interpretation and harmonization.

Why it's relevant: CFTR variant-notation harmonization is a stated near-term priority, and this paper is an open-source, production-grade example of the same problem: synonym resolution and canonical forms for variant notation, solved in a different setting. The useful lesson isn't to adopt FHIR Genomics Operations wholesale. It's three narrower things: (a) the local biocommons/hgvs + seqrepo + uta toolchain, which can resolve HGVS or SPDI from any transcript or build into one canonical chromosomal form with no external API; (b) the rule that data and queries are normalized the same way; and (c) Table 4 as a checklist of edge cases that any CFTR harmonization effort should test.

Buildable artifact (paste-ready MVP): A local CFTR variant-notation normalizer. Input: a table of CFTR variant notations in mixed formats (HGVS against various transcripts, SPDI, chromosome- or gene-relative) from whatever sources Karen's side uses. Engine: biocommons/hgvs, with seqrepo and uta loaded with the CFTR region only. Output: each variant resolved to one canonical chromosome-level SPDI (or HGVS, if Karen's side prefers), plus a failure-triage report that sorts every notation that fails to normalize into Table 4's categories for manual review, so nothing is dropped silently. One-line MVP: mixed CFTR notations in, one canonical SPDI per variant plus a failure-triage report out. Difficulty: S–M. The hard normalization logic is already mature in biocommons/hgvs. The work is wiring it up, scoping the local sequence databases to CFTR and building the triage report.

What to verify first

  • Coverage: we'd run a real sample of CFTR notations from the sources Karen's side actually uses (e.g., ClinVar, CFTR2, internal lab reports) through Table 4's failure categories, to see what fraction fails to normalize and why before assuming full coverage.
  • Canonical-form choice: SPDI, HGVS and GA4GH VRS each have tradeoffs, and the paper picks SPDI for range search. We'd need to check which form the downstream tools and collaborators that consume the harmonized CFTR list need.
  • Local sequence-database maintenance: we'd need to check how much work it takes to keep a CFTR-scoped seqrepo/uta populated and current as new transcripts and references are released, compared with calling a live NCBI API.
  • Structural and deep-intronic variants: CFTR has clinically important large structural and deep-intronic variants. The paper's limitations (SPDI can't represent imprecise SV endpoints, some HGVS syntax fails) need to be checked against CFTR's known variant catalog specifically, not assumed to be rare edge cases.

JORDAN The title is a mouthful, so let's unpack the vocabulary first. 标题有点长，所以我们先拆解一下词汇。 Start with HGVS, because I see it everywhere. 先从HGVS讲起吧，因为我到处都能看到它。 What am I actually looking at in a string like NC_000019.9:g.11200236G>A? 像NC_000019.9:g.11200236G>A这样的字符串，我到底在看什么？

ALEX HGVS is the Human Genome Variation Society nomenclature, the standard way to write a variant as text. HGVS（人类基因组变异学会制定的变异命名规范）是用文本书写变异的标准方式。 The part before the colon is the reference sequence, here NC_000019.9, which is chromosome 19, version 9. 冒号前面的部分是参考序列（reference sequence），这里是NC_000019.9，即19号染色体序列的第9版。 The "g." says the coordinates are genomic, as opposed to "c." for coding-transcript coordinates. "g."表示坐标是基因组坐标，与之相对的"c."表示编码转录本坐标。 Then comes position 11200236, where the reference base G is changed to A. 接着是位置11200236，此处参考碱基G变成了A。

JORDAN And SPDI? 那SPDI呢？

ALEX SPDI is the Sequence-Position-Deletion-Insertion format from NCBI. SPDI（"序列-位置-删除-插入"四段式变异表示格式）是由NCBI（美国国家生物技术信息中心）制定的格式。 The same variant becomes NC_000019.9:11200235:G:A, four fields separated by colons. 同一个变异写作NC_000019.9:11200235:G:A，由冒号分隔成四个字段。 Notice the position is one lower. 注意位置小了一。 That's because SPDI is zero-based and interbase, meaning it counts the gaps between bases, while HGVS is one-based and counts the bases themselves. 这是因为SPDI采用从零开始的碱基间（interbase）坐标，即计数碱基之间的间隙，而HGVS从一开始，计数的是碱基本身。

JORDAN So it's an off-by-one that is actually correct. 所以这是一个其实完全正确的"差一"。 What about builds, GRCh37 versus GRCh38? 那基因组版本呢，GRCh37和GRCh38？

ALEX A reference genome build is a versioned assembly of the human genome that coordinates are measured against. 参考基因组版本（reference genome build）是人类基因组的一个带版本号的组装，所有坐标都相对于它来度量。 GRCh37, also called hg19, is from 2009, and GRCh38, or hg38, is from 2013. GRCh37又称hg19，发布于2009年；GRCh38又称hg38，发布于2013年。 The same variant sits at different positions in each, so 11200236 on build 37 becomes 11089560 on build 38. 同一个变异在两个版本中位置不同，所以37版的11200236在38版中变成了11089560。

JORDAN And what does "justification" mean here? 那这里的"对齐方式"是什么意思？

ALEX Justification is about insertions and deletions inside repeated bases. 对齐方式（justification）针对的是重复碱基内部的插入和缺失。 If the reference has seven T's in a row and the patient has six, you cannot tell which T was lost. 如果参考序列连续有七个T，而患者只有六个，你无法判断丢失的是哪一个T。 Left-justified assumes the first one, right-justified assumes the last one, and fully justified describes the whole run, seven T's becoming six. 左对齐假设丢失的是第一个，右对齐假设是最后一个，而完全对齐则描述整个重复区段，即七个T变成六个T。

JORDAN Which brings us to canonical form. 这就引出了规范形式（canonical form）。

ALEX A canonical form is one agreed representation that every synonym gets converted into. 规范形式是所有同义表示都要被转换成的一种约定表示。 Normalization is that conversion. 规范化（normalization）就是这个转换过程。 Without it, exact-match search quietly misses records that describe the same variant differently. 没有它，精确匹配检索会悄无声息地漏掉那些以不同方式描述同一变异的记录。

JORDAN So what problem is this paper actually responding to? 那么这篇论文究竟在回应什么问题？

ALEX The core problem is that genomic data is wildly variable in how it's represented. 核心问题在于，基因组数据的表示方式极其多样。 The same variant, the same HLA allele, or the same annotation can be written in many synonymous ways. 同一个变异、同一个HLA（人类白细胞抗原，位于6号染色体的免疫相关基因区域）等位基因或同一条注释，都可以用许多种同义方式书写。 The authors argue that this is a major barrier to precise search, to writing clinical decision-support rules, and to variant annotation. 作者认为，这是精确检索、编写临床决策支持（clinical decision support）规则以及变异注释（variant annotation）的主要障碍。 Their Table 1 is a great tour of the problem. 他们的表1是对这个问题的一次很好的导览。 First, format: the HGVS string and the SPDI string we just read are the same variant. 首先是格式：我们刚才读到的HGVS字符串和SPDI字符串是同一个变异。 Second, the choice of reference sequence. 其次是参考序列的选择。 NM_001195798.2:c.12G>A and NM_001195803.2:c.12G>A are written against two different transcripts, yet both equal the chromosomal NC_000019.9:g.11200236G>A and the gene-level NG_009060.1:g.5180G>A. NM_001195798.2:c.12G>A和NM_001195803.2:c.12G>A是相对于两个不同转录本（transcript）书写的，但二者都等同于染色体层面的NC_000019.9:g.11200236G>A以及基因层面的NG_009060.1:g.5180G>A。

JORDAN Four strings, one variant. 四个字符串，一个变异。 And then builds stack on top of that. 然后基因组版本的差异还要叠加上去。

ALEX Right, GRCh37 NC_000019.9 versus GRCh38 NC_000019.10, at positions 11200236 versus 11089560. 对，GRCh37的NC_000019.9对比GRCh38的NC_000019.10，位置分别是11200236和11089560。 Then there's justification. 然后是对齐方式。 Their example is a run of seven T's starting at position 117548628 on NC_000007.14. 他们的例子是NC_000007.14上从位置117548628开始的一段由七个T组成的重复。 A one-base deletion there can be written left-justified, right-justified, or fully justified, and none of those is wrong. 那里的单碱基缺失可以写成左对齐、右对齐或完全对齐，而这些写法都不算错。

JORDAN Chromosome 7, that's CFTR's chromosome, isn't it? 7号染色体，那正是CFTR所在的染色体，对吧？

ALEX It is, but we'll treat the example as a general illustration rather than read anything CFTR-specific into it. 是的，但我们把这个例子当作一般性说明，而不从中解读出任何CFTR特有的含义。 The broader point is that different labs and tools pick different conventions, so the same variant looks different across sources without anyone making an error. 更广泛的要点是，不同实验室和工具采用不同的约定，因此同一变异在不同来源中看起来不同，但并没有人出错。

SNOMED 1259754003用一个编码表示原发性鳞状非小细胞肺癌，而SNOMED 372087000加上ICD-O-3（国际肿瘤疾病分类第三版）编码8070/3，则用两个编码的组合表达了同一事实。

JORDAN So what did they build? 那他们构建了什么？

ALEX The objective was to show that clinical-grade normalization algorithms can live inside a public, open-source FHIR Genomics reference implementation called FHIR Genomics Operations. 目标是证明临床级的规范化算法可以封装在一个公开、开源的FHIR Genomics参考实现（reference implementation）中，它叫FHIR Genomics Operations。 Their design considerations are worth lifting on their own. 他们的设计考量本身就值得借鉴。 One, reuse well-maintained open-source libraries instead of inventing new normalization algorithms. 第一，复用维护良好的开源库，而不是发明新的规范化算法。 Two, normalization should enhance basic search rather than replace it, since FHIR already supports exact code search and fuzzy token search. 第二，规范化应当增强而非取代基础检索，因为FHIR本身已经支持精确的编码检索和模糊的token检索。 Three, resolve variants to a chromosomal canonical form so that range-based search works. 第三，将变异解析为染色体层面的规范形式，以便基于区间的检索能够工作。 Four, run locally rather than depending on external API calls. 第四，在本地运行，而不是依赖外部API（应用程序接口）调用。

JORDAN How did the variant pipeline get to where it is now? 变异处理流程是怎么演变成现在这样的？
