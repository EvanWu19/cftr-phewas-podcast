Ep4 (Track C 2/2 — registry QC): Transparent Reporting of Data Quality in Distributed Data Networks

Paper: Kahn MG, Brown JS, Chun AT, Davidson BN, Meeker D, Ryan PB, Schilling LM, Weiskopf NG, Williams AE, Zozus MN. "Transparent Reporting of Data Quality in Distributed Data Networks." EGEMS (Washington, DC), 2015.

Blurb

The Data Quality Collaborative (DQC), convened by the EDM Forum, built a "data lifecycle" model tracking how data flows from originator through successive stewards to consumer, and produced 20 data-quality reporting recommendations formatted to parallel the STROBE reporting checklist — a "Table 1a for data-quality reporting." The 20 items split into four contexts: data capture descriptions (6), data processing descriptions / provenance (5), data elements characterizations (4, flagged as the most resource-intensive in practice despite being numerically smallest), and analysis-specific data elements characterizations (the remainder, deliberately the least prescriptive). Full text was retrieved (open access). The recommendations were developed via DQC teleconferences and outreach to 200+ individuals rather than a formal consensus method like Delphi, and the paper itself states that empirical evaluation of the recommendations' feasibility and cost hadn't been done at publication — this is an explicit proposal, not a validated one. Primary pipeline-stage touch: (d) evaluation — not a new accuracy metric, but a structured way to disclose what a flagging pipeline actually did, with a secondary touch on (c) adjudication/correction via its data-processing-provenance recommendations (outlier removal and flag-replacement must be disclosed). Buildable artifact: a DQ Reporting Scorecard that auto-generates a Kahn-style disclosure table from a pipeline description.

Plain-English glossary

  • Data lifecycle model — a conceptual model tracking how data flows from the originator, through successive data stewards, to the final data consumer.（中文:一种概念模型,追踪数据如何从产生者,经过一系列数据管理者,最终流向数据使用者。）
  • Data provenance — making explicit every transformation applied to a data element from creation to final storage (unit conversion, imputation, outlier removal, recoding).（中文:明确记录一个数据元素从产生到最终存储过程中经历的每一步转换,如单位换算、缺失值填补、异常值剔除、重编码。）
  • Distributed data network — a multi-site research setup where each site keeps patient data locally but agrees on a common data structure, so the same analysis can run across all sites without a central repository holding raw patient-level data.（中文:一种多站点研究架构,各站点在本地保留患者数据,但共同约定一套通用数据结构,使同一分析可在所有站点运行,而无需中央存储库持有原始患者层级数据。）
  • Fitness for use — whether a dataset is adequate for a specific intended analysis; a concept that applies only weakly to a general data warehouse but more strongly as the intended use narrows.（中文:一个数据集是否适合某个特定预期分析的概念;对通用数据仓库这一概念只是弱适用,但随着预期用途变得具体,适用性会增强。）
  • STROBE — a reporting guideline for observational studies; this paper's recommendations extend STROBE items 8 (data sources/measurement) and 12c (missing data) into more structured data-quality reporting.（中文:一套针对观察性研究的报告准则;本文的建议在STROBE第8条——数据来源/测量方法——和第12c条——缺失数据——的基础上,扩展出更结构化的数据质量报告要求。）
  • State-transition check — a data-quality check verifying that a variable follows an expected sequence over time, e.g., an inpatient-admission event should be followed only by discharge or death.（中文:一种数据质量检查,验证某个变量是否按预期顺序随时间演变,例如住院入院事件之后只应跟着出院或死亡事件。）

Methods / tools to lift

  • The "Table 1a for Data Quality Reporting" concept — a structured, STROBE-parallel checklist format for disclosing data-quality work.
  • The four-context taxonomy (data capture / data processing-provenance / data elements characterization / analysis-specific characterization) as an organizing structure for any data-quality disclosure.
  • Specific data-elements-characterization techniques named: goodness-of-fit testing against an expected distribution, state-transition checks, and co-occurrence-rule conformance checks.

Where it lands + buildable artifact

Pipeline stage: primary (d) evaluation (a structured disclosure format, not a new accuracy metric); secondary touch on (c) adjudication / review budget via its data-processing-provenance recommendations, which require disclosing outlier-removal and flag-replacement transformations — creating an audit trail useful when later judging whether a flagged value's original cleaning decision still looks defensible.

Buildable artifact — DQ Reporting Scorecard (S). One-line MVP: given a written description of an outlier-detection pipeline (candidate generator, adjudication, review process), walk through a checklist version of the 20 Kahn-style items and auto-generate a formatted markdown disclosure table (addressed / not addressed / not applicable per item).

What to verify first

  • Whether empirical evaluation of the recommendations' feasibility and cost — which the paper itself says hadn't been done at publication — was ever carried out afterward, and what it found.
  • Whether a more representative or more rigorous consensus process has since produced a revised or competing set of recommendations worth comparing against, given the original development relied on a convenience sample rather than Delphi or another formal consensus method.
  • How directly the four reporting contexts, built around multi-site distributed-network studies, map onto a single national registry's data flow, rather than assuming the fit is automatic.

Pipeline stage

(d) evaluation, primary; (c) adjudication / review budget, secondary (via data-processing-provenance disclosure requirements).

Error types covered / not covered

Not an error-detection method — it's a reporting/disclosure framework. It requires disclosing that transformations like outlier removal, unit conversion, and flag-replacement occurred, but does not itself define or detect specific error types (digit transposition, decimal shift, carry-forward, or real-clinical-event confusion).
