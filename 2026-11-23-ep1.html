A graph-based approach to variant description extraction from sequences

Santcroos MA, Kosters WA, Lefter M, Laros JFJ, Vis JK (Leiden University Medical Center / Leiden University). NAR Genomics and Bioinformatics 2025. A pure methods paper that formalizes the problem Karen's team hits constantly: the same underlying genetic change can be written down in several different, textually incompatible HGVS strings, and nobody has agreed on one algorithm for turning a reference-versus-observed sequence comparison into a single "correct" description. The authors build a compressed graph of every minimal alignment between the two sequences (the cLCS-graph), which they show is a complete representation of a variant, and pull three different kinds of description out of it: a maximal "supremal variant," a partitioned "local supremal variant" for alleles of several changes in cis, and a shortest-path "canonical variant" meant to resemble what a human curator would write by hand. Benchmarked against 102 million dbSNP entries on chromosome 1, the method agrees with dbSNP on nearly everything simple, but also exposes 10,310 cases where dbSNP quietly stores the same underlying change twice, under two different notations. Lands on Karen's variant-notation-harmonization work; the buildable artifact is a CFTR Variant-Description Reconciler built on the authors' open-source mutalyzer/algebra package.

Plain-English glossary

  • Allele description (in cis) — Reporting two or more smaller variants as sitting together on the same copy of the chromosome, rather than merging them into one large combined edit.（中文：把位于同一条染色体拷贝上的几个独立小变化分别报告出来，而不是合并成一个大的变化。）
  • Canonical variant — This paper's shortest-path extraction from the variant graph; argued to match how a human curator would typically write the HGVS description by hand.（中文：本文从变异图中按最短路径提取出的描述方式，论文认为它最接近人工手写HGVS时得到的结果。）
  • cLCS-graph (compressed LCS-graph) — A directed acyclic graph built from every minimal alignment between a reference and an observed sequence; the paper's claim is that it completely represents a variant.（中文：由参考序列与观测序列之间所有最短对齐方式构建出的有向无环图，论文认为它是对一个变异的完整表示。）
  • Delins — HGVS shorthand for "deletion-insertion": a notation for a region where some bases are deleted and others inserted in their place.（中文：HGVS中"缺失-插入"的简写，描述某区域内部分碱基被删除、同时插入其他碱基的变化。）
  • Dominator node — A graph-theory concept: a node that every path from source to sink must pass through; used here to split a combined variant into independent parts.（中文：图论概念，指从源节点到汇节点的每条路径都必须经过的节点，本文用它把一个复合变异拆分成独立的组成部分。）
  • HGVS — The Human Genome Variation Society's human-readable naming convention for variants (e.g. c.1521_1523delCTT); the Society specifies the notation but not how to algorithmically derive one from raw sequence.（中文：由Human Genome Variation Society制定的变异命名规范，规定了命名写法，但未规定如何从原始序列算出该命名。）
  • IVS8 poly-T tract — A polymorphic run of T nucleotides near CFTR intron 8 (the clinically familiar 5T/7T/9T variant) that modifies the penetrance of the R117H allele; a repeat-rich region of exactly the kind this paper's method is built to handle.（中文：CFTR内含子8附近一段多聚T的重复序列（即临床上的5T/7T/9T变异），会影响R117H等位基因的外显率；是本文方法所要处理的典型重复密集区域。）
  • Local supremal variant — A partition of the supremal variant into independent component parts, using dominator nodes; the natural description for an allele made of several separate changes in cis.（中文：利用支配节点把supremal variant再细分成独立组成部分，是描述同一染色体上多个独立变化组成的等位基因的自然方式。）
  • SNV (single nucleotide variant) — A variant affecting exactly one nucleotide position; all 91.5 million SNVs in this paper's dbSNP benchmark matched exactly between the two methods.（中文：影响单个核苷酸位置的变异；本文基准测试中全部9150万个SNV在两种方法间完全一致。）
  • SPDI — NCBI's machine-readable variant format (Sequence, Position, Deletion, Insertion), a four-field record paired with the VOCA normalization step.（中文：NCBI提出的机器可读变异格式，由序列、位置、缺失、插入四个字段组成，配套使用VOCA归约步骤。）
  • Supremal variant — The single largest replacement spanning a variant's entire graph; a compact, storage-friendly description, deliberately analogous to (but not always identical to) NCBI's VOCA-normalized SPDI.（中文：跨越整个变异图、覆盖全部变化的单一最大替换操作，是便于存储的紧凑描述，设计上类比NCBI的VOCA归约SPDI，但不总是完全相同。）
  • VOCA (Variant Overprecision Correction Algorithm) — NCBI's normalization step for SPDI, which tries to shrink a variant description to its smallest unambiguous form.（中文：NCBI对SPDI的归约算法，尝试把变异描述压缩到最小且无歧义的形式。）

Full citation

Santcroos MA, Kosters WA, Lefter M, Laros JFJ, Vis JK. "A graph-based approach to variant description extraction from sequences." NAR Genomics and Bioinformatics 2025. PMID: 41368195 | PMC12684398 | DOI: 10.1093/nargab/lqaf173

Methods / tools to lift

  • mutalyzer/algebra — open-source Python package implementing the cLCS-graph construction and all three extraction methods (supremal, local supremal, canonical); versioned and archived on Zenodo.
  • Mutalyzer normalizer — the public web tool (test.mutalyzer.nl/normalizer) this package is already wired into; usable directly for ad hoc variant checks without writing code.
  • ONP-algorithm extension — the underlying all-minimal-alignments computation; relevant if a custom implementation is ever needed rather than the shipped package.

Where it lands + buildable artifact

Lands on Karen's CFTR variant-interpretation and notation-harmonization work (method only). Buildable artifact: CFTR Variant-Description Reconciler (M) — run the full set of CFTR variant descriptions from CFTR2, ClinVar, and gnomAD through mutalyzer/algebra's supremal and canonical extraction to flag (a) textually different descriptions across sources that resolve to the identical change, and (b) single delins entries that decompose into multiple independent component variants — the same 10,310-variant pattern the paper found in dbSNP. Needs a transcript-mapping step added, since CFTR curation runs at the coding (c.) level and this paper's method is genomic (g.)-level only.

What to verify first

  • The paper's benchmark "ground truth" is dbSNP's own stored HGVS, which the paper itself shows is sometimes uninterpretable or internally inconsistent — a disagreement with dbSNP needs independent spot-checking (e.g. against VariantValidator) before being read as a database error.
  • The genomic-to-transcript mapping is unvalidated in this paper and would need its own correctness check, especially near splice boundaries where CFTR's clinically important variants cluster.
  • Repeat-region handling (mononucleotide and mixed repeats) is explicitly incomplete per the authors; CFTR's own IVS8 poly-T tract is a repeat region, so this is a near-term risk, not a hypothetical one.
  • No claim is made, and none should be assumed, about how CFFPR itself currently stores or has already resolved CFTR variant notations.

ALEX Today it's a methods paper out of Leiden University Medical Center — Santcroos, Kosters, Lefter, Laros, and Vis, published this year in NAR Genomics and Bioinformatics, "A graph-based approach to variant description extraction from sequences." 今天我们聊的是一篇来自荷兰莱顿大学医学中心（Leiden University Medical Center）的方法学论文——作者是Santcroos、Kosters、Lefter、Laros和Vis，今年发表在《NAR Genomics and Bioinformatics》上，题为《从序列中提取变异描述的图方法》（A graph-based approach to variant description extraction from sequences）。

JORDAN A paper with no clinical cases and not a single disease gene in it — why does this belong on the Karen track? 这篇论文里没有一个临床病例，连一个疾病基因都没提到——为什么它会被放进服务Karen工作的那条线？

ALEX Because half of Karen's actual job is reconciling four different notations for what turns out to be the same CFTR variant, and this paper is a formal, implementable answer to exactly that problem — it's pure Track A, variant-notation harmonization, no biology required. 因为Karen实际工作的一半，就是去判断四种不同写法说的其实是同一个CFTR变异，而这篇论文正是给这个问题提供了一个正式、可落地实现的答案——这是纯粹的A线任务，变异命名协调（variant-notation harmonization），完全不需要涉及生物学。

JORDAN So today's buildable artifact is going to be about cleaning up variant descriptions, not calling pathogenicity? 所以今天的可动手项目是关于清理变异描述，而不是判断致病性？

ALEX Exactly — think of it as plumbing work that everything downstream, including pathogenicity calls, depends on getting right. 没错——可以把它想象成管道工程，下游的一切，包括致病性判断，都依赖于这一步做对。

JORDAN Let's get the vocabulary straight before we go further. What's HGVS, concretely? 在继续往下讲之前，先把术语理清楚。HGVS具体是什么？

ALEX HGVS is the Human Genome Variation Society's naming convention for variants — things like c.1521_1523delCTT for the common CFTR deletion, or a genomic coordinate like g.117559590_117559592del on the reference sequence; it's meant to be human-readable, but the Society never specified an algorithm for generating one from raw sequence. HGVS（变异命名的标准化书写规范，由Human Genome Variation Society制定）是对变异的一套命名约定——比如常见CFTR缺失变异写成c.1521_1523delCTT，或者在参考序列上用g.117559590_117559592del这样的基因组坐标表示；它的设计目标是让人能读懂，但该学会从未规定过该如何从原始序列算出这样一个命名。

JORDAN And SPDI? 那SPDI呢？

ALEX SPDI is NCBI's machine-readable alternative — Sequence, Position, Deletion, Insertion — a four-field record instead of a notation string, paired with its own normalization step called VOCA, the Variant Overprecision Correction Algorithm, which tries to shrink a variant description down to its smallest unambiguous form. SPDI（NCBI提出的机器可读替代方案，即序列-位置-缺失-插入四个字段组成的记录，而不是一串命名文本）还搭配了自己的归约步骤，叫VOCA（变异过度精确校正算法，Variant Overprecision Correction Algorithm），它会尝试把一个变异描述压缩到最小的、不含糊的形式。

JORDAN Why would the same variant end up with different descriptions at all? Isn't a deletion just a deletion? 同一个变异怎么会出现不同的描述呢？删除不就是删除吗？

ALEX Not when the surrounding sequence has repeats — delete one base from a run of ten identical bases and there are ten equally valid positions to say the deletion happened, and different tools and databases pick different ones by convention, not because any one is more "correct." 如果周围序列是重复序列，情况就不一样了——从十个相同碱基连续排列的区域里删掉一个碱基，有十个位置都同样"正确"，说删除发生在哪里都说得通，而不同工具和数据库只是按各自的约定选了不同的位置，并不是哪个更"对"。

JORDAN Is that actually a real problem, or mostly cosmetic? 这真的是个实际问题，还是只是表面上好看不好看的事？

ALEX It's real — the paper cites earlier work showing that searching PubMed for one textual description of a variant can fail to retrieve papers reporting the exact same variant under a different notation, and a separate clinical study found notation drift can, quote, "hide clinically relevant information in plain sight." 是真实存在的问题——论文引用了早期研究，显示用一种文本描述在PubMed上搜索某个变异，可能检索不到用另一种命名报告了同一个变异的论文；另有一项临床研究发现，命名漂移甚至可能——原话是——"把具有临床意义的信息明摆在眼前却被掩藏起来"。

JORDAN One more term — "delins" and "allele" as they use them here. 再来一个术语——论文里用的"delins"和"allele"分别是什么意思。

ALEX Delins is shorthand for "deletion-insertion," HGVS's way of describing a region where some bases are deleted and others inserted in their place; an allele description, in this context, means reporting several separate smaller changes that sit on the same copy of the chromosome — what geneticists call "in cis" — instead of lumping them into one big delins block. delins是"缺失-插入"（deletion-insertion）的简写，是HGVS用来描述某个区域里一部分碱基被删除、同时另一部分碱基被插入进去的写法；而这里说的allele（等位）描述，指的是把位于同一条染色体拷贝上的几个独立的小变化分别报告出来——遗传学上称之为"同源（in cis）"——而不是把它们合并成一个大的delins区块。

JORDAN So what's actually broken today, mechanically? 那现在具体是哪个环节出了问题？

ALEX Two things. First, nobody had a principled, implementable way to go from "here is a reference sequence and here is the observed sequence" straight to a correct HGVS string — existing tools pick one alignment path more or less by convention and run with it. Second, the field had no single data structure that captured a variant completely enough to derive every legitimate description from it, so tools built on different assumptions kept disagreeing. 两个问题。第一，此前没有人有一个有原则、可实现的方法，能从"这是参考序列，这是观测到的序列"直接算出一个正确的HGVS字符串——现有工具基本上是按惯例选一条对齐路径，然后就照着跑了。第二，这个领域此前没有一种数据结构，能完整到足以从中推导出所有合法的描述方式，所以建立在不同假设上的工具之间总是互相矛盾。

JORDAN Is there a canonical "right" description everyone's supposed to converge on? 有没有一个大家都该趋同的、规范意义上"正确"的描述？

ALEX In principle HGVS says yes, but the authors point out the recommendations are silent on how to construct a description from sequence in the first place, and even dbSNP — NCBI's own authoritative variant database — stores millions of entries internally inconsistent with its own stated conventions, which is precisely the benchmark this paper uses to prove its point. 理论上HGVS的回答是"有"，但作者指出，HGVS的建议文件对于究竟该如何从序列构造出一个描述这件事完全没有说明；甚至连dbSNP——NCBI自己最权威的变异数据库——里都存着数以百万计、与其自身规定不一致的条目，而这正是这篇论文用来证明自己观点的基准数据集。

JORDAN Why does this matter specifically for something like CFTR, where the clinical community has had decades to standardize? 为什么这件事对CFTR这样一个临床界已经有几十年时间去做标准化的基因来说依然重要？

ALEX Two reasons. CFTR curation draws on ClinVar, CFTR2, gnomAD, and lab-specific systems that each ingested variant calls from different pipeline eras, and some of CFTR's best-known regions — the polymorphic T-tract near intron 8, the one clinicians call the 5T/7T/9T or IVS8 poly-T variant that modifies penetrance of the R117H allele — sit inside exactly the kind of repeat-rich sequence this paper is built to handle, where naive notation choices diverge the most. 有两个原因。CFTR的变异整理工作要同时参考ClinVar、CFTR2、gnomAD，以及各实验室自己的系统，这些系统录入变异结果的时间跨越了不同的分析流程时代；而CFTR最知名的几个区域之一——内含子8（intron 8）附近的多聚T区（poly-T tract），也就是临床上说的5T/7T/9T，或IVS8多聚T变异，它会影响R117H等位基因的外显率（penetrance）——恰好就位于这篇论文所要处理的那种富含重复序列的区域里，而正是在这类区域，简单直接的命名选择最容易产生分歧。

JORDAN So this isn't abstract computer science, it's the kind of mess that actually shows up in CFTR's own messiest locus. 所以这不是抽象的计算机科学问题，而是实实在在会出现在CFTR自身最棘手的那个位点上的混乱。

ALEX Right — the repeat-heavy regions are where the disagreement concentrates, and that's not a coincidence, it's the mathematical structure of the problem. 没错——分歧恰恰集中在重复序列密集的区域，这不是巧合，而是这个问题本身的数学结构决定的。

JORDAN Walk me through what they actually built. 具体说说他们到底构建了什么。

ALEX They start from the simple edit distance between a reference string and an observed string, but instead of computing just one alignment, they compute all of the alignments tied for minimal length, using an extension of a classic algorithm called ONP; from those, they build a directed acyclic graph where nodes are matching stretches of sequence and edges are the minimal edits connecting them, which they call the compressed LCS-graph, or cLCS-graph. 他们从参考字符串和观测字符串之间的简单编辑距离出发，但不只计算一条对齐路径，而是用一种经典算法ONP（一种计算最短编辑距离的经典算法）的扩展版本，把所有并列最短的对齐方式全部计算出来；基于这些结果，他们构建出一个有向无环图，节点代表序列中匹配的片段，边代表连接这些片段的最小编辑操作，他们称之为压缩LCS图，即cLCS-graph（compressed LCS-graph）。

JORDAN And the claim is that graph is a "complete" representation of the variant? 他们的说法是，这个图就是该变异的一个"完整"表示？

ALEX Yes — every path from the graph's single source node to its single sink node is a valid, minimal description of the same underlying change, so instead of picking one description and hoping it's the useful one, you get the entire solution space explicitly, and three different extraction methods pull three different kinds of answer out of it. 是的——从图里唯一的源节点到唯一的汇节点的每一条路径，都是对同一个底层变化的一个有效、最简的描述，所以你不再是选一个描述然后寄希望于它够用，而是显式地拿到整个解空间，再用三种不同的提取方法，从里面取出三种不同类型的答案。

JORDAN What are the three? 这三种方法分别是什么？

ALEX The supremal variant is the single largest all-encompassing replacement spanning the whole graph — good for storage and for comparing two variants algebraically, deliberately analogous to NCBI's own VOCA-normalized SPDI, though the paper shows it's often not identical. supremal variant（可以理解为"覆盖全局的单一替换"）是跨越整个图、覆盖所有变化的一个单一、最大的替换操作——适合用来存储，也适合用代数方式比较两个变异，其设计上有意类比NCBI自己经过VOCA归约的SPDI，不过论文显示两者往往并不完全相同。 The local supremal variant partitions that same region using graph theory's notion of "dominator" nodes — points every path must pass through — which naturally splits a messy combined change into its independent component parts, useful exactly when a variant is really an allele of several separate changes in cis. local supremal variant（局部的覆盖性替换）则用图论中"支配节点"（dominator，即每条路径都必须经过的节点）的概念，把同一个区域再细分开，这样就能自然地把一个混杂在一起的复合变化拆分成互相独立的组成部分，这正好适用于一个变异其实是同一条染色体上（in cis）几个独立变化组成的等位基因（allele）的情况。 And the canonical variant takes the shortest path through the graph, which the paper argues corresponds most closely to how a human would actually write the HGVS description by hand. 而canonical variant（规范变异）走的是图中的最短路径，论文认为这最接近人工手写HGVS描述时实际会得出的结果。

JORDAN Where's the pushback here — what would you challenge in this design? 你会在这个设计里质疑什么地方？

ALEX The whole method works at the genomic-sequence level and is explicitly blind to gene structure — it has no concept of exons and introns, so two genomic-level descriptions it treats as equivalent can land on completely different sides of a splice boundary and have completely different effects on the transcript; the authors admit this outright and flag it as future work, but it means you can't hand this tool a CFTR coding-level question without bolting on a separate, unvalidated transcript-mapping step first. 整个方法都是在基因组序列层面运作的，而且明确地不考虑基因结构——它没有外显子（exon）和内含子（intron）的概念，所以两个它认为等价的基因组层面描述，完全可能落在剪接边界的两侧，对转录本（transcript）产生完全不同的影响；作者自己也坦率承认了这一点，并把它列为未来工作，但这意味着你不能直接拿这个工具去处理CFTR编码层面（c.层面）的问题，除非先接上一个另外、尚未经过验证的转录本映射步骤。

JORDAN Is the code actually usable, or is this theory-only? 这个代码真的能用，还是只是理论上的东西？

ALEX It's real and shipped — a Python package called mutalyzer/algebra, versioned and archived on Zenodo, already wired into the public Mutalyzer normalizer web tool that a lot of clinical variant curators already use. 是真实可用、已经发布的——一个叫mutalyzer/algebra的Python包，带版本号并在Zenodo上存档，而且已经接入了公开的Mutalyzer归约化网页工具，很多临床变异整理人员本来就在用它。

JORDAN What did they actually test it against? 他们实际拿什么来测试这个方法？

ALEX Every variant on chromosome 1 of GRCh38 in dbSNP build 156 — roughly 102 million entries — comparing the HGVS description dbSNP stores against the HGVS description their method derives from dbSNP's own SPDI representation of the same variant. GRCh38参考基因组1号染色体上dbSNP build 156里的所有变异——大约1.02亿条记录——把dbSNP存储的HGVS描述，和他们的方法根据dbSNP自己对同一变异的SPDI表示所推导出的HGVS描述进行比较。

JORDAN And the headline numbers? 最核心的数字是什么？

ALEX 98,144,148 identical descriptions out of roughly 102 million — all 91,487,743 SNVs matched exactly, plus about 6.66 million of the 10.57 million non-SNV entries. They skipped 18,555 dbSNP entries because the stored HGVS was itself uninterpretable, and another 668 with ambiguous nucleotide symbols. 大约1.02亿条里有98,144,148条描述完全一致——全部91,487,743个SNV（单核苷酸变异，single nucleotide variant）都精确匹配，另外在1057万3738个非SNV条目里，约有666万条也一致。他们跳过了18,555条dbSNP条目，因为这些条目本身存储的HGVS就无法解析，还另外跳过668条含有不确定核苷酸符号的条目。

JORDAN What about the roughly 3.9 million that disagreed? 那剩下约390万条不一致的呢？
