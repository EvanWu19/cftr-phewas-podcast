Show notes — Track B (AI for registry/bioinformatics, tool-development lens)

Blurb. Rieder et al. (JAMIA Open, 2026) extend the OMOP Common Data Model to cover extracorporeal life support (ECLS/ECMO), and the paper is really a reusable case study in how to extend a standardized data model when the standard has no concepts for your domain. They quantify the gap with a landscape analysis: only 19/75 (25%) of ELSO Maastricht Treaty concepts and a similar shortfall in the 438-concept Registry document map cleanly to OHDSI Standardized Vocabularies. Rather than shoehorn ECLS circuit data into generic tables linked by fact_relationship, they build a governed extension — the ECLS CDM (custom PostgreSQL core/support tables) — and contribute 142 new concepts upstream into the official OMOP Extension vocabulary. The payoff: up to 90% fewer database entries to store ECLS use cases, and a clean end-to-end demo mapping 110/175 columns of a 326-run WashU dataset. Ships code (GitHub, CC0-1.0). Where it lands: AI-tooling / career plus a Liz data-quality side — a concept-gap auditor that scores how much of a domain's required data maps onto a target vocabulary and stubs an extension for the rest.

Plain-English glossary.

  • ECLS / ECMO — extracorporeal life support; a machine circuit that takes over gas exchange or circulation, pumping blood out of the body, oxygenating it, and returning it.（中文：ECLS/ECMO——体外生命支持/体外膜氧合，用机器回路接管气体交换或循环，把血液泵出体外加氧再送回。）
  • ELSO Maastricht Treaty / Registry Data Definitions — the authoritative documents defining ECLS clinical terminology and required data elements.（中文：ELSO 马斯特里赫特公约/登记库数据定义——定义 ECLS 临床术语和必填数据元素的权威文档。）
  • Federated analysis — running shared analysis code at each site so patient data never leaves; only code and aggregate results move.（中文：联邦式分析——在每个站点运行共享分析代码，病人数据从不外流，只有代码和聚合结果流动。）
  • OHDSI Standardized Vocabularies / Athena — the controlled concept lists (drawn from SNOMED CT, LOINC, etc.) every coded value maps onto; Athena is the browser for them.（中文：OHDSI 标准化词表/Athena——每个编码值都要映射到的受控概念清单（取自 SNOMED CT、LOINC 等）；Athena 是它们的浏览器。）
  • OMOP CDM — Observational Medical Outcomes Partnership Common Data Model; a standard database schema institutions map clinical data into so the same analysis runs across sites.（中文：OMOP CDM——观察性医疗结果合作通用数据模型，机构把临床数据映射进去的标准结构，让同一分析能跨站点运行。）
  • post-coordination — expressing a concept by logically combining existing concepts instead of using one equivalent concept.（中文：后组配——用已有概念的逻辑组合来表达一个含义，而不是用单一等价概念。）
  • fact_relationship — an OMOP table used to link facts that otherwise live in separate tables; heavy reliance on it is a sign the schema doesn't natively represent your object.（中文：fact_relationship——OMOP 里用来连接分散在不同表中事实的表；过度依赖它说明结构没有原生地表示你的对象。）

Full citation. Rieder C, et al. Expanding the OMOP common data model to support extracorporeal life support research. JAMIA Open. 2026. PMID 42339164; PMC PMC13284988; DOI 10.1093/jamiaopen/ooag112.

Methods / tools to lift.

  • Concept-gap landscape analysis — cross-reference every required domain concept against OHDSI vocabularies via Athena/SNOMED/LOINC and bucket as directly-mappable / post-coordinatable / needs-new-concept, with counts.
  • Governed CDM extension — custom core/support tables with proper primary keys and minimal nullable columns, preserving object-and-configuration together to keep timelines intact.
  • Upstream concept contribution — submit missing concepts into the official OMOP Extension vocabulary with SNOMED-style naming and is-a hierarchy links, instead of private one-off codes.
  • Exclude recomputable derived values — keep the model clean by not storing values calculable from other columns.

Where it lands + buildable artifact (tool sketch). Serves AI-tooling / career (+ Liz data-quality method). Paste-ready MVP: concept-gap-auditor (M) — input a domain data-definition document (flat list of fields/concepts); the tool queries the OHDSI Athena vocabulary API per term, emits a coverage report (directly-mappable / post-coordinatable / needs-new-concept), and stubs an extension-table schema for the leftovers. For CF, point it at sweat chloride, modulator start/stop events, and CF-specific microbiology to surface which need custom concepts.

What to verify first.

  • Vocabulary version drift: OHDSI ships new concepts each release, so pin the vocabulary version and re-run after each release; the audit is a snapshot.
  • Mapped ≠ faithful: a term can map to a standard concept yet lose the distinction you need (their decannulation example) — human-review the mapped bucket, not just the gaps.
  • Avoid duplicate concepts: before creating a new concept, confirm it doesn't already exist under another name; upstream contribution + naming discipline prevents interoperability drift.
  • Scope of claims: method and public-tooling only — no assumptions about registry internals.

ALEX This is the Track B tooling slot, and today we're reading "Expanding the OMOP common data model to support extracorporeal life support research," by Christian Rieder and colleagues, in JAMIA Open, 2026. 这是 Track B 的工具环节，今天我们读的是 Christian Rieder 及同事的《扩展 OMOP 通用数据模型以支持体外生命支持研究》，2026 年发表在 JAMIA Open 上。It ships code — the whole extension is on GitHub under a CC0 public-domain license — which is exactly what this track wants. 它带代码——整个扩展都在 GitHub 上，采用 CC0 公共领域许可——这正是这个 track 想要的东西。And under the ECMO-specific surface, it's really a case study in how to extend a standardized data model when the standard doesn't have concepts for your domain. 而在它体外膜氧合这层专门的表皮之下，它其实是一个案例研究：当标准里没有你所在领域的概念时，该怎么去扩展一个标准化数据模型。

JORDAN Give me the two pieces of jargon first. 先给我讲两个术语。What is OMOP, and what is extracorporeal life support? 什么是 OMOP，什么是体外生命支持？

ALEX OMOP is the Observational Medical Outcomes Partnership Common Data Model — a standard database schema that many institutions map their clinical data into, so that the same analysis code runs unchanged across hospitals without patient data ever leaving each site. OMOP（观察性医疗结果合作通用数据模型，指许多机构把各自临床数据映射进去的一套标准数据库结构，好让同一份分析代码不加改动就能在多家医院上运行，而病人数据从不离开各自的站点）。It's governed by the OHDSI community, which also maintains the Standardized Vocabularies — the controlled lists of concepts, drawn from terminologies like SNOMED CT and LOINC, that every coded value has to map onto. 它由 OHDSI 社区管理，该社区还维护"标准化词表"——一批受控的概念清单，取自 SNOMED CT、LOINC 这类术语体系，每一个编码值都必须映射到它们上面。Extracorporeal life support, ECLS — the best-known form is ECMO — is when a machine circuit takes over gas exchange or circulation for a critically ill patient, pumping blood out of the body, oxygenating it, and returning it. 体外生命支持，简称 ECLS，最有名的形式是 ECMO（体外膜氧合），指用一套机器回路替危重病人接管气体交换或循环，把血液泵出体外、加氧、再送回来。

JORDAN Why does this matter beyond ECMO specifically — what's the bigger motivation? 这件事在 ECMO 本身之外为什么重要——更大的动机是什么？

ALEX The motivation is that ECLS data today is mostly collected by hand into administrative and clinical registries, and manual collection is a hard ceiling. 动机在于，如今的 ECLS 数据大多是人工采集进行政和临床登记库的，而人工采集是一道很硬的天花板。When a human is transcribing, you limit how many data elements you include, and you basically cannot capture repeated, high-resolution measurements — the flow readings, pressures, and settings that change minute to minute on a circuit. 当靠人转录时，你会限制纳入多少数据元素，而且你基本上没法捕获重复的、高分辨率的测量——回路上那些分分钟都在变的流量读数、压力和设置。A common data model like OMOP is built for the opposite: longitudinal, machine-ingested data, and it supports federated analysis, where each site keeps its patient data and only shared code and aggregate results move. 而像 OMOP 这样的通用数据模型是为相反的情形建的：纵向的、机器摄入的数据，而且它支持联邦式分析，也就是每个站点自己保留病人数据，只有共享的代码和聚合结果在流动。So the prize isn't tidiness for its own sake — it's enabling multi-center ECLS research and quality measurement that manual registries can't reach. 所以奖品不是为了整洁而整洁——而是要让手工登记库够不着的多中心 ECLS 研究和质量测量成为可能。

JORDAN And why doesn't OMOP already handle that? 那 OMOP 为什么本来处理不了这个？

ALEX Because OMOP was built around patients, visits, diagnoses, drugs, and measurements — the shape of ordinary clinical records. 因为 OMOP 是围绕病人、就诊、诊断、用药和测量来建的——是普通临床记录的形态。An ECLS circuit is a different kind of object: it has cannulas with insertion sites, laterality, sizes, flow directions, tip positions, and configurations that change over time, sometimes with multiple circuits running at once. 而一个 ECLS 回路是另一类对象：它有插管，有插入部位、左右侧、尺寸、血流方向、尖端位置，还有会随时间变化的配置，有时还多个回路同时运转。To store one circuit component in stock OMOP, you have to spread its attributes across several tables and stitch them back together through a table called fact_relationship. 要在原生 OMOP 里存一个回路组件，你得把它的属性摊到好几张表里，再通过一张叫 fact_relationship 的表把它们重新缝起来。That makes the SQL to answer even a simple ECLS question enormously complicated. 这就让回答哪怕一个简单的 ECLS 问题的 SQL 变得极其复杂。

JORDAN So how did they actually assess the gap instead of just asserting it? 那他们是怎么真去评估这个缺口，而不是光嘴上说的？

ALEX They did a landscape analysis, and this is the part worth stealing. 他们做了一次全景分析，而这正是值得偷师的部分。They took the authoritative definitions of ECLS data — the ELSO Maastricht Treaty and the ELSO Registry Data Definitions Document — and cross-referenced every concept against the OHDSI Standardized Vocabularies using Athena, the OHDSI concept browser, plus the SNOMED CT and LOINC browsers. 他们拿来 ECLS 数据的权威定义——ELSO 马斯特里赫特公约和 ELSO 登记库数据定义文档——把里面每一个概念都用 Athena（OHDSI 的概念浏览器）以及 SNOMED CT 和 LOINC 浏览器，逐一对照标准化词表。Of the 75 concepts in the Maastricht Treaty, only 19, that's 25 percent, mapped directly to existing standard concepts. 马斯特里赫特公约的 75 个概念里，只有 19 个，也就是 25%，能直接映射到已有的标准概念。One more could be handled by post-coordination, combining concepts logically, and 55, that's 74 percent, could not be matched without losing semantic fidelity. 还有一个可以用后组配 (post-coordination，指把多个概念逻辑地组合起来表达一个含义)处理，而 55 个，也就是 74%，在不损失语义保真度的情况下根本没法匹配。For the larger Registry Definitions document, 438 concepts, 51 of them, 12 percent, needed brand-new concepts created. 对更大的登记库定义文档里的 438 个概念，其中 51 个，占 12%，需要创建全新的概念。

JORDAN That coverage audit is quantitative and reproducible. 这个覆盖度审计是定量而且可复现的。What did they build once they knew the gap? 知道缺口之后，他们建了什么？

ALEX A governed extension, not a hack. 一个受治理的扩展，而不是一个临时凑合。They designed a custom OMOP expansion, the ECLS Common Data Model, with its own PostgreSQL tables split into core and support tables, following database best practices — proper primary keys, minimal nullable columns. 他们设计了一个定制的 OMOP 扩展，叫 ECLS 通用数据模型，有它自己的 PostgreSQL 表，分成核心表和支持表，遵循数据库最佳实践——恰当的主键、尽量少的可空列。And crucially, they didn't just invent private codes — they contributed the missing concepts upstream. 而关键在于，他们没有只是自造一批私有编码——他们把缺失的概念贡献到了上游。134 new ECLS-specific concepts went into the official OMOP February 2024 vocabulary release, and 8 more in August 2024, integrated into the existing hierarchy through is-a relationships, released as part of the OMOP Extension vocabulary. 134 个新的 ECLS 专用概念进入了官方 OMOP 2024 年 2 月的词表发布，还有 8 个进入了 8 月的发布，通过"是一种" (is-a) 关系整合进已有的层级结构，作为 OMOP Extension 词表的一部分发布。The reported win: the number of database entries needed to store the ECLS use cases dropped by up to 90 percent versus the fact_relationship approach. 报告出来的收益是：相比 fact_relationship 那套做法，存储 ECLS 用例所需的数据库条目数量下降了最多 90%。

ALEX Then they demonstrated it end to end. 然后他们做了端到端的演示。They mapped a deidentified dataset of 326 ECLS runs over six years from Washington University in St. Louis — 175 fields across nine tables — into the model. 他们把一个来自圣路易斯华盛顿大学的去标识化数据集映射进了模型——六年里 326 次 ECLS 运行，9 张表里的 175 个字段。110 of the 175 columns mapped cleanly; 65 were excluded, and they were honest about why: missing semantic context, missing timestamps, duplicative information, or values that were just calculated from other columns. 175 列里有 110 列干净地映射了进来；65 列被排除，而且他们坦白了原因：缺少语义环境、缺少时间戳、信息重复，或者只是从其他列算出来的值。That last category — excluding derived values you can recompute — is a small discipline that keeps a data model clean. 最后那一类——把可以重新算出来的派生值排除掉——是一个能让数据模型保持干净的小小纪律。

JORDAN You said the extension preserves temporal relationships. 你说这个扩展保留了时间关系。Why is that the crux for ECLS? 为什么这对 ECLS 是关键？

ALEX Because an ECLS course is a sequence of configurations, not a single static fact. 因为一次 ECLS 疗程是一连串的配置，而不是单个静态的事实。A patient might start on one cannulation setup, then a cannula gets added, then the configuration switches — and the clinical meaning of any measurement depends on which configuration was live at that moment. 一个病人可能一开始是一种插管配置，然后加了一根插管，接着配置又切换了——而任何一个测量的临床含义，都取决于那一刻是哪种配置在运行。In stock OMOP, once you shatter a component across tables and rejoin through fact_relationship, you can lose or blur which attributes belonged to which configuration at which time. 在原生 OMOP 里，一旦你把一个组件打碎到多张表里、再通过 fact_relationship 重新连接，你就可能丢失或模糊掉哪些属性在哪个时间属于哪个配置。The custom tables keep a component and its configuration together as first-class objects, so the timeline stays intact by construction. 而定制的表把一个组件和它的配置作为头等对象放在一起，于是时间线在设计上就保持了完整。That's the difference between being able to ask "what was the flow while the patient was on VA configuration" and not being able to ask it at all. 这就是"能问出'病人处于 VA 配置时流量是多少'"和"根本问不出来"之间的区别。

JORDAN There's an OMOP philosophy underneath this — bring the analysis to the data instead of exporting the data. 这底下有一套 OMOP 的哲学——把分析带到数据面前，而不是把数据导出去。Is that what's really being protected? 这才是真正被保护的东西吗？

ALEX Exactly, and it's why the schema choice isn't cosmetic. 正是，这也是为什么结构的选择不是表面功夫。Federated analysis only works if every site's data means the same thing when the shared code runs against it, so semantic fidelity at the model layer is what makes "never move the patient data" actually deliver comparable results. 联邦式分析只有在每个站点的数据在共享代码跑过来时含义相同的前提下才成立，所以模型层的语义保真度，才是让"绝不搬动病人数据"真正产出可比结果的东西。If the model quietly flattens distinctions — a routine versus an accidental decannulation — then two sites can run identical code and still be measuring different things. 如果模型悄悄把区别抹平了——常规拔管和意外脱管——那么两个站点跑一模一样的代码，测的却仍然是不同的东西。So extending the vocabulary faithfully is upstream of every downstream federated claim. 所以忠实地扩展词表，是每一个下游联邦式结论的上游前提。

JORDAN One number jumped out — of the concepts they touched, how many were actually required fields? 有个数字很扎眼——在他们处理的概念里，到底有多少是必填字段？

ALEX That's the detail that tells you this wasn't a fringe exercise. 这个细节正好告诉你，这不是一次边缘性的练习。Of the 51 newly created concepts, 21 were mandatory data elements in the ELSO definitions, and another 108 mandatory elements sat in the group they could already cover. 在新创建的 51 个概念里，有 21 个是 ELSO 定义中的必填数据元素，另有 108 个必填元素落在他们本已能覆盖的那一组里。So the gaps weren't obscure edge cases — they included fields you're required to record for every ECLS run. 所以这些缺口并不是些晦涩的边角情形——它们包含了你对每一次 ECLS 运行都被要求记录的字段。That's the argument for why a generic vocabulary genuinely failed the domain, rather than just being inconvenient. 这就是"为什么一个通用词表在这个领域是真的失效了、而不只是不方便"的论据。

JORDAN Let me push on the design, because Track B is supposed to be critical. 我来对这个设计发问，因为 Track B 就应该带批判性。What's the cost of going custom like this? 走这种定制路线，代价是什么？

ALEX Good, because the authors name the costs themselves. 好，因为作者自己就点了这些代价。First, the extension is only partially compatible with the standard OHDSI analytic tools — the Hades packages and the Atlas cohort builder — so by leaving the stock schema you give up some of the ecosystem that made OMOP attractive in the first place. 第一，这个扩展只与标准的 OHDSI 分析工具部分兼容——Hades 工具包和 Atlas 队列构建器——所以一旦离开原生结构，你就放弃了一部分当初让 OMOP 有吸引力的生态。Second, the ECLS CDM adds real complexity and requires manual user input, which they admit could slow adoption. 第二，ECLS CDM 增加了实实在在的复杂度，还需要手动的用户输入，他们承认这可能拖慢采纳。Third, it was built primarily around the ELSO Registry as the gold standard, and things like trauma, cardiac, or ECPR addenda weren't in this first release, and other EHR and registry formats may not generalize. 第三，它主要是围绕作为金标准的 ELSO 登记库来建的，创伤、心脏或 ECPR 附录这些东西在第一版里还没有，而其他电子病历 (EHR) 和登记库格式可能不容易推广。So the honest framing is: they traded ecosystem breadth and simplicity for semantic fidelity and query sanity in one specialized domain. 所以诚实的说法是：他们用生态的广度和简洁，换来了在一个专门领域里的语义保真度和查询上的清爽。

JORDAN That trade-off sounds familiar for any registry with domain-specific data the generic vocabulary doesn't cover. 这个取舍对任何有着通用词表覆盖不到的领域专属数据的登记库来说，都很耳熟。Where does this land for us? 那它落到我们身上是哪里？

ALEX It lands squarely on the AI-tooling and career lane, with a side that touches the Liz data-quality method work. 它正好落在 AI 工具与职业发展这条线上，还有一侧触及了 Liz 那边的数据质量方法工作。The transferable move is the concept-gap audit — before you build any harmonization layer, you systematically score how much of your domain's required data actually maps onto a target vocabulary, and where the holes are. 可迁移的动作是"概念缺口审计"——在你搭建任何协调层之前，你系统地评估你所在领域所需的数据里，究竟有多少能真正映射到目标词表上，以及漏洞在哪里。So the buildable artifact — and I'll land the beat on it — is a concept-gap auditor. 所以可动手做的东西——我就把这段收在它上面——是一个"概念缺口审计器"。The MVP: feed it a domain data-definition document, a flat list of the fields and concepts your specialty actually records; it queries the OHDSI Athena vocabulary API for each term and emits a coverage report bucketing every concept as directly-mappable, post-coordinatable, or needs-a-new-concept, and then stubs out an extension-table schema for the leftovers.
