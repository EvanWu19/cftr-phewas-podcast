Why Non-ASCII Unicode Characters Should Not Be Used in the HGVS Nomenclature

A short, sharp correspondence piece in the Journal of Molecular Diagnostics (2026) from five authors who sit at the center of variant-nomenclature governance — Raymond Dalgleish and Ivo Fokkema from the HGVS nomenclature committee, Elspeth Bruford from HGNC — rebutting a separate paper that proposed swapping four characters central to HGVS variant notation (:, /, >, *) for visually similar Unicode lookalikes, in order to make HGVS-compliant strings legal as file and folder names on Windows, Linux, and macOS. The authors argue the fix is worse than the problem: every downstream system that matches variant descriptions — ClinVar, CFTR2, gnomAD, a lab's own pipeline — does so by text-string comparison, and Unicode substitutions break that silently, render inconsistently across fonts (the original paper's own replacement characters displayed as blank boxes in Firefox on Linux), and are detectable by essentially one tool (the LOVD HGVS library, underlying VariantValidator). The buildable idea: a small, defensive scanner that walks every CFTR variant description your project touches and flags any character outside HGVS's strict ASCII range before it silently breaks a string match. It lands on Karen's variant-interpretation and notation-harmonization track as a cheap insurance policy sitting alongside the planned CFTR HGVS harmonization pass.

Plain-English glossary

  • Code point — a single numbered entry in the Unicode standard; two characters can look identical on screen while being different code points under the hood.（中文:Unicode标准里的一个编号条目;两个字符在屏幕上看起来一样,底层编码的码点却可能完全不同。）
  • Confusables table — a list Unicode itself publishes of code points that render as visually near-identical to another code point, used for security/anti-spoofing checks.（中文:Unicode组织自己发布的一份列表,列出哪些码点在视觉上和另一个码点几乎一样,用于安全和防伪检查。）
  • HGVS nomenclature — the Human Genome Variation Society's standardized text format for describing a genetic variant, e.g. NM_000088.4:c.589G>T.（中文:人类基因组变异学会制定的、用于描述基因变异的标准化文本格式。）
  • Homoglyph — a character from one script (e.g. Cyrillic) that looks nearly identical to a character from another script (e.g. Latin) but is a distinct code point.（中文:来自一种文字体系的字符,看起来和另一种文字体系的字符几乎一样,但其实是不同的码点。）
  • LOVD — Leiden Open Variation Database, a widely used variant database platform whose HGVS parsing library is, per this letter, the only validator that detects and auto-corrects Unicode substitutions back to ASCII.（中文:莱顿开放变异数据库平台,据本文所述,其HGVS解析库是唯一能检测并自动把Unicode替代字符纠正回ASCII的校验工具。）
  • NFKC (Unicode normalization form) — a standard text-normalization process that folds certain "compatibility" characters (e.g. some fullwidth punctuation) back to their plain-ASCII equivalent, but does not touch true cross-script homoglyphs with no decomposition mapping.（中文:一种标准的文本归一化流程,能把某些"兼容性"字符折叠回纯ASCII形式,但无法处理没有分解映射关系的跨文字体系同形异义字符。）
  • VariantValidator — a widely used interactive tool for validating, mapping, and formatting HGVS variant descriptions, which incorporates the LOVD HGVS library under the hood.（中文:一个广泛使用的交互式工具,用于校验、映射和格式化HGVS变异描述,底层内置了LOVD的HGVS解析库。）

Methods / tools to lift

  • VariantValidator — interactive HGVS validation/mapping tool; already demonstrates the correct pattern of filename-safe character substitution without touching the underlying variant string.
  • LOVD HGVS library — the parsing engine behind the LOVD database platform; the only tool named here that specifically detects and reverses Unicode substitutions in HGVS strings.
  • Unicode confusables table — Unicode Consortium's own published list of visually-confusable code-point pairs, useful as a lookup layer for any defensive scanner.

What to verify first

  • Whether any Unicode lookalike characters have actually turned up in CFTR2, ClinVar, or VCF-annotation exports this project draws from — an empirical check, not an assumption.
  • Whether a hand-built lookalike/confusables table is complete and current enough to catch realistic contamination sources (PDF copy-paste, spreadsheet autocorrect, font-rendering artifacts).
  • Whether this kind of silent substitution risk has ever actually affected data inside the registry pipeline itself — that question belongs to CFF's own data team and their ingestion logs, not to this podcast or any outside paper.
