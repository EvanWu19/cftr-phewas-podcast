How did this episode land for you?

Show notes — KEEPER + LLM case adjudication (Track B, 2026-08-01)

Blurb. Schuemie and colleagues (npj Digital Medicine, 2025, open access) test whether large language models can automate case adjudication in observational research — the labor-intensive chart-review step used to validate phenotype algorithms. Their prior tool, KEEPER (Knowledge-Enhanced Electronic Profile Review), replaces raw charts with a standardized, clinically-organized profile of a patient's structured data (conditions, symptoms, comorbidities, treatments) drawn from the OMOP Common Data Model, so review works even on claims data with no charts. Here they feed that profile to four locally-hosted LLMs (GPT-3.5 Turbo, GPT-4, Llama-2, Sheep-Duck-Llama-2) at temperature 0 with zero-shot, iteratively-optimized prompts, and ask for a case/non-case verdict. Across ten diseases, sensitivity ran 78–98% and specificity 48–98% — competitive with humans at the good end, but the operating point is set by prompt wording, not a tunable threshold. The real prize (workflow panel d): because the LLM is cheap, review can scale to non-cases too, enabling sensitivity estimation, not just PPV. Ships code as the OHDSI Keeper R package (GitHub, v0.2.0). Where it lands: AI-tooling / career (+ Liz data-quality, method only) — a buildable outcome-adjudication-assistant that pre-screens phenotype cases and routes only low-confidence/disagreement cases to a human.

Plain-English glossary

  • Case adjudication — the expert judgment of whether an individual patient truly meets a case definition.（中文：病例判定，由专家判断某个病人是否真正符合病例定义。）
  • Chart review — a human reading a patient's clinical record to validate whether an algorithm classified them correctly.（中文：病历审查，由人阅读病人的临床记录，以验证算法是否分类正确。）
  • Index date — the timepoint at which an algorithm believes a patient became a case; all data windows are defined relative to it.（中文：索引日期，算法认为病人成为病例的时间点，所有数据窗口都相对于它定义。）
  • OMOP Common Data Model — the OHDSI standard that maps heterogeneous health databases into one shared vocabulary and structure.（中文：OMOP 通用数据模型，OHDSI 把异构的医疗数据库映射到同一套共享词汇与结构的标准。）
  • Phenotype algorithm — a rule set over codes (e.g. ICD-10, LOINC) that decides which patients count as cases.（中文：表型算法，基于编码（如 ICD-10、LOINC）的规则集，用来判定哪些病人算作病例。）
  • Positive predictive value (PPV) — of the patients an algorithm flags as cases, the fraction that truly are; estimable from case-only review.（中文：阳性预测值，算法标记为病例的病人中真正是病例的比例；仅审查病例即可估计。）
  • Reference standard / gold standard — the benchmark judgment (here, expert or human-majority-vote adjudication) against which the LLM is scored.（中文：参考标准/金标准，用来给大语言模型打分的基准判断（此处为专家或人类多数投票的判定）。）

Full citation

Schuemie MJ, et al. Standardized patient profile review using large language models for case adjudication in observational research. npj Digital Medicine. 2025. PMID 39789235; PMC PMC11718233; DOI 10.1038/s41746-025-01433-4.

Methods / tools to lift

  • KEEPER (OHDSI R package, GitHub v0.2.0) — extracts a patient's OMOP-structured findings into a standardized, clinical-reasoning-ordered profile; portable to charts-free datasets.
  • LLM adjudication over structured profiles — feed the KEEPER text profile to a locally-hosted LLM (temperature 0, zero-shot + iterative prompt optimization) for a case/non-case verdict.
  • Leave-one-out human-majority gold standard — build the reference from human reviewers so LLMs can be plotted against individual humans.
  • Scale review to non-cases (workflow panel d) — cheap LLM adjudication enables reviewing non-cases, unlocking sensitivity estimation (not just PPV).

Where it lands + buildable artifact

Serves: AI-tooling / career (+ Liz data-quality, method only). Ends on the tool sketch.

Paste-ready MVP: outcome-adjudication-assistant (M) — input a candidate case cohort in OMOP form; generate a KEEPER-style profile per patient; feed each to a locally-hosted LLM with a specificity-tuned prompt; output case/non-case + confidence flag; route only low-confidence and human-disagreement cases to manual review; because non-cases are now cheap to review, report both PPV and sensitivity.

What to verify first

  • Disease-specific calibration — specificity floor of 48% shows the operating point isn't stable across conditions; any CF-relevant outcome needs its own prompt tuning and its own measured sens/spec.
  • Gold standard is imperfect — human majority vote has its own error; "matches humans" is a ceiling, not ground truth.
  • Profile completeness caps specificity — the LLM can only weigh what the structured data captured; findings only in free text or never coded are invisible to it.
  • Brittle parsing — yes/no keyword parser + prompt sensitivity → log every response verbatim and audit the parses.
  • Method runs on OMOP-standardized data generally; describes no specific registry's internals.

ALEX Welcome back. 欢迎回来。 Today's Track B paper is "Standardized patient profile review using large language models for case adjudication in observational research," by Martijn Schuemie and colleagues from the OHDSI community. 今天 Track B 的论文是 Martijn Schuemie 及其同事（来自 OHDSI 社区）发表的《使用大语言模型对观察性研究中的病例进行标准化患者档案审查与判定》。 It's in npj Digital Medicine, 2025, fully open access, and it ships code. 它发表在 2025 年的《npj Digital Medicine》上，完全开放获取，而且附带代码。 We're reading it because it automates one of the most tedious, least portable steps in real-world-evidence work — chart review to validate a phenotype — and that's a step a registry team runs constantly. 我们读它，是因为它把真实世界证据工作中最枯燥、最难迁移的一个步骤——用病历审查来验证表型——自动化了，而这正是注册库团队会不断做的一步。

JORDAN Let me get the vocabulary straight first. 先让我把术语理清楚。 What's a phenotype algorithm, and what's this chart review it's replacing? 什么是表型算法，它要替代的病历审查又是什么？

ALEX In observational research you rarely have a clean field that says "this patient has osteoporosis." 在观察性研究里，你很少能有一个干净的字段直接写着"这个病人有骨质疏松"。 So you write a phenotype algorithm — a rule set over codes like ICD-10 diagnoses and LOINC lab tests that decides who counts as a case. 于是你写一个表型算法（phenotype algorithm）——一套基于编码（比如 ICD-10 诊断码和 LOINC 检验码）的规则，用来判定谁算作一个病例。 The trouble is that a code-based rule is a proxy, and proxies misfire. 问题在于，基于编码的规则是一种代理，而代理会出错。 To check it, epidemiologists do chart review: a human reads the patient's clinical record and judges whether the algorithm was right. 为了检查它，流行病学家做病历审查（chart review）：一个人读病人的临床记录，判断算法是否判对了。 That's the reference standard here — expert human adjudication of individual cases. 这就是这里的参考标准（reference standard）——由专家对单个病例做人工判定。 The pain points are real: chart review is slow, subjective, and it doesn't port between datasets, because one hospital's charts look nothing like another's, and claims databases often have no charts at all. 痛点是实实在在的：病历审查慢、主观，而且无法在数据集之间迁移，因为一家医院的病历跟另一家完全不同，而理赔数据库常常根本没有病历。

JORDAN So how do they get around the "no charts" problem? 那他们怎么绕开"没有病历"这个问题？

ALEX This is where their prior tool, KEEPER, comes in, and it's the key idea. 这就轮到他们之前的工具 KEEPER 登场了，也是核心思路。 KEEPER stands for Knowledge-Enhanced Electronic Profile Review. KEEPER 是"知识增强的电子档案审查"（Knowledge-Enhanced Electronic Profile Review）的缩写。 Instead of a raw chart, KEEPER pulls a patient's structured data elements — relevant conditions, symptoms, comorbidities, treatments — and lays them out in a standardized profile organized by clinical reasoning. KEEPER 不用原始病历，而是抽取病人的结构化数据元素——相关的病症、症状、合并症、治疗——并按临床推理的逻辑，把它们排成一份标准化的档案。 Crucially it's built on the OMOP Common Data Model, the OHDSI standard that maps different databases into one shared vocabulary and structure. 关键是它建立在 OMOP 通用数据模型（OMOP Common Data Model，即 OHDSI 把不同数据库映射到同一套共享词汇和结构的标准）之上。 So the same KEEPER profile can be generated from a claims database that never had charts to begin with — the standardization is what buys portability. 所以同一份 KEEPER 档案，也能从一个本来就没有病历的理赔数据库里生成——标准化换来了可迁移性。 In their earlier work, giving human reviewers a KEEPER profile instead of a raw chart sped up review and raised inter-annotator agreement. 在他们更早的工作里，给人类审查者一份 KEEPER 档案而非原始病历，加快了审查、也提高了标注者之间的一致性。 This paper's move is to hand that KEEPER profile to a large language model and ask the model to make the case-or-not call. 这篇论文的动作，是把那份 KEEPER 档案交给一个大语言模型，让模型来做"是不是病例"的判定。

JORDAN And they cared enough about privacy to host the models themselves. 而且他们足够在意隐私，把模型自己托管了起来。

ALEX Right, and that design choice matters for anyone with sensitive patient data. 没错，这个设计选择对任何拥有敏感患者数据的人都很重要。 They tested four LLMs — the commercial GPT-3.5 Turbo and GPT-4, plus the openly available Llama-2 and a fine-tune called Sheep-Duck-Llama-2 — all hosted locally so patient profiles never leave the environment. 他们测试了四个大语言模型——商业的 GPT-3.5 Turbo 和 GPT-4，加上开放可得的 Llama-2 以及一个名为 Sheep-Duck-Llama-2 的微调版本——全部本地托管，这样患者档案永远不离开本地环境。 They set temperature to zero for all of them, meaning the model gives its most deterministic answer rather than a creative sample. 他们把所有模型的温度（temperature）设为零，意思是模型给出最确定的答案，而不是一个带随机性的采样。 The prompting is mostly zero-shot — no worked examples in the prompt — with a round of iterative prompt optimization on top. 提示方式主要是零样本（zero-shot，即提示里不放示例），再叠加一轮迭代式的提示优化。 The KEEPER output is turned into plain text grouped by category, the LLM is asked to reason and then give a summary verdict, and a simple parser strips everything but the summary and looks for "yes" or "no." KEEPER 的输出被转成按类别分组的纯文本，让大语言模型先推理、再给一个总结判定，然后一个简单的解析器把除总结外的内容都去掉，寻找"yes"或"no"。 One design choice I'd push on: a keyword parser looking for yes/no is brittle — if the model hedges or phrases the verdict oddly, you either misread it or drop the case. 有一个设计选择我想质疑：一个找 yes/no 的关键词解析器很脆弱——如果模型含糊其辞或用奇怪的措辞给结论，你要么误读它，要么丢掉这个病例。

JORDAN Give me a concrete example of what the model is actually looking at. 给我一个具体例子，说说模型实际上在看什么。

ALEX Osteoporosis is the one they walk through, and it makes the design tangible. 骨质疏松是他们详细走过的例子，它让这个设计变得具体。 The phenotype algorithm identifies cases by the first recorded diagnosis code that maps to the standard OMOP concept for osteoporosis or any of its descendants — and that single standard concept covers two hundred twenty-three ICD-10 codes, including things like M81.9, unspecified osteoporosis, and M81.0, postmenopausal osteoporosis. 表型算法通过首次记录的、映射到 OMOP 中"骨质疏松"标准概念（或其任何下位概念）的诊断码来识别病例——而这一个标准概念就涵盖了二百二十三个 ICD-10 编码，包括 M81.9（未特指的骨质疏松）和 M81.0（绝经后骨质疏松）等。 Mapping to one standard concept instead of hand-listing codes is what makes the algorithm portable across systems. 映射到一个标准概念、而不是手工列举编码，正是让算法能跨系统迁移的原因。 Then KEEPER extracts a defined set of concepts from specific time windows: related conditions like malignant neoplasm within ninety days of the index date, symptoms like joint pain of the pelvic region within thirty days before index, comorbidities like a prior bone fracture at any point, and treatments like zoledronic acid prescribed after diagnosis. 然后 KEEPER 从特定时间窗口里抽取一组预定义的概念：像在索引日期（index date）前后九十天内的恶性肿瘤这样的相关病症，像索引前三十天内的骨盆区关节痛这样的症状，像既往任何时间的骨折这样的合并症，以及像诊断后处方的唑来膦酸这样的治疗。 The index date is the point the algorithm believes the patient became a case, and every window is defined relative to it. 索引日期是算法认为病人成为病例的时间点，每个窗口都是相对于它来定义的。 So the LLM isn't reading a chart — it's reading a clinically-organized summary of coded facts and their timing, and judging whether that pattern really adds up to osteoporosis. 所以大语言模型读的不是病历，而是一份按临床逻辑组织的、编码事实及其时序的摘要，并判断这个模式是否真的构成骨质疏松。

JORDAN And the paper frames this as a progression of workflows, right? 而这篇论文把这个框定为工作流的递进，对吧？

ALEX Yes, four steps, and the fourth is the real prize. 是的，四个步骤，第四个才是真正的奖赏。 The status quo is chart review applied only to identified cases, which lets you estimate positive predictive value and nothing else. 现状是只对已识别的病例做病历审查，这只能让你估计阳性预测值（PPV），别的都算不了。 KEEPER with human reviewers replaces the chart with a structured summary, making review efficient enough to apply to more data. 有人类审查者的 KEEPER 用结构化摘要替代病历，让审查高效到足以应用于更多数据。 KEEPER with an LLM cuts the manual effort further. 有大语言模型的 KEEPER 进一步削减了人工。 And the fourth step is the one that changes the science: because the LLM is cheap to run, you can scale review to include non-cases, not just cases — and reviewing both cases and non-cases is what lets you compute sensitivity, not just PPV. 第四步则是改变科学的那一步：因为大语言模型运行成本低，你可以把审查扩展到也包括非病例，而不只是病例——而同时审查病例和非病例，正是让你能计算敏感性、而不只是 PPV 的前提。 That matters because for rare outcomes, reviewing enough non-cases by hand to estimate sensitivity is basically never feasible. 这很重要，因为对于罕见结局，靠人工审查足够多的非病例来估计敏感性，基本上从来都不可行。

JORDAN How did they know whether the model was right? 他们怎么知道模型判得对不对？

ALEX Against human gold standards, across ten diseases. 用人类金标准来对照，跨十种疾病。 For one test set the gold standard came from external reviewers; for the others it was the majority vote of human reviewers using a leave-one-out approach, which also lets them plot how the LLMs compare against individual humans. 有一个测试集的金标准来自外部审查者；其余的则是人类审查者用留一法（leave-one-out）得出的多数投票，这也让他们能画出大语言模型与单个人类的比较。 The headline result is a range, and the range itself is the finding. 主要结果是一个区间，而这个区间本身就是发现。 Across the ten diseases, sensitivity ran from seventy-eight to ninety-eight percent and specificity from forty-eight to ninety-eight percent, depending on the model and the prompt. 在这十种疾病里，敏感性从 78% 到 98%，特异性从 48% 到 98%，取决于模型和提示。 So at the good end it's genuinely competitive with human reviewers, and at the bad end — that forty-eight percent specificity — the model is waving through a lot of non-cases as cases. 所以在好的一端，它确实能与人类审查者竞争，而在差的一端——那个 48% 的特异性——模型把很多非病例当成病例放行了。 The takeaway they draw is measured: this is promising for automating phenotype evaluation, not a solved replacement for human review. 他们得出的结论是审慎的：这对自动化表型评估很有前景，但还不是能取代人工审查的已解决方案。

JORDAN Why does specificity swing so much more than sensitivity? 为什么特异性的波动比敏感性大得多？

ALEX That's the diagnostically interesting part. 这正是诊断上有意思的地方。 A KEEPER profile is a curated list of things consistent with the disease, so a model biased toward "yes" will look sensitive but sloppy on specificity — it says case whenever it sees supportive findings, without weighing the absence of confirming evidence. 一份 KEEPER 档案是一串与该疾病一致的信息，所以一个偏向"yes"的模型看起来敏感，但特异性上很马虎——只要看到支持性的信息就说是病例，而不去权衡确证证据的缺失。 The prompt is doing a lot of work: a prompt that tells the model to demand confirming evidence before saying case pulls specificity up, and that's why iterative prompt optimization moved the numbers. 提示承担了很多工作：一个要求模型在判定为病例前必须有确证证据的提示，会把特异性拉上去，这也是为什么迭代式提示优化能改变这些数字。 The deeper point for a data scientist is that the model's operating point — where it sits on the sensitivity-specificity trade-off — is set by wording, not by a threshold you can tune numerically, which makes it harder to control and audit than a classifier with an explicit cutoff. 对数据科学家更深的一点是：模型的工作点——它落在敏感性-特异性权衡曲线的哪个位置——是由措辞决定的，而不是一个你能用数值调节的阈值，这让它比有明确切点的分类器更难控制和审计。

JORDAN Where does this land for us? 那这对我们意味着什么落点？

ALEX This lands on the AI-tooling and career target, with a strong secondary tie to the Liz-sponsored data-quality work — and I'll keep it to method only, nothing about registry internals. 这个落点在 AI 工具与职业目标上，同时与 Liz 主导的数据质量工作有很强的次要关联——我只讲方法，绝不涉及注册库内部。 The transferable idea: outcome validation is the bottleneck in real-world evidence, and this pattern turns it into a semi-automated pipeline where a standardized profile plus an LLM adjudicator pre-screens cases, so humans only review the disagreements. 可迁移的思路是：结局验证是真实世界证据的瓶颈，而这个模式把它变成一个半自动化流水线——标准化档案加上一个大语言模型判定器先做初筛，人类只审查有分歧的部分。 Since the code is a real OHDSI R package — Keeper, on GitHub at the v0.2.0 tag — this is a wrap-and-adapt job, not a from-scratch build. 由于代码是一个真实的 OHDSI R 包——Keeper，在 GitHub 上的 v0.2.0 标签——这是一个"封装并改造"的活，而不是从零构建。 So the buildable artifact, and I'll end on this tool sketch: an outcome-adjudication-assistant. 所以可构建的东西，我就以这个工具草图收尾：一个 outcome-adjudication-assistant（结局判定助手）。 The MVP: take a candidate case list from a phenotype algorithm, generate a KEEPER-style standardized profile for each from OMOP-mapped data, feed each profile to a locally-hosted LLM with a specificity-tuned prompt, and output a case/non-case call plus a confidence flag — routing only the low-confidence and disagreement cases to a human. MVP 版本：拿一份来自表型算法的候选病例清单，从 OMOP 映射的数据里为每个病例生成一份 KEEPER 式的标准化档案，把每份档案喂给一个本地托管的大语言模型（配一个针对特异性调过的提示），输出病例/非病例的判定加一个置信度标记——只把低置信度和有分歧的病例转给人类。 Input is a cohort of candidate cases in OMOP form; difficulty is medium; the payoff is that you can finally review non-cases too, which lets you estimate sensitivity, not just positive predictive value. 输入是一队 OMOP 格式的候选病例；难度中等；回报是你终于也能审查非病例，从而估计敏感性，而不只是阳性预测值。

JORDAN What would we need to verify before leaning on that assistant? 在依赖那个助手之前，我们需要核实什么？

ALEX Several things, all phrased as what we'd need to check. 有几件事，都表述成"我们需要核对的东西"。 First, disease-specific calibration: their specificity floor of forty-eight percent shows the operating point isn't stable across conditions, so any CF-relevant outcome would need its own prompt tuning and its own measured sensitivity and specificity before use. 第一，疾病特异性的校准：他们 48% 的特异性下限表明，工作点在不同病症间并不稳定，所以任何与 CF 相关的结局，在使用前都需要各自的提示调优、各自实测的敏感性和特异性。 Second, the gold standard is human majority vote, which has its own error, so "matches humans" is a ceiling defined by imperfect adjudicators, not ground truth. 第二，金标准是人类多数投票，它本身也有误差，所以"与人类一致"是一个由不完美判定者定义的上限，而不是绝对真相。 Third, the profile only contains what the structured data captured — if a confirming finding lives only in free text or was never coded, the LLM can't weigh evidence that isn't in front of it, which caps achievable specificity independent of the model. 第三，档案只包含结构化数据捕捉到的内容——如果一个确证信息只存在于自由文本里、或者从未被编码，大语言模型就无法权衡它面前没有的证据，这会给可达到的特异性设一个与模型无关的上限。 Fourth, the yes/no parser and prompt sensitivity mean you'd want to log every model response verbatim and audit the parses, not just trust the final label. 第四，yes/no 解析器加上对提示的敏感性，意味着你会想逐字记录每个模型的回复并审计解析结果，而不是只信最终标签。 None of this describes any specific registry's data or structure — it's a method that runs on OMOP-standardized data generally. 这一切都不描述任何具体注册库的数据或结构——它是一个在 OMOP 标准化数据上普遍运行的方法。
