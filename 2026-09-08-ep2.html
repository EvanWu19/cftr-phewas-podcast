Ep2 (Track B) — An OMOP Pipeline for ECG/HRV Integration

Reali and colleagues (2026, Frontiers in Bioinformatics) built and open-sourced an ETL pipeline that ingests raw ECG recordings from heterogeneous PhysioNet datasets and standardizes them into the OMOP Common Data Model — mapping diagnoses, PhysioNet annotations, automatically detected conduction abnormalities, and computed heart-rate-variability (HRV) indices to OMOP concepts wherever possible. The headline finding is a clean split: all 7 diagnoses, 16 annotation types, and 6 conduction abnormalities mapped completely to existing standard OMOP concepts, but only 2 of 15 computed HRV indices did — the remaining 13 required adding a custom vocabulary, which the authors candidly note makes those features invisible in multi-site network studies. The pipeline scaled to a 21,799-record, ~3GB PhysioNet dataset (PTB-XL) on a single consumer workstation, though the authors flag the current implementation as effectively single-threaded, with parallelization left as future work. The transferable idea for registry work isn't the ECG code — it's the diagnostic pattern of running every field through "does a standard OMOP concept exist" and using the pass/fail split as a structured gap report.

Plain-English glossary

  • OMOP CDM — Observational Medical Outcomes Partnership Common Data Model; a standardized relational schema (maintained by OHDSI) for representing health data from different sources in one common structure and vocabulary.（中文:观察性医学结果合作关系通用数据模型,由OHDSI社区维护的标准化关系型数据模式。）
  • ETL (Extract-Transform-Load) — the three-stage process of pulling raw data, converting it to a target schema, and loading it into a database.（中文:抽取-转换-加载,把原始数据提取、转换为目标模式、再加载入库的三阶段流程。）
  • Concept / Concept ID — the atomic coded unit of an OMOP vocabulary representing one specific clinical idea; "standard" concepts are the canonical representation, "non-standard" ones must map to a standard concept to be broadly usable.（中文:OMOP词汇体系的最小编码单位;"标准概念"为规范表示,"非标准概念"须映射到标准概念才能广泛使用。）
  • Custom vocabulary / custom standard concept — a locally added concept used when no existing OMOP vocabulary term fits; custom standard concepts cannot map to anything else in OMOP, so they become invisible in cross-site network studies.（中文:当OMOP现有词汇都不合适时本地新增的概念;自定义"标准"概念无法映射到OMOP其他概念,因而在跨站点联合研究中不可见。）
  • LOINC / SNOMED — standardized medical vocabularies (for lab/clinical observations, and clinical terms respectively) used to give the same concept the same code across institutions.（中文:标准化医学术语体系(分别用于检验/临床观测项目、临床术语),让不同机构对同一概念使用相同编码。）
  • HL7 FHIR — Fast Healthcare Interoperability Resources; a structural interoperability standard used more for live clinical data exchange, distinct from OMOP's research-warehouse orientation.（中文:快速医疗互操作性资源标准,更多用于实时临床数据交换,区别于OMOP面向研究仓库的定位。）
  • HRV (heart rate variability) indices — metrics computed from beat-to-beat timing variation of the heart, e.g. AVRR (average RR interval) and SDRR (standard deviation of RR intervals).（中文:从心跳逐搏间隔时间变化中计算出的指标,如AVRR(平均RR间期)和SDRR(RR间期标准差)。）
  • "Center effect" — bias introduced into pooled multi-site data by systematic differences in acquisition devices/protocols across collection sites.（中文:因不同采集站点的设备或流程系统性差异,给汇总的多中心数据带来的偏倚。）
  • WFDB / mhrv — established open-source toolkits (MATLAB-based) used for ECG waveform annotation and HRV feature computation respectively.（中文:基于MATLAB的开源工具包,分别用于心电波形标注和HRV特征计算。）

Full citation

Methods / tools to lift

  • Concept-mapping decision tree (Strategies A–D) — standard → standard+non-standard → custom non-standard → custom standard, applied systematically to every extracted feature.
  • Concept-coverage gap analysis — using the pass/fail split across a feature inventory (7+16+6 diagnoses/annotations/abnormalities vs. 15 HRV indices) as a structured way to surface where a vocabulary doesn't yet cover computed features.
  • Open pipeline repo: github.com/hbd-polimi-ws4/ecg2omop-public — MATLAB + Python ETL against a PostgreSQL OMOP instance.
  • WFDB + mhrv for beat annotation and HRV computation from raw signal.

Where it lands + buildable artifact

Serves the AI-tooling / career priority (Track B). Buildable artifact: an OMOP concept-coverage auditor — MVP: take a list of registry-derived/computed fields, query the OHDSI Athena vocabulary API (or a local OMOP vocabulary table) for each, and output a report classifying each field as standard-mapped / non-standard-mappable / custom-vocabulary-required. Difficulty: S (mostly API calls + a lookup table).

What to verify first

  • Whether defaulting to a custom-vocabulary strategy for any given field is worth the loss of cross-site queryability — this needs to be an explicit tradeoff decision, not a default.
  • The scalability claim is a single successful run without parallelization, not a throughput benchmark — wall-clock timing per ETL stage would be needed before treating it as evidence of registry-scale readiness.
  • Whether a feature-extraction window (e.g., whole-trace vs. episode-level HRV) matches the clinical question being asked, independent of whether the field is cleanly concept-mapped.

JORDAN Start with the acronym soup — OMOP CDM, and why does ECG data even need "harmonizing"? 先讲讲这堆缩写——OMOP CDM,以及心电图数据为什么需要"协调"(harmonizing)?

ALEX OMOP CDM is the Observational Medical Outcomes Partnership Common Data Model — a standardized relational schema, maintained by the OHDSI community, that lets health data from completely different sources sit in the same table structure with the same vocabulary. OMOP CDM,全称Observational Medical Outcomes Partnership Common Data Model(观察性医学结果合作关系通用数据模型),是由OHDSI社区维护的一套标准化关系型数据库模式,能让来自完全不同来源的医疗数据放进同一套表结构、使用同一套术语体系。 The paper distinguishes harmonization at three levels: data content — making the actual signal values comparable across sites, which for biosignals like ECG is relatively easy since it's mostly sampling-rate and reference-point differences; data format — the raw file format, like European Data Format or BIDS for signals versus DICOM for images; and metadata — both structure (which OMOP or FHIR handles) and semantics, meaning the vocabulary used to describe what a field actually means, which is where LOINC and SNOMED come in. 论文把协调分成三个层次:数据内容层——让不同站点采集的信号数值本身可以比较,对于像心电图这样的生理信号来说相对容易,因为差异主要在采样率和参考点上;数据格式层——原始文件格式,比如生理信号常用的European Data Format(欧洲数据格式)或BIDS(脑成像数据结构),而医学影像则通常用DICOM格式;以及元数据层——既包括结构层面(由OMOP或HL7 FHIR处理),也包括语义层面,也就是描述某个字段实际含义所用的词汇体系,这正是LOINC和SNOMED发挥作用的地方。 LOINC and SNOMED are standardized medical terminologies — think of them as controlled vocabularies that assign one agreed-upon code to a concept, like "heart rate" or "12-lead ECG," so two hospitals using different local naming conventions can still be queried the same way. LOINC和SNOMED是标准化的医学术语体系——可以理解为受控词表,为每个概念(比如"心率"或"12导联心电图")赋予一个统一认可的编码,这样即使两家医院各自使用不同的本地命名习惯,也能用同一种方式被查询到。

JORDAN And HRV — heart rate variability — is the specific feature type they're trying to fit into this model? HRV,也就是心率变异性,就是他们要放进这个模型里的具体特征类型?

ALEX Right, HRV indices are derived metrics computed from the beat-to-beat timing of the heart — things like AVRR, the average RR interval, or SDRR, the standard deviation of RR intervals — and they're exactly the kind of computed, higher-order feature that a common data model wasn't originally designed around. 没错,HRV(心率变异性)指标是从心跳的逐搏间隔时间中计算出来的衍生指标——比如AVRR(平均RR间期)或SDRR(RR间期的标准差)——而这正是通用数据模型最初在设计时没有充分考虑到的一类计算得出的高阶特征。 A "concept" in OMOP is the atomic unit of the vocabulary — a single coded entry, with a numeric Concept ID, that represents one specific idea, like "12-lead ECG" or "right bundle branch block." OMOP中的"概念"(concept)是词汇体系里的最小单位——一个带有数字概念ID(Concept ID)的编码条目,代表一个具体的含义,比如"12导联心电图"或"右束支传导阻滞"。 A concept is "standard" if it's the canonical, OMOP-blessed representation of that idea; "non-standard" concepts exist and can be looked up but must map to a standard one to be usable across sites. 如果某个概念是OMOP官方认可的、代表某个含义的规范表示,就称为"标准概念"(standard);"非标准概念"也存在、也可以查询,但必须映射到某个标准概念才能在跨站点场景中使用。

JORDAN So what problem is the pipeline actually solving, beyond "ECG data is messy"? 那这个流程到底解决了什么问题,除了"心电图数据很乱"之外?

ALEX The deeper motivation is reusability at scale. 更深层的动机是大规模的可复用性。 If you want to pool ECG recordings from multiple hospitals or public datasets for a study — say, comparing HRV changes across arrhythmia types — every source uses different file formats, different annotation conventions, and different local names for the same clinical concept. 如果你想把多家医院或多个公开数据集的心电图记录汇总起来做研究——比如比较不同类型心律失常之间的HRV变化——每个数据源都可能使用不同的文件格式、不同的标注习惯,以及对同一个临床概念的不同本地命名。 Without a common model, every new pooling project means re-writing the mapping logic from scratch, and results are hard to compare across studies because nobody's using the same vocabulary. 如果没有一个通用模型,每一个新的数据汇总项目都得从头重写映射逻辑,而且研究结果之间也很难比较,因为大家用的词汇体系都不一样。 The authors also note that biosignals are comparatively the easy case in this landscape — bioimages like MRI are far more demanding, because features extracted from scanners vary even within the same manufacturer and model, whereas ECG signal content differences are mostly resolvable with basic signal processing like resampling or re-referencing. 作者也指出,在这个领域里,生理信号其实算是相对容易处理的一类——像MRI这样的医学影像要复杂得多,因为不同扫描仪提取出来的特征即便在同一厂商同一型号之间也会有差异,而心电信号内容上的差异大多可以通过重采样或改变参考点等基本信号处理方法来解决。 That framing matters because it tells you where to expect this kind of pipeline to generalize easily versus where it won't. 这个框架很重要,因为它告诉你这类流程在哪些场景下容易推广,在哪些场景下不容易。

JORDAN Walk me through what the pipeline actually does, end to end. 那具体讲讲这个流程从头到尾是怎么运作的。

ALEX It's an Extract-Transform-Load, or ETL, pipeline written in MATLAB and Python, with PostgreSQL as the backing database for the OMOP tables — that's the RDBMS the OHDSI community itself recommends. 这是一个用MATLAB和Python编写的抽取-转换-加载(Extract-Transform-Load,简称ETL)流程,后端用PostgreSQL数据库存储OMOP表——这也是OHDSI社区自己推荐的关系型数据库管理系统(RDBMS)。 The Extract step pulls from PhysioNet public datasets — three moderate-sized sources for development, plus PTB-XL, a fourth dataset of 21,799 twelve-lead ECG recordings at roughly 3 gigabytes, added specifically to test scalability on a workstation with a consumer-grade CPU and 32 gigabytes of RAM. 抽取(Extract)步骤从PhysioNet公开数据集中拉取数据——开发阶段用了三个中等规模的数据源,另外还加入了第四个数据集PTB-XL,包含21,799条12导联心电记录、约3GB大小,专门用来在一台配备消费级CPU和32GB内存的工作站上测试可扩展性。 Feature extraction uses established open-source toolkits — the MATLAB-based WFDB, or Waveform Database Software Package, and a heart-rate-variability tool called mhrv — to pull beat annotations, automatically detect conduction abnormalities, and compute the HRV indices. 特征提取阶段使用了成熟的开源工具包——基于MATLAB的WFDB(Waveform Database Software Package,波形数据库软件包)以及一个叫mhrv的心率变异性分析工具——用来提取心跳标注、自动检测传导异常,并计算HRV指标。 The Transform step is where the concept mapping happens, following four strategies labeled A through D depending on whether a standard concept already exists, a standard-plus-non-standard combination is needed, or — when nothing in OMOP's vocabularies fits — a custom vocabulary has to be added. 转换(Transform)步骤是概念映射发生的地方,遵循从A到D四种策略,具体取决于是否已经存在标准概念、是否需要标准与非标准概念的组合,或者——当OMOP词汇表里完全没有合适选项时——是否需要添加自定义词汇。 Load then populates the OMOP tables: visit_occurrence for each day's recording session, procedure_occurrence for each individual ECG acquisition, and measurement for the extracted HRV values and detected abnormalities.加载(Load)步骤则把数据填入OMOP的各张表:visit_occurrence(就诊记录表)记录每天的采集场次,procedure_occurrence(操作记录表)记录每一次单独的心电图采集,measurement(测量值表)记录提取出的HRV数值和检测到的异常。

JORDAN Where do you push back on this design? 你会在这个设计的哪个地方提出质疑?

ALEX On the custom-vocabulary strategy, Strategy D. 我会质疑自定义词汇策略,也就是策略D。 It's the only option when nothing in OMOP's standard vocabularies fits, and the authors are upfront that it comes at a real cost: a custom standard concept can't be mapped to anything else already in OMOP, which means any feature captured that way becomes invisible in multi-site network studies, since other sites won't recognize your custom codes. 当OMOP标准词汇表里没有任何合适选项时,这是唯一的办法,而作者也坦率地指出了这样做的实际代价:自定义标准概念无法映射到OMOP中已有的任何其他概念,这意味着通过这种方式记录的特征在多站点联合研究中会变得"不可见",因为其他站点根本无法识别你的自定义编码。 That's a real tension for anyone building a registry-scale harmonization tool: the more novel or computed your feature is — exactly the kind of thing an AI or signal-processing pipeline tends to produce — the less likely OMOP's existing vocabulary covers it, and the more you're forced into a choice that trades local usability for cross-site invisibility. 这对任何想要构建注册规模协调工具的人来说都是一个真实的矛盾:你的特征越新颖、越是计算衍生出来的——而这恰恰是AI或信号处理流程最容易产出的那类特征——OMOP现有词汇表覆盖到它的可能性就越小,你就越容易被迫做出这样的取舍:牺牲跨站点的可见性来换取本地的可用性。

JORDAN So how much of their feature set actually hit that wall? 那他们的特征集里,到底有多少撞上了这堵墙?

ALEX One more query example is worth having, because it shows a real gotcha in signal-derived features specifically. 还有一个查询示例值得一提,因为它揭示了信号衍生特征中一个真实存在的陷阱。 They looked at AVRR — average RR interval — grouped by detected arrhythmia type, comparing shorter, standard 12-lead recordings against longer 24-hour recordings. 他们按检测到的心律失常类型对AVRR(平均RR间期)进行分组比较,对比了较短的标准12导联记录和较长的24小时记录。 The expected physiological pattern — AVRR decreasing during one arrhythmia type and increasing during another — showed up clearly in the short recordings, but was much less pronounced in the 24-hour ones, because their pipeline currently computes HRV indices over the entire trace rather than isolating the specific arrhythmic episode within a long recording. 在短时记录中,预期的生理模式——AVRR在一种心律失常类型下降低、在另一种类型下升高——表现得很清楚,但在24小时记录中就没那么明显了,因为他们目前的流程是对整段记录计算HRV指标,而不是在一段长记录中单独截取出具体的心律失常发作片段。 That's a useful, honest limitation: a concept-mapped, harmonized dataset still inherits whatever granularity choices were made in feature extraction, and those choices can wash out the very signal you're querying for. 这是一个很实用也很诚实的局限性:一个经过概念映射、协调统一的数据集,仍然会继承特征提取阶段所做的粒度选择,而这些选择恰恰可能把你想查询的信号本身给冲淡掉。

JORDAN And the scalability test on the big dataset — did it actually hold up? 那在大数据集上的可扩展性测试呢——真的撑得住吗?
