Plain-English glossary.

  • BAM: binary alignment file — reads placed at their genomic coordinates after alignment to a reference.
  • Bioinformatics pipeline: fixed sequence of specialized tools turning raw sequencing output into interpretable results (e.g., FASTQ → BAM → VCF).
  • DSL2 module: in modern Nextflow, a self-contained wrapper around one tool invocation; nf-core maintains a central, reviewed library of them.
  • FASTQ: raw sequencing reads — short A/C/G/T strings each with a per-base quality score.
  • MultiQC: tool (same group) that aggregates QC metrics/logs from every pipeline step into one interactive HTML report.
  • Reference genome / build: the genome coordinates and annotation version reads are aligned/interpreted against — itself a silent dependency that changes results.
  • VCF (variant call format): the list of positions where a sample differs from the reference.

JORDAN Then start me at the bottom. When a bioinformatician says "pipeline," what is the actual thing? I work in tooling, so don't explain containers to me — explain what's genomics-specific here.

ALEX Fair split. A bioinformatics pipeline is a fixed sequence of processing steps that takes raw sequencing output and walks it down to something interpretable. The canonical chain: you start with FASTQ files — the raw reads, basically millions of short text strings of A, C, G, T with a quality score per letter. You align those reads to a reference genome, producing a BAM file — the reads now placed at their genomic coordinates. Then you call variants off that alignment, producing a VCF — variant call format — the list of positions where this sample differs from the reference. Each of those arrows is a separate specialized tool, often from a different lab, with its own version, its own quirks, its own reference-data dependencies. A pipeline is the glue that runs aligner-then-caller-then-annotator in the right order with the right files. And the genomics-specific pain is that the reference data — which genome build, which annotation version — is itself a dependency that silently changes your answer.

JORDAN So what was broken badly enough in 2020 that this paper needed to exist?

ALEX The reproducibility crisis in computational genomics. Picture the normal state of the field: every lab writes its own variant-calling pipeline as a pile of shell scripts. It runs on their cluster, with their installed tool versions, their reference files, their hardcoded paths. Hand it to the lab next door and it breaks — different scheduler, different software versions, a reference build that's off by one. Worse, run the "same" pipeline two years apart and you might get different variant calls because a dependency quietly updated. For a field whose whole output is "here are the variants associated with disease," that's corrosive. Nextflow — yesterday's paper — solved part of it: it's a workflow language that abstracts away the compute environment, so the same pipeline runs on a laptop, an HPC cluster, or the cloud without rewriting. But Nextflow gives you the engine, not the standards. Nothing stopped you from writing an unreadable, untested, unversioned Nextflow pipeline.

JORDAN And nf-core is the standards layer. What does it actually impose?

ALEX Right — nf-core is a curated, community-maintained collection of Nextflow pipelines, plus the scaffolding and rules that make them uniform. The core ideas: one, a standardized pipeline template — every nf-core pipeline has the same directory structure, the same config system, the same documentation layout, so once you can read one you can read all of them. Two, packaged software — every tool a pipeline needs is pinned to an exact version and shipped in a container or Conda environment, so the software environment is reproducible rather than "whatever was on the cluster." Three, continuous integration testing — every pipeline ships with a tiny test dataset and runs automatically on every code change, so a broken pipeline gets caught before release. Four, stable, versioned releases — you can cite "I ran nf-core/sarek version X" and someone can rerun exactly that. Five, a linting tool that checks any pipeline against the community standards and flags noncompliance. The unifying bet is: portability plus pinned software plus automated tests equals results that actually reproduce.

ALEX And here's where I'd push on a design choice. That uniformity is bought with rigidity. The nf-core template is opinionated and fairly heavy — there's real overhead to scaffolding a compliant pipeline, the linting can feel like it's enforcing ceremony, and for a single analyst doing a one-off internal analysis, standing up containers and CI for a three-step workflow can be more machinery than the problem warrants. The framework is optimized for pipelines meant to be shared and rerun by many people over years, which is the right target — but it means the on-ramp is steep, and you should know you're adopting a community's conventions, not just a tool.

JORDAN You mentioned a shared module library. Why does that matter more than it sounds?

ALEX Because it's how the community avoids reinventing the same step a hundred times. In the DSL2 era of Nextflow, a pipeline is built from modules — a module is a self-contained wrapper around one tool invocation, say "run this aligner with these inputs and outputs." nf-core maintains a central library of those modules, so the alignment step you use in a variant-calling pipeline is the same reviewed, tested module someone else uses in an RNA-seq pipeline. Fix a bug or bump a version in the shared module, and every pipeline that imports it inherits the fix. That's ordinary software engineering — don't-repeat-yourself, shared dependencies — but it was genuinely novel as a norm in bioinformatics, where the default had been every pipeline a monolith. It also means a new pipeline is more assembly than authorship: you compose vetted modules rather than writing each tool wrapper from scratch.

JORDAN How many pipelines are we talking about, and who maintains them?

ALEX At the time of the paper the framework already offered a couple dozen production, peer-reviewed pipelines for common assays — RNA-seq, variant calling, ATAC-seq and the like — and it has grown well beyond that since, but I want to flag I'm not going to quote you an exact count from a Correspondence I can't fully read. The maintenance model is the actual innovation: it's community-curated. Pipelines aren't owned by one lab; they're maintained by a distributed community against shared standards, with code review, shared module libraries, and a Slack-and-GitHub culture. That's how you get pipelines that outlive the grad student who wrote them.

JORDAN Did the model deliver — is there evidence it worked beyond "nice idea"?

ALEX The strongest evidence is adoption rather than a benchmark number, and I'll be careful to call it that. nf-core pipelines became a de facto standard in a lot of sequencing core facilities and national genomics efforts — when you see a methods section say "we processed reads with nf-core/rnaseq," that's the framework doing its job: a named, versioned, reproducible pipeline replacing "we used an in-house script." The shared module library means improvements to, say, the alignment step propagate across every pipeline that uses it. So the deliverable wasn't a single accuracy score; it was a cultural and infrastructural shift toward pipelines that are portable, tested, and citable. For a Track B paper, that's the point — the contribution is the engineering pattern, and the repo is the paper.

JORDAN Make one of those concrete for me — what does a real nf-core pipeline give you out of the box?

ALEX Take nf-core/sarek, the germline-and-somatic variant-calling pipeline. You point it at FASTQs and a reference build, and it handles the whole chain — quality trimming, alignment, duplicate marking, base recalibration, variant calling, annotation — each step a pinned, containerized module. It emits the BAMs and VCFs, and then a MultiQC report. MultiQC — also from this group, Phil Ewels' earlier tool — scrapes the log and metric outputs of every step and aggregates them into one interactive HTML page: per-sample read counts, duplication rates, coverage, alignment quality, all in one view. That report is the unsung hero, because it turns "did this 200-sample run go okay?" from spelunking through log files into one glance. The whole thing is configured by a samplesheet and a config file, runs identically on your laptop or a cluster, and you can pin the exact version for a paper.

ALEX Framed as "what to verify," not settled fact. One: match the tool to the scale of the problem — full nf-core compliance is worth it for something that will be rerun and shared, but for a genuinely one-off exploration the overhead may not pay back, so be deliberate about when you adopt the ceremony.
