How did this episode land for you?

Blurb

The HGVS Nomenclature — the global standard for writing down a genetic variant — got a structural overhaul, and this Genome Medicine paper is the specification document. Governance moved under HUGO with a formal eleven-member committee; the Facebook group and single-chair inbox were replaced by public, archived mailing lists and GitHub pull requests; the spec adopted semantic versioning with an explicit provider/consumer compatibility contract; and, most importantly, the syntax is now defined in EBNF (Extended Backus-Naur Form) from a single machine-readable grammar file, making variant strings machine-parseable rather than prose-interpretable. Two substantive spec changes: a double-colon syntax for gene fusions / adjoined transcripts, and — the one that matters for CF — a recommendation to use MANE Select transcripts, giving "which transcript?" a default answer for the first time. This lands on the Karen / variant-interpretation priority: it defines precisely what CFTR notation harmonization should normalize to. Buildable artifact: cftr-hgvs-conformance-harness — normalize any CFTR variant string to HGVS on MANE Select, and report why the failures fail.

Plain-English glossary

Adjoined transcript — the chimeric RNA produced by a gene fusion; written in HGVS with a double colon joining two transcript ranges.（中文：基因融合产生的嵌合 RNA；在 HGVS 中用双冒号连接两段转录本范围来书写。）

Coding-DNA (c.) coordinates — a numbering system that counts only exonic bases of a chosen transcript; intronic positions are written as offsets from the nearest exon boundary (e.g. c.1585-1G>A).（中文：只对某一条转录本的外显子碱基编号的坐标系；内含子位置写成相对最近外显子边界的偏移。）

EBNF (Extended Backus-Naur Form) — a formal notation for rigorously specifying the syntax of a language; normally used for programming languages, now used for HGVS variant strings.（中文：一种用于严格定义某种语言语法的形式化记法，通常用于编程语言，现在被用于 HGVS 变异字符串。）

Exon / intron — exons are the segments of a gene retained in the mature RNA; introns are the segments spliced out.（中文：外显子是基因中保留在成熟 RNA 里的片段；内含子是被剪接掉的片段。）

Gene fusion — the joining of two or more genes such that a chimeric transcript, or a novel regulatory interaction, is produced; common in cancer.（中文：两个或更多基因连接在一起，产生嵌合转录本或新的调控互作；在肿瘤中常见。）

HGVS Nomenclature — the international standard for describing DNA, RNA, and protein sequence variants in text; e.g. NM_000492.4:c.1521_1523del.（中文：用文字描述 DNA、RNA、蛋白质序列变异的国际标准。）

Length polymorphism — a variant defined by a difference in the number of repeated units (e.g. the CFTR poly-T tract) rather than a base substitution; often awkward to express unambiguously.（中文：由重复单元数目差异定义的变异（如 CFTR 的 poly-T 序列），而非碱基替换；往往难以无歧义地表达。）

MANE Select — Matched Annotation from NCBI and EMBL-EBI: a joint transcript set where NCBI and Ensembl agree on identical exon structure and sequence, matching GRCh38 exactly; defines one representative transcript per protein-coding locus.（中文：NCBI 与 EMBL-EBI 的匹配注释集，两家在外显子结构与序列上完全一致并与 GRCh38 完全吻合；每个蛋白编码位点定义一条代表性转录本。）

Reference sequence — the exact accessioned molecule (e.g. NM_000492.4) a variant description is written relative to; the part of an HGVS string before the colon.（中文：变异描述所相对的那条确切的、带编号的参考分子；HGVS 字符串中冒号之前的部分。）

Semantic versioning — the X.Y.Z (major.minor.patch) version scheme, adopted here so tools can declare which spec version they emit or accept.（中文：X.Y.Z（主.次.修订）版本编号方案，此处被采用，使工具能声明自己产出或接受哪个规范版本。）

Transcript — the RNA copy of a gene; a gene may have several, and different transcripts number bases differently.（中文：基因的 RNA 拷贝；一个基因可能有多条转录本，不同转录本对碱基的编号不同。）

Methods / tools to lift

  • EBNF grammar as a single source of truth — all syntax rules stored in one machine-readable file indexed by molecule type × variant type; every human-facing view (per-molecule pages, cross-cutting Syntax Summary) is generated from it. The generalizable pattern: one grammar file, many rendered views, guaranteed consistency.
  • Semantic versioning with a provider/consumer contract — data providers advertise the spec version they emit; consumers advertise what they accept, and must match the provider's major version with a minor ≥ the provider's. Directly liftable to any harmonization pipeline that emits normalized identifiers.
  • MANE Select as the transcript default — one representative transcript per protein-coding locus, identical between RefSeq and Ensembl, exactly matching GRCh38; removes the transcript-choice ambiguity that silently forks variant tables.
  • The official HGVS software list — curated libraries/APIs that manipulate HGVS expressions (not merely consume them); open-source only, tests and peer-reviewed publication preferred. The starting point for not writing a parser yourself.
  • "Reduce optionality" — the committee's stated goal of eliminating multiple valid representations of the same variant (e.g. one- vs three-letter amino-acid codes). Frames variant-string equality as a specification problem, not a fuzzy-matching problem.

Where it lands + buildable artifact

Priority served: Karen / variant interpretation (CFTR variant-notation harmonization — the genetics-first opening move).

MVP (paste-ready): cftr-hgvs-conformance-harness — a script that takes one column of CFTR variant strings in any form (legacy CF names like 1717-1G>A / 621+1G>T, F508del-style protein shorthand, c. strings on an unstated transcript, one- vs three-letter amino-acid codes) and emits per row: (1) the normalized HGVS expression on the MANE Select CFTR transcript, (2) the HGVS spec version used, (3) a validity flag, and (4) a reason code when normalization fails or yields more than one valid representation. Input: a CSV column of variant strings. Difficulty: M. The deliverable is not the successes — it's the distribution of reason codes: a CFTR-specific "optionality audit" quantifying how much of the CF legacy vocabulary cannot be unambiguously expressed under HGVS 21.1. That is a citable table, and it is explicitly what the HVNC says it wants from compliance-facing collaborators.

What to verify first

  • Which accession is MANE Select for CFTR, and whether CFTR also carries a MANE Plus Clinical transcript. The paper recommends the set; it does not enumerate it. Do not assume the accession.
  • What CFTR2 and ClinVar actually use today. If the community's canonical resources sit on a different transcript than MANE Select, normalizing only to MANE Select silently disconnects you from the databases you most need to join against — the harness may need to emit both and record the mapping.
  • Which HGVS-aware libraries are on the official software list, and which spec version each claims. The versioning contract is worthless unchecked.
  • The CF-specific trap: length polymorphisms. The poly-T / TG tracts are repeat-length variants, not substitutions; legacy CF notation for them may have no single unambiguous HGVS form. These rows are the scientifically interesting ones and should be hand-checked before any tool is trusted on them.
  • The grammar is not yet strictly valid. The authors state the spec "is not easily represented as a strictly valid grammar" and that this release adopts EBNF syntax "without attempting to reconcile missing or ambiguous elements." Conformance tests are listed as future work. Ambiguity was made legible, not removed — build accordingly.

ALEX Today's paper is "HGVS Nomenclature 2024: improvements to community engagement, usability, and computability," by Reece Hart, Ivo Fokkema, Marina DiStefano, Ros Hastings, Jeroen Laros, Rachel Taylor, Alex Wagner, and Johan den Dunnen, published in Genome Medicine in December 2024. 今天这篇论文是《HGVS 命名法 2024：在社区参与、可用性与可计算性方面的改进》，作者是 Reece Hart、Ivo Fokkema、Marina DiStefano、Ros Hastings、Jeroen Laros、Rachel Taylor、Alex Wagner 和 Johan den Dunnen，2024 年 12 月发表于《Genome Medicine》。 This is Track A — variant interpretation and harmonization. 这属于 Track A——变异解读与命名统一。 We're reading it because it is the specification document for the exact thing the Karen Raraigh collaboration would be built on: how a CFTR variant is *written down*. 我们读它，是因为它正是 Karen Raraigh 合作可能建立其上的那个东西的规范文件：一个 CFTR 变异到底该*怎么写*。 And it is fully open access, so everything we say today is from the full text. 而且它是完全开放获取的，所以我们今天说的每一句都来自全文。

JORDAN Start me at zero. 从零开始给我讲。 What is HGVS, actually? HGVS 到底是什么？

ALEX HGVS stands for the Human Genome Variation Society, and "HGVS Nomenclature" is the global standard for *writing down* a genetic variant in text. HGVS 是人类基因组变异协会 (Human Genome Variation Society) 的缩写，而 "HGVS Nomenclature"（HGVS 命名法）是把一个遗传变异用文字*写下来*的全球标准。 Something like `NM_000492.4:c.1521_1523del` is an HGVS expression. 像 `NM_000492.4:c.1521_1523del` 这样的字符串就是一个 HGVS 表达式。 Read it left to right: the accession before the colon names the **reference sequence** — the exact molecule you are describing the variant relative to. 从左往右读：冒号前的编号指明**参考序列** (reference sequence)——也就是你相对于哪一条确切的分子在描述这个变异。 Then a single letter says which *coordinate system* you're in: `g.` for genomic, `c.` for coding DNA, `r.` for RNA, `p.` for protein. 接着一个字母说明你用的是哪一套*坐标系*：`g.` 表示基因组坐标，`c.` 表示编码 DNA 坐标，`r.` 表示 RNA，`p.` 表示蛋白质。 The rest is the position and the change. 剩下的部分是位置和改变本身。

JORDAN Why does the reference sequence matter so much? 为什么参考序列这么关键？

ALEX Because a **transcript** — the RNA copy of a gene that gets made into protein — can have several versions, and they don't all number the bases the same way. 因为**转录本** (transcript)——也就是基因被抄写成、并最终翻译为蛋白质的那条 RNA——可能存在好几个版本，而它们对碱基的编号方式并不一致。 A gene is made of **exons**, the pieces kept in the final RNA, and **introns**, the pieces spliced out. 一个基因由**外显子** (exon)——最终保留在 RNA 里的片段——和**内含子** (intron)——被剪接掉的片段——组成。 In `c.` coordinates you count only the exonic bases, and intronic positions are written as an offset from the nearest exon boundary, like `c.1585-1G>A`. 在 `c.` 坐标系里你只数外显子上的碱基，内含子里的位置则写成相对于最近外显子边界的偏移，例如 `c.1585-1G>A`。 So if two labs pick different transcripts, the *same* physical variant gets two different numbers. 所以如果两个实验室选了不同的转录本，*同一个*物理变异会得到两个不同的编号。 That is not a typo problem. 这不是一个笔误问题。 That is two databases that can never be joined. 这是两个永远无法连接的数据库。

JORDAN And CF has a whole legacy naming culture on top of that. 而囊性纤维化 (CF) 领域在这之上还有一整套遗留命名文化。

ALEX It does, and that's exactly why this paper matters to us. 确实如此，这也正是这篇论文对我们重要的原因。 The CF community grew up with names like F508del and legacy strings like `1717-1G>A` and `621+1G>T`, which come from an older numbering convention. CF 社区是伴随着 F508del 这样的名字、以及 `1717-1G>A`、`621+1G>T` 这类遗留字符串长大的，它们来自一套更旧的编号约定。 Those names are still in charts, in registries, in papers, and in people's heads. 这些名字至今仍存在于病历、登记库、论文和人们的脑子里。 They are not HGVS. 它们不是 HGVS。 The gap between "what CF clinicians write" and "what a variant-effect predictor will accept as input" is a real, unglamorous, load-bearing engineering problem. “CF 临床医生写下的东西”与“变异效应预测工具愿意接受的输入”之间的落差，是一个真实的、不光鲜的、却承重的工程问题。

JORDAN OK, so what problem did the authors set out to fix? 好，那作者们想解决什么问题？

ALEX Two, really, and they're tangled together. 其实是两个，而且它们纠缠在一起。 The first is governance and maintenance. 第一个是治理与维护。 HGVS Nomenclature was created in 1996, when sequencing was low-throughput and largely manual, and the recommendations were written for *human* readers. HGVS 命名法诞生于 1996 年，当时测序还是低通量、基本靠手工，相关建议是为*人类*读者写的。 The paper is blunt about what maintenance used to look like: community questions went to a Facebook group, or to a single email address that only the committee chair could read. 论文对过去的维护方式说得毫不客气：社区提问要发到一个 Facebook 群组，或者发到一个只有委员会主席能看到的邮箱地址。 That is a standard the entire clinical genomics world depends on, run out of one person's inbox. 一个全世界临床基因组学都依赖的标准，却运行在一个人的收件箱里。

JORDAN That's genuinely alarming when you say it out loud. 这话说出来是真的让人心惊。

ALEX The second problem is deeper, and it's the one worth your attention. 第二个问题更深，也是值得你关注的那个。 The standard was an *informal* grammar — prose recommendations with worked examples. 这套标准过去是一份*非正式*的语法——是带例子的散文式建议。 Prose is fine when a human reads a variant off a report. 当一个人从报告上读出一个变异时，散文是够用的。 It is not fine when a pipeline has to decide, automatically, whether `NM_000492.4:c.1521_1523delCTT` and `NM_000492.4:c.1521_1523del` are the same thing. 但当一条流水线必须*自动*判断 `NM_000492.4:c.1521_1523delCTT` 和 `NM_000492.4:c.1521_1523del` 是不是同一个东西时，散文就不够用了。 The authors note that some variants have multiple *valid* representations — protein variants can use one-letter or three-letter amino-acid codes, for instance — so exact string matching is often simply wrong. 作者指出，有些变异存在多种*都合法*的写法——比如蛋白质变异既可以用单字母也可以用三字母氨基酸代码——所以精确字符串匹配常常直接就是错的。 Every one of us who has ever tried to join two variant tables on the variant string has felt this. 我们每一个曾经试图用变异字符串去连接两张变异表的人，都体会过这一点。

JORDAN So what did they actually change? 那他们究竟改了什么？

ALEX Governance first. 先说治理。 The standard now lives under HUGO — the Human Genome Organization — maintained by a formal committee, the HGVS Variant Nomenclature Committee, eleven members from academia, industry, and national institutions, four-year terms, meeting about six times a year. 这套标准现在归属于 HUGO——人类基因组组织——由一个正式的委员会 HGVS Variant Nomenclature Committee 维护，十一名成员来自学术界、企业和国家机构，任期四年，每年约开六次会。 The Facebook group is dead; there are now two public Google Groups, one for announcements and one for discussion, both publicly archived, and the discussion list is fielding roughly three questions a week. Facebook 群组已经废止；现在有两个公开的 Google Groups，一个发公告，一个做讨论，二者的记录都公开存档，讨论组每周大约处理三个问题。 Change proposals go through GitHub as pull requests. 修改提案通过 GitHub 以 pull request 的形式提交。

JORDAN They turned a standards body into a software repo. 他们把一个标准组织变成了一个软件仓库。

ALEX Exactly, and they went all the way. 正是如此，而且他们做到底了。 The spec now uses **semantic versioning** — X.Y.Z, major-minor-patch — with an explicit compatibility contract. 规范现在采用**语义化版本控制** (semantic versioning)——X.Y.Z，即主版本-次版本-修订号——并附带一份明确的兼容性契约。 Data *providers* — tools or databases that emit HGVS strings — should advertise which version they use. 数据*提供方*——也就是产出 HGVS 字符串的工具或数据库——应当声明自己用的是哪个版本。 Data *consumers* — anything that accepts HGVS as input — should advertise which versions they accept, and should match the provider's major version with a minor version greater than or equal to it. 数据*消费方*——任何接受 HGVS 作为输入的东西——应当声明自己接受哪些版本，并且主版本要与提供方一致、次版本要大于或等于对方。 That is a real interoperability contract, borrowed wholesale from software engineering. 这是一份真正的互操作性契约，整套照搬自软件工程。

JORDAN And the grammar? 那语法呢？

ALEX This is the headline. 这是重头戏。 The syntax is now defined in **EBNF** — Extended Backus-Naur Form, a formal notation for specifying the exact structure of a language. 语法现在用 **EBNF**（扩展巴科斯范式，一种用来精确定义某种语言结构的形式化记法）来定义。 It is what you'd use to specify a programming language, and now it specifies variant strings. 你会用它来定义一门编程语言，现在它被用来定义变异字符串。 All the grammar rules live in a single machine-readable file, indexed by molecule type (DNA, RNA, protein) and variant type (substitution, deletion, and so on), and every view on the website — the per-molecule pages and the new cross-cutting Syntax Summary — is *generated* from that one file. 所有语法规则都存放在一个机器可读的文件里，按分子类型（DNA、RNA、蛋白质）和变异类型（替换、缺失等）建立索引，网站上的每一种视图——按分子分的页面和新的跨类型 Syntax Summary——都是从这一个文件*生成*出来的。 Single source of truth. 单一事实来源。 The site itself is Markdown, rendered with MkDocs, deployed on Read the Docs, source on GitHub under MIT and CC0. 网站本身是 Markdown 写的，用 MkDocs 渲染，部署在 Read the Docs 上，源码在 GitHub，采用 MIT 和 CC0 许可。

JORDAN Push back on something for me. 帮我挑一个刺。

ALEX Happily, and the authors hand me the knife themselves. 乐意之至，而且这把刀是作者自己递给我的。 They state plainly that the current HGVS Nomenclature "is not easily represented as a strictly valid grammar," and that this release adopts EBNF *syntax* "without attempting to reconcile missing or ambiguous elements of the previous release." 他们坦白地写道，当前的 HGVS 命名法“并不容易被表示为一个严格合法的语法”，而这一版只是采用了 EBNF 的*写法*，“并未试图去调和上一版中缺失或歧义的部分”。 So: it *looks* like a formal grammar, and it is a huge improvement in clarity, but it is not yet a grammar you can hand to a parser generator and get a conformant parser out of. 所以：它*看起来*像一个形式语法，可读性上是巨大进步，但它还不是那种你能直接丢给 parser generator、就吐出一个合规解析器的语法。 The conformance tests that would settle the question are explicitly listed as *future work*. 那些能一锤定音的一致性测试 (conformance tests) 被明确列为*未来工作*。 The ambiguity was not removed; it was *rendered legible*. 歧义并没有被消除；它只是被*渲染得可读了*。 That's still worth a lot — you can now see the ambiguity — but don't confuse the map for the territory. 这依然很有价值——你现在能*看见*歧义了——但别把地图当成地形。

JORDAN What are the substantive spec changes, as opposed to process changes? 除了流程上的变化，规范本身有哪些实质改动？

ALEX Two. 两个。 First, gene fusions. 第一，基因融合。 A **gene fusion** is when two genes get joined so that a single chimeric transcript is produced — common in cancer. **基因融合** (gene fusion) 是指两个基因被接在一起，从而产生一条嵌合转录本 (chimeric transcript)——在肿瘤中很常见。 HGVS now represents the resulting **adjoined transcript** with a double colon, like `NM_002354.2:r.−358_555::NM_000251.2:r.212_*279`, and has aligned its terminology with the Variant Interpretation for Cancer Consortium. HGVS 现在用双冒号来表示由此产生的**相邻转录本** (adjoined transcript)，写作 `NM_002354.2:r.−358_555::NM_000251.2:r.212_*279`，并且把术语与 Variant Interpretation for Cancer Consortium 对齐了。 The older terms "RNA Fusion" and "Fusion Transcript" are deprecated. 旧术语 "RNA Fusion" 和 "Fusion Transcript" 已被废弃。 That one is mostly a cancer-genomics concern, not a CF one. 这一条主要是肿瘤基因组学的关切，与 CF 关系不大。

JORDAN And the second? 第二个呢？

ALEX The second is the one that matters enormously to us: **transcript selection**. 第二个对我们极其重要：**转录本的选择**。 Historically HGVS said "use the longest transcript that represents the known biological and clinical significance of the locus," which is advice, not an algorithm. HGVS 过去的说法是“使用能代表该位点已知生物学和临床意义的最长转录本”，这是建议，不是算法。 It also collides with reality: RefSeq and Ensembl transcripts differ from each other, and both can differ from the primary genome assembly. 它还和现实相冲突：RefSeq 和 Ensembl 的转录本彼此不同，而且两者都可能与主要基因组组装序列不同。 The new recommendation is to use **MANE Select** — Matched Annotation from NCBI and EMBL-EBI — a joint transcript set where NCBI and Ensembl agree on identical exon structure and sequence, and where the transcript sequence matches the GRCh38 reference assembly exactly. 新的建议是使用 **MANE Select**（NCBI 与 EMBL-EBI 的匹配注释集）——这是一个联合转录本集合，NCBI 和 Ensembl 在其中就完全相同的外显子结构和序列达成一致，并且转录本序列与 GRCh38 参考组装序列完全吻合。 MANE Select defines *one* transcript per protein-coding locus. MANE Select 为每个蛋白编码位点只定义*一条*转录本。 The old recommendation to use Locus Reference Genomic sequences is withdrawn. 旧的、建议使用 Locus Reference Genomic 序列的说法被撤回了。

JORDAN So "which transcript" finally has a default answer. 所以“该用哪条转录本”终于有了默认答案。

ALEX For protein-coding genes, yes — and CFTR is a protein-coding gene. 对蛋白编码基因来说，是的——而 CFTR 就是蛋白编码基因。 That single sentence is the whole reason this paper is buildable rather than merely interesting. 就这一句话，让这篇论文从“有意思”变成了“可以动手做”。

JORDAN So where does it land? 那它落在哪个方向？

ALEX Squarely on **Karen / variant interpretation**. 稳稳落在 **Karen / 变异解读**这条线上。 Remember what the opening move there was: CFTR variant-notation harmonization. 记得那条线最初的切入点是什么：CFTR 变异命名的统一。 This paper tells you what the target of that harmonization is, precisely, as of version 21.1: HGVS on the MANE Select transcript, with a version tag attached. 这篇论文精确地告诉你，截至 21.1 版，统一的*目标*是什么：基于 MANE Select 转录本的 HGVS，并附上版本标签。 So the buildable artifact is a **cftr-hgvs-conformance-harness**. 所以可动手的产物是一个 **cftr-hgvs-conformance-harness**（CFTR HGVS 一致性检验工具）。 MVP: take one column of CFTR variant strings in whatever form they arrive — legacy CF names, `c.` strings on an unstated transcript, protein-only names, three-letter and one-letter amino-acid codes — and emit, per row, four things: the normalized HGVS expression on the MANE Select CFTR transcript, the HGVS version used, a validity flag, and a *reason code* when normalization fails or is ambiguous.
