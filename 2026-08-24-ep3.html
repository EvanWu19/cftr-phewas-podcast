Blurb

This 2023 conference paper from Germany's CORD-MI rare-disease EHR network asks a question distinct from most data-quality work: does the ETL (Extract-Transform-Load) pipeline itself change data quality, separate from whatever quality issues already existed in the source data? Comparing the same ~79,810 inpatient cases before (SAP export) and after (FHIR-standardized) ETL, the authors found a mixed picture -- the pipeline actively deduplicated records (uniqueness improved to its maximum), but also lost nearly all Orphacode-based rare-disease identification and introduced completeness gaps traced to specific FHIR mapping errors. Range plausibility, notably, was untouched by the transformation. The paper doesn't supply a candidate-generation rule or an adjudication technique for CFFPR's outlier work -- it supplies a framework and a caution (pipeline stage (e)): that auditing a transformation step by comparing pre/post versions of the same records is a distinct, useful check, separate from flagging implausible values within an already-processed dataset. Buildable artifact: a lightweight pre/post-transformation comparator computing the same completeness/plausibility/uniqueness indicators on two pipeline-stage snapshots and diffing them.

Plain-English glossary

  • ETL (Extract-Transform-Load) -- the process of extracting records from a source system, transforming them into a shared standard, and loading them into a pooled data resource.（中文：从源系统提取记录、转换为统一标准、再加载进汇集数据资源库的流程。）
  • HL7 FHIR -- Fast Healthcare Interoperability Resources, a widely used standardized format for representing clinical data for exchange between systems.（中文：一种广泛使用的标准化临床数据交换格式。）
  • Orphacode -- a rare-disease-specific coding system maintained by Orphanet, offering finer-grained disease identification than general ICD-10 codes typically allow.（中文：由Orphanet维护的罕见病专用编码体系，比一般ICD-10编码提供更精细的疾病识别。）
  • completeness / plausibility / uniqueness (DQ dimensions) -- a data-quality framework: completeness asks whether required fields are populated; plausibility asks whether populated values fall in an expected range; uniqueness asks whether a real-world case is represented once rather than duplicated. Related to the Kahn and Weiskopf-and-Weng EHR data-quality frameworks.（中文：数据质量框架的三个维度——完整性问字段是否被填写；合理性问数值是否落在预期范围；唯一性问同一病例是否被重复记录。与Kahn及Weiskopf-and-Weng的EHR数据质量框架相关。）
  • MII core data set (MII-CDS) -- a shared schema, from Germany's Medical Informatics Initiative, defining which fields and codes every participating hospital's data must include.（中文：德国医学信息学倡议制定的共享数据模式，规定各参与医院数据必须包含的字段和编码。）

Methods / tools to lift

  • Pre/post-transformation DQ comparison design -- computing the same quality indicators on two versions of the same underlying records (before and after a pipeline stage) to isolate pipeline-introduced quality changes from source-data quality issues.
  • dqLib (R package) -- a configurable data-quality reporting tool the same group developed, generating both a metrics report and a detected-issues report per dataset.
  • Seven-indicator DQ decomposition -- breaking three abstract DQ dimensions (completeness, plausibility, uniqueness) into concrete, computable indicators (item completeness rate, value completeness rate, Orphacoding completeness rate, etc.).

Where it lands + buildable artifact

Pipeline stage: (e) nothing directly, but supplies vocabulary/framework -- the idea that a transformation step itself can be an independent source of data-quality change, distinct from data-entry error. Buildable artifact: a lightweight pre/post-transformation comparator -- given two versions of the same records at different pipeline stages, compute the same completeness/plausibility/uniqueness-style indicators on each and diff them, surfacing which stage a quality change entered at. Difficulty: S.

What to verify first

  • Single hospital, single year, one specific ETL implementation -- whether the "fixes duplicates but degrades some completeness" pattern generalizes at all is unknown.
  • DQ indicators were validated by the study team checking for internal contradictions, not against an independent gold-standard chart review.
  • Whether a comparable "before transformation" snapshot is available or constructible for any CFFPR data field is an open question this paper cannot answer.

Pipeline stage

(e) Framework/vocabulary only -- no direct candidate-generation, adjudication, review-budget, or evaluation contribution.

Error types covered / not covered

Covered: completeness loss (missing/dropped fields, e.g. Orphacodes), semantic/mapping errors introduced during transformation, duplicate records (via the uniqueness/dissimilarity indicator). Not covered: value-level implausibility introduced by transformation (range plausibility was unaffected in this study), unit conversion errors, digit transposition, decimal shift, carry-forward errors, or distinguishing real clinical events from data errors.
