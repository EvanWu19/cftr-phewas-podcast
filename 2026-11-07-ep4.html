Ep4 — Developing a Systematic Approach to Assessing Data Quality in Secondary Use of Clinical Data Based on Intended Use

Track C — Registry & EHR Data Quality (2 of 2 today)

Blurb

Razzaghi, Greenberg, and Bailey (Learning Health Systems, 2022) tackle a gap that every registry team eventually hits: structural data-quality programs like PCORnet's 314 checks and PEDSnet's 800+ checks tell you whether fields exist and are populated correctly, but not whether the values actually mean what they're supposed to mean clinically. The paper proposes a four-part sequence — Clinical Data Factors, Analytic Uses, DQ Principles, DQ Methods/Practice — derived from an inductive thematic analysis of 160 full-text papers, and illustrates it with a hypertension provenance example and two worked case studies. It's a conceptual/process contribution with no algorithm and no quantitative validation. For CFFPR, the primary value is vocabulary and scoping discipline rather than a new method — concretely, a lightweight four-part scoping worksheet to run before specifying any new anthropometric check.

Plain-English Glossary

  • Analytic Uses — the framework step that scopes how much DQ scrutiny a variable deserves based on its role in the analysis (e.g., primary outcome vs. minor covariate).（中文：框架中的一步,根据变量在分析中的角色——比如主要结局变量还是次要协变量——来判断该给它多少数据质量审查。）
  • Clinical Data Factors — the framework step that ties a clinical concept to its data provenance, recognizing that the same concept (e.g., hypertension) can be captured via diagnosis codes, medications, or vital signs, each with different failure modes.（中文:框架中的一步,把临床概念和它的数据来源联系起来,同一个概念可能通过诊断编码、用药或生命体征等不同途径被记录,各有不同的出错方式。）
  • Completeness (Kahn framework) — whether data that should be present in a record actually are.（中文:Kahn框架术语,指应该存在的数据是否真的存在,即完整性。）
  • Concordance — agreement between different data sources or domains (e.g., labs, vitals, diagnoses, medications) on the same clinical fact.（中文:不同数据来源或领域对同一临床事实的一致程度,即符合度。）
  • Conformance (Kahn framework) — whether data match an expected format, structure, or type.（中文:Kahn框架术语,指数据是否符合预期的格式、结构或类型,即规范性。）
  • DQ (Data Quality) — the general term for how fit data are for a given use.（中文:数据质量的缩写,指数据对某种用途的适用程度。）
  • DQ Methods/Practice — the framework step describing the concrete, implementable check (a threshold rule, a clustering approach, etc.).（中文:框架中的一步,指实际落地实施的具体检查方法,比如阈值规则或聚类方法。）
  • DQ Principles — the framework step where general DQ concepts (outlier detection, completeness, concordance, plausible distributions) are operationalized for a specific variable.（中文:框架中的一步,把通用的数据质量概念——如异常值检测、完整性、符合度、合理分布——落实到具体变量上。）
  • EHR (Electronic Health Record) — the digital clinical record system from which secondary-use research data is often extracted.（中文:电子健康记录,许多二次利用研究数据的来源系统。）
  • Plausibility (Kahn framework) — whether values make clinical or biological sense given real-world knowledge, independent of whether they are complete or correctly formatted.（中文:Kahn框架术语,指数值是否符合临床或生物学常理,即合理性,与数据是否完整或格式正确无关。）
  • Semantic data quality — whether data align with clinical reality and meaning, not just expected format.（中文:指数据是否符合临床现实和意义,而不只是格式上的正确,即语义数据质量。）
  • Structural data quality — whether data conform to expected format, structure, and type.（中文:指数据是否符合预期的格式、结构和类型,即结构性数据质量。）
  • Validation (Kahn axis) — checking data against something external to the dataset (e.g., CDC growth charts).（中文:Kahn框架中的一条轴线,指拿数据去对照数据集外部的参照标准,即验证。）
  • Verification (Kahn axis) — checking data against its own internal rules (e.g., a BMI field matching height and weight in the same record).（中文:Kahn框架中的一条轴线,指拿数据去对照其自身内部规则,即核实。）
  • Weiskopf & Weng 3x3 model — a DQ assessment model organized around three constructs: time, variables, and patients, used to scope which checks matter for a given question.（中文:一种数据质量评估模型,围绕时间、变量、患者三个维度组织,用来界定在特定问题下哪些检查才重要。）

Methods/Tools to Lift

  • Kahn conformance/completeness/plausibility taxonomy, crossed with the verification-vs-validation axes, as a shared vocabulary for describing any DQ issue.
  • Weiskopf & Weng's time/variables/patients 3x3 model as a lens for scoping which checks matter for a given analytic question.
  • The structural-vs-semantic DQ distinction as a one-line way to classify whether an existing check program (e.g., a registry's existing QC) is checking format or checking clinical meaning.
  • The four-part scoping sequence — Clinical Data Factors → Analytic Uses → DQ Principles → DQ Methods/Practice — as a lightweight pre-build exercise for any new check.
  • The hypertension provenance example as a template for thinking through "which source captures this concept, and what are that source's failure modes" before building a check on any clinical concept with multiple possible data sources.

Where It Lands + Buildable Artifact

Primary: (e) nothing directly, but supplies vocabulary/framework worth borrowing. This paper has no algorithm, no detection method, no substrate model, and no performance numbers — it cannot serve as a candidate generator, inform adjudication logic, set a human-review budget, or function as an evaluation method. What it supplies is the Kahn/Weiskopf vocabulary and the four-part structuring discipline, which is useful for scoping which height/weight checks matter and why (its own outlier-detection example explicitly names height/weight measurement and mechanical errors).

Weak secondary link to (a) candidate generator: running a proposed anthropometric check through the Analytic-Use/DQ-Principle questions before building it could sharpen which checks get prioritized — a one-step-removed, non-primary connection.

Buildable artifact: a one-page internal worksheet implementing the four-part framework (Clinical Data Factor → Analytic Use → DQ Principle → DQ Method) as a scoping exercise to run before specifying a new anthropometric check. Input: the candidate variable and its clinical context (e.g., "weight at encounter for a pediatric CF patient"). Output: a one-paragraph justification for what to build and why. Difficulty: S (template, not code).

What to Verify First

  • Whether walking through the four-part structure actually changes which checks get built, versus documenting intuitions a good analyst already applies.
  • Whether the inductive thematic-analysis methodology (no predefined framework tested, no inter-rater reliability reported) missed categories a different research team or literature sample would have surfaced.
  • How this framework would interact with more recent OMOP/common-data-model-based DQ tooling, given the paper predates much of that ecosystem's maturation.
  • Whether "intended use" scoping as a design philosophy has, in practice, led anyone to under-check a field that looked fine for one study and caused problems for a later one.
  • None of the above is a claim about CFFPR's actual current DQ process or Liz's team's methods — explicitly unknown to this podcast and worth checking, not assuming.

Pipeline Stage

Error Types Covered / Not Covered

This paper names height/weight measurement and mechanical errors as its canonical outlier-detection example, but it provides no specific detection method and no error taxonomy — no breakdown of unit-conversion errors, digit-transposition errors, decimal-shift errors, or carry-forward errors. It is framework-level (what kinds of checks are worth building and why), not detector-level (how to actually catch a specific error pattern).
