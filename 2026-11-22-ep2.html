CUI-Curate: a GraphRAG-based framework for automated clinical concept curation for NLP applications

Blake V, Novak J, Miller M, Ooi SY, Gallego B. Journal of the American Medical Informatics Association 2026. CUI-Curate automates one of the most labor-intensive, under-tooled steps in clinical NLP and phenotyping: building a "concept set" — the full list of UMLS Concept Unique Identifiers (CUIs) that together represent one clinically meaningful idea, like chronic heart failure or poor mobility. The framework builds a knowledge graph straight from UMLS's release files (SNOMED CT, NCI Thesaurus, MeSH), retrieves a focused candidate pool via embedding similarity plus one-hop graph expansion (a GraphRAG pattern), then runs a two-stage LLM workflow (filter, then classify as definitive vs. context-dependent) to curate it — comparing GPT-5 against a locally hosted, 4-bit-quantized Qwen3-32B. Across five test concepts, GPT-5 preserved at least 95% of definitive gold-standard CUIs and beat manual UMLS-browser curation on every concept, at a fraction of the cost (about $0.88 and 21 minutes per concept vs. 1–2 hours of clinician time). Ships as an installable, open-source Python package on GitHub. Lands on the AI-tooling/career track — buildable artifact: a scoped-down "Mini Concept-Set Curator" that applies the same recipe (targeted graph retrieval + two-stage LLM filter/classify) to a single CF-relevant phenotype, as a portfolio demonstration of the graph-plus-LLM skill combination this paper showcases.

Plain-English glossary

  • Concept Unique Identifier (CUI) — A single unique ID for a biomedical concept in the UMLS.（中文：UMLS中某个生物医学概念对应的唯一标识符。）
  • Concept set / value set — A curated list of all the CUIs (synonyms, subtypes, related terms) that together represent one clinically meaningful idea.（中文：由多个CUI——同义词、子类型、相关术语——组成的清单，共同代表一个有临床意义的概念，也叫value set。）
  • FAISS — An open-source library for fast similarity search over vector embeddings, used here to index UMLS node embeddings for retrieval.（中文：一个开源的向量相似度检索库，这里用于对UMLS节点嵌入建立索引以支持检索。）
  • GraphRAG — A retrieval-augmented-generation approach that retrieves from a graph's nodes and edges, rather than a flat document collection, before an LLM reasons over the results.（中文：一种检索增强生成方法，在大语言模型进行推理之前，从图的节点和边中检索信息，而不是从扁平的文档集合中检索。）
  • MIMIC-III — A publicly available, de-identified dataset of US intensive-care-unit clinical notes, commonly used as a benchmark corpus in clinical NLP.（中文：一个公开的、去标识化的美国重症监护病房临床记录数据集，常用作临床自然语言处理的基准语料库。）
  • OHDSI Athena — The existing standard platform for building concept sets from structured, coded clinical vocabularies; built for coded data, not free-text CUIs.（中文：目前构建概念集合的标准平台，面向结构化编码临床词表，而非自由文本中的CUI。）
  • Pooled relevance assessment — An information-retrieval evaluation method that unions the results of multiple retrieval methods into one pool for human adjudication, used here (as in TREC search benchmarks) to build a gold-standard concept set without exhaustively reviewing all of UMLS.（中文：一种信息检索评测方法，将多种检索方法的结果合并成一个池子供人工裁定，这里借用这一方法——如同TREC搜索基准——在不必穷尽审查整个UMLS的情况下构建金标准概念集合。）
  • QuickUMLS — A fast, open-source, string-matching tool for tagging UMLS concepts in free text.（中文：一个快速的、开源的、基于字符串匹配的工具，用于在自由文本中标记UMLS概念。）
  • SNOMED CT — A large, hierarchically structured clinical terminology and one of UMLS's primary source vocabularies.（中文：一个庞大的、层级结构化的临床术语体系，是UMLS的主要来源词表之一。）
  • Unified Medical Language System (UMLS) — A US National Library of Medicine resource integrating over four million biomedical concepts from 180+ source vocabularies.（中文：美国国家医学图书馆的一个资源库，整合了来自180多个来源词表的四百多万个生物医学概念。）

Methods / tools to lift

  • GraphRAG over UMLS — knowledge graph built directly from UMLS RRF release files (MRCONSO, MRREL, MRDEF, MRSTY), embedded for semantic retrieval.
  • Two-stage LLM curation — a filter pass (retain concepts indicating the target phenotype), then a classification pass (definitive vs. context-dependent), run with GPT-5 and compared against a locally hosted Qwen3-32B.
  • Pooled relevance assessment — a TREC-style gold-standard construction method applicable whenever exhaustive review of a large reference space is infeasible.
  • Clinical-text observability check (QuickUMLS + MIMIC-III) — a pragmatic sanity check on whether a "missed" concept actually matters in real text.
  • Code repository: github.com/vickyblake/CUICurate

Where it lands + buildable artifact

Lands on AI-tooling / career (ships code; no claim made about CFFPR's own data structures). Buildable artifact: Mini Concept-Set Curator — pull a targeted UMLS subgraph for one CF-relevant phenotype (e.g., pancreatic insufficiency or CF-related diabetes) via the UMLS API, embed and retrieve candidates with one off-the-shelf model plus one-hop expansion, then run a two-stage LLM filter/classify pass (API or local open-source model) to produce a clinician-reviewable concept set. Difficulty: S–M.

What to verify first

  • Recall varied widely by concept type in the source paper — clean, well-bounded diagnoses retrieved far better than diffuse, multi-descriptor phenotypes; check which kind a target CF phenotype resembles before assuming the method transfers smoothly.
  • The paper's own gold-standard sets carry real inter-rater disagreement (Cohen's κ as low as 0.35 for the broadest concepts) — any replica's "accuracy" is only as good as its own reference standard.
  • The clinical-text observability check used a single, ICU-focused US corpus (MIMIC-III); whether the same missed-concepts-are-mostly-rare pattern holds in a different clinical text source is untested here.
  • No claim made about what form CFFPR's own free-text or coded fields actually take — that remains a separate, registry-side question.

JORDAN No genes, no variants — why's this on the show? 没有基因，也没有变异——这篇为什么会上节目？

ALEX Because it's Track B, ships real code on GitHub, and it's a clean example of fusing a knowledge graph with an LLM to automate a curation task that's normally pure clinician hours — exactly the kind of tool-building muscle the career track wants you building. 因为这是B线，它在GitHub上发布了真实可用的代码，而且干净地展示了如何把知识图谱和大语言模型结合起来，自动化一项通常需要临床医生大量人工投入的整理工作——这正是职业发展这条线想让你练出来的那种工具构建能力。

JORDAN Let's get the vocabulary straight first — what's a CUI? 先把词汇搞清楚——什么是CUI？

ALEX Concept Unique Identifier — a single ID from the UMLS（统一医学语言系统，Unified Medical Language System）, a US National Library of Medicine resource with over four million biomedical concepts pulled from more than 180 source vocabularies. 概念唯一标识符——是来自UMLS的一个单一ID，UMLS是美国国家医学图书馆的一个资源库，汇集了四百多万个生物医学概念，来源于一百八十多个词表。

JORDAN And why isn't one CUI enough? 为什么一个CUI不够用？

ALEX Because clinical ideas are messy — "heart failure" in a chart might show up as chronic heart failure, congestive heart failure, or left-sided heart failure, each with its own CUI; a concept set（概念集合，also called a value set）is the curated list of all the CUIs that together represent one clinically meaningful idea. 因为临床概念本身就很混乱——病历里的"心力衰竭"可能表现为慢性心力衰竭、充血性心力衰竭或左心衰竭，每一种都有自己的CUI；而概念集合——也叫value set——就是把共同代表同一个临床含义的所有CUI整理成的一份清单。

JORDAN And SNOMED CT, that keeps coming up — what is it? SNOMED CT也一直出现——那是什么？

ALEX SNOMED CT is one of UMLS's largest source vocabularies — a structured clinical terminology with hierarchical parent-child relationships between concepts; MeSH and the NCI Thesaurus, the other two vocabularies this paper uses, are similarly structured but built for different purposes, literature indexing and cancer terminology respectively. SNOMED CT是UMLS里最大的来源词表之一——一种结构化的临床术语体系，概念之间有层级化的父子关系；MeSH和NCI Thesaurus是这篇论文用到的另外两个词表，结构类似但用途不同，分别是用于文献索引和癌症术语。

JORDAN Where does OHDSI's Athena tool fit in? OHDSI的Athena工具在这里是什么角色？

ALEX Athena is the existing standard tool for building concept sets — but it's built for structured, coded data, not free-text CUIs, and it still relies heavily on a human doing the curating; that gap is exactly what this paper is trying to close. Athena是目前构建概念集合的标准工具——但它是为结构化编码数据设计的，不是为自由文本中的CUI设计的，而且仍然严重依赖人工整理；而这篇论文想要填补的，正是这个缺口。

JORDAN So what was broken before CUI-Curate — why couldn't people just use Athena or a hierarchy search? 那在CUI-Curate出现之前，问题到底出在哪——为什么不能直接用Athena或者层级检索来解决？

ALEX Because hierarchy alone misses too much — relevant variants of a concept can sit outside a single parent-child branch entirely, while a broader parent concept can drag in clinically inappropriate terms; the paper shows this concretely, with CUIs relevant to one clinical idea scattered across the UMLS graph in ways a pure hierarchy walk won't catch. 因为单靠层级关系会漏掉太多东西——一个概念的相关变体完全可能落在某个父子分支之外，而更宽泛的父概念又可能把临床上不合适的术语一并带进来；论文用具体例子展示了这一点，同一个临床概念相关的CUI分散在UMLS图谱的各个角落，单纯沿着层级走是抓不全的。

ALEX Manual curation, meanwhile, is genuinely slow — the paper reports one to two hours of clinician time per concept just using the UMLS Metathesaurus Browser（UMLS元词表浏览器，一个用于人工浏览CUI的界面）, and even then the resulting lists are small and incomplete. 而人工整理确实很慢——论文报告说，光是用UMLS元词表浏览器，每个概念就需要一到两个小时的临床医生工作时间，而且做出来的清单往往还不完整。

JORDAN Why not just throw the whole UMLS at an LLM and ask it to figure out the concept set? 为什么不直接把整个UMLS扔给大语言模型，让它自己去找出概念集合？

ALEX Scale and noise — the UMLS is enormous, and feeding a model that much irrelevant context is both expensive and a good way to get unreliable answers; what you actually want is a small, clinically relevant candidate pool first, then let the model reason over that pool, which is exactly the retrieval-augmented-generation playbook you already know, just applied to a graph instead of a flat document index. 规模和噪声是问题——UMLS体量巨大，把这么多不相关的上下文喂给模型，既昂贵又容易得到不可靠的答案；真正需要的是先拿到一个小而临床相关的候选池，再让模型在这个池子里做推理，这其实就是你已经熟悉的检索增强生成（RAG）思路，只不过这里作用的对象是图结构，而不是扁平的文档索引。

ALEX That graph-flavored version is called GraphRAG — retrieval over a graph's nodes and edges rather than a document collection — and the UMLS, being inherently graph-structured with explicit relationships between concepts, is close to an ideal substrate for it. 这种图结构版本叫GraphRAG——在图的节点和边上做检索，而不是在文档集合上做检索——而UMLS本身天生就是图结构，概念之间有明确的关系，几乎是GraphRAG的理想应用场景。

JORDAN Walk me through the actual architecture. 带我过一遍具体的架构。

ALEX First, they built a bi-directed knowledge graph straight from UMLS's Rich Release Format files — CUIs as nodes, with synonyms, definitions, and semantic types attached, relationships as edges — restricted to three vocabularies, SNOMED CT-US, NCI Thesaurus, and MeSH. 首先，他们直接从UMLS的Rich Release Format文件构建了一个双向知识图谱——CUI作为节点，附带同义词、定义和语义类型，关系作为边——限定在三个词表范围内：SNOMED CT-US、NCI Thesaurus和MeSH。

ALEX Every node got embedded three separate ways for comparison — text-embedding-3-large, a general-purpose closed OpenAI model; SapBERT, a BERT-based model trained specifically on UMLS synonym pairs; and e5-large-v2, an open-source general-purpose embedding model — indexed with FAISS（一个常用的向量检索库）cosine similarity for retrieval. 每个节点都用三种不同的方式做了嵌入以便比较——text-embedding-3-large，一个通用的OpenAI闭源模型；SapBERT，一个专门用UMLS同义词对训练的BERT模型；以及e5-large-v2，一个开源的通用嵌入模型——用FAISS做余弦相似度索引以支持检索。

ALEX For retrieval, a target-concept description gets embedded and used to pull the top-k semantically similar CUIs, then expanded recursively through child nodes plus one hop of parent and synonym edges, with semantic-type filters and a max-neighbors cap keeping the candidate pool a manageable size for the next stage. 在检索阶段，目标概念的描述会被嵌入，并用来找出语义最相似的前k个CUI，然后通过子节点递归扩展，再加上一跳的父节点和同义词边扩展，同时用语义类型过滤和邻居数量上限，把候选池控制在下一阶段可以处理的规模内。

ALEX Then a two-stage LLM workflow does the curation itself — first filtering candidates down to concepts that indicate or strongly suggest the target phenotype, then classifying the survivors as either "definitive," meaning they explicitly indicate the concept, or "context-dependent," meaning they'd need more clinical information to confirm; they compared GPT-5 against a locally deployed, 4-bit quantized Qwen3-32B（一个开源大语言模型）. 接下来，一个两阶段的大语言模型流程来完成实际的整理工作——第一阶段把候选概念筛选到那些明确提示或强烈暗示目标表型的概念，第二阶段把筛选后剩下的概念分类为"明确"（即明确指示该概念）或"依赖情境"（即需要更多临床信息才能确认）；他们比较了GPT-5和一个本地部署、4-bit量化的开源大语言模型Qwen3-32B。

JORDAN A two-stage filter-then-classify split feels like a deliberate design choice rather than an obvious one. 先筛选再分类的两阶段设计，感觉是一个经过深思熟虑的选择，而不是显而易见的做法。

ALEX It is, and I'd push on it a little — collapsing filtering and classification into a single LLM call would be cheaper, but splitting them lets each stage optimize for a different failure mode, catching irrelevant concepts early and reserving the finer definitive-versus-context-dependent judgment for a smaller, already-relevant pool; the cost is two LLM passes instead of one, and the paper doesn't actually report whether a single combined pass was tried and how much worse it did, which would have been the natural ablation to include. 确实如此，我想在这里追问一下——把筛选和分类合并成一次大语言模型调用会更省钱，但分开来做可以让每个阶段专门针对不同的失败模式进行优化，先在早期剔除不相关概念，再把更精细的"明确与否"判断留给一个已经相对相关的较小池子；代价是要跑两次模型而不是一次，而论文其实并没有报告是否尝试过把两步合并成一次，以及效果会差多少，这本该是一个很自然的对照实验。

JORDAN Before the numbers — how did they even get a trustworthy answer key, if exhaustively reviewing every candidate CUI in UMLS is infeasible? 在看数字之前——既然要把UMLS里每一个候选CUI都审一遍是不现实的，他们到底怎么拿到一份可信的"标准答案"？

ALEX They used pooled relevance assessment（汇总相关性评估，一种源自信息检索评测的方法）, a standard methodology from information-retrieval evaluation — essentially, run every candidate-generation method you have, union everything they surface into one pool, then have clinicians adjudicate that pool rather than the entire UMLS; it's the same approach TREC（Text REtrieval Conference，一项信息检索领域的标准评测会议）uses to build reference standards for search-engine benchmarks, and it's been shown to hold up for modern neural retrieval systems too. 他们用的是汇总相关性评估，这是信息检索评测里的一种标准方法——本质上是把手头所有候选生成方法都跑一遍，把它们找出来的结果合并成一个池子，再让临床医生去裁定这个池子，而不是审查整个UMLS；这和TREC用来为搜索引擎基准建立参考标准的方法是一样的，而且已经证明对现代神经检索系统同样适用。

JORDAN Give me the headline numbers. 说说关键数字。

ALEX The full UMLS graph came to 924,211 nodes and 1,429,114 edges; restricted to the semantic types actually used in the pipeline, that shrank to a working subgraph of 144,646 nodes and 223,043 edges. 完整的UMLS图谱有924,211个节点和1,429,114条边；限定到流程里实际用到的语义类型之后，缩小为一个有144,646个节点和223,043条边的工作子图。

ALEX Manual concept sets built by clinicians using the UMLS browser ranged from just 30 to 130 CUIs per concept across the five test concepts — chronic heart failure, ischemic stroke, fluid overload, left ventricular systolic dysfunction, and poor mobility — against pooled gold-standard sets of 163 to 675 CUIs, so the manual baseline was capturing a small fraction of what's actually out there. 由临床医生用UMLS浏览器人工构建的概念集合，在五个测试概念——慢性心力衰竭、缺血性脑卒中、体液过多、左心室收缩功能障碍和活动能力差——上只有30到130个CUI，而汇总出的金标准集合有163到675个CUI，这说明人工基线实际上只捕捉到了真实情况的一小部分。

ALEX At their chosen operating point — text-embedding-3-large, 500 seed CUIs, one-hop expansion, a 1,000-neighbor cap — graph retrieval alone generated about 750 candidate CUIs per concept while hitting overall recall of 0.66 to 0.96, and recall above 0.90 on the most clinically specific "definitive" concepts for everyone except poor mobility. 在他们选定的参数配置下——text-embedding-3-large嵌入模型、500个种子CUI、一跳扩展、邻居数上限1,000——仅图检索阶段就为每个概念生成了约750个候选CUI，整体召回率在0.66到0.96之间，而对于最具临床特异性的"明确"概念，除了活动能力差这一项，其他全部召回率都超过0.90。

ALEX After LLM filtering, GPT-5 preserved at least 95 percent of definitive gold-standard CUIs across all five concepts, and clearly beat manual curation on full-set recall — 0.33 to 0.82 for GPT-5 versus 0.09 to 0.60 for the manual sets; Qwen3-32B landed in between, recall 0.17 to 0.69, but still ahead of manual curation on every concept. 经过大语言模型筛选之后，GPT-5在全部五个概念上都保留了至少95%的"明确"金标准CUI，并且在全集召回率上明显优于人工整理——GPT-5是0.33到0.82，人工整理只有0.09到0.60；Qwen3-32B介于两者之间，召回率0.17到0.69，但在每个概念上都仍然领先于人工整理。

ALEX And the cost comparison is the part worth remembering — one-time UMLS embedding ran about eight dollars and two hours, GPT-5 filtering and classification cost roughly 88 cents per query and 21 minutes, and Qwen3-32B ran locally in about 14 minutes with zero API cost, against one to two hours of clinician time per concept for the manual approach. 而成本对比是最值得记住的一点——一次性完成UMLS嵌入花费约8美元、耗时两小时，GPT-5的筛选和分类每次查询大约花费88美分、耗时21分钟，而Qwen3-32B本地运行大约14分钟、没有任何API费用，相比之下人工方法每个概念要花一到两个小时的临床医生时间。
