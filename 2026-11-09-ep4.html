Ep4 (Track C — registry QC, slot 2/2): Running a standardized DQ rule battery on a real OMOP CDM instance

Yankam and colleagues (Frontiers in Big Data, 2026) standardize a historical, paper-based, French-to-English-translated respiratory-disease registry from Douala General Hospital, Cameroon (2009–2023, 108 variables, 2,154 records) into the OMOP Common Data Model, then evaluate the resulting instance with OHDSI's Data Quality Dashboard (DQD) before and after an iterative ETL remediation cycle. The headline numbers: 2,344 checks run before remediation with a reported 96% corrected pass rate, rising to 2,374 checks and a reported 100% corrected pass rate after; conformance improved most (95%→99%, failed checks 54→25), plausibility more modestly (16→11 failed), and completeness barely moved (5→4 failed), attributed to upstream data-collection limits rather than anything ETL could fix. A persistent, instructive failure: all 287 CONCEPT_plausibleGender checks stayed unrunnable before and after, because gender values were never resolved to standard OMOP concept IDs during transformation — a sharp lesson that a check removed from the denominator is not the same as a check that passed. This episode flags that some of the granular raw pass/fail counts retrievable from the fetched text don't fully reconcile with other figures in the same text, and treats the paper's headline percentages, not the individual raw counts, as the reliable summary. Pipeline stage: primarily (d) evaluation, with a secondary (a) candidate-generation angle via DQD's individual bounds-and-temporal-logic checks. Buildable artifact: an OMOP DQD-style rule battery ported to anthropometric fields, with denominator-aware pass-rate tracking.

Plain-English glossary

  • OMOP CDM (Observational Medical Outcomes Partnership Common Data Model) — A standardized database schema plus standardized vocabulary (SNOMED CT, LOINC, RxNorm) that lets health data from different source systems be transformed into one common shape for shared analytic code.（中文：一套标准化的数据库结构，配合标准化词汇表（SNOMED CT、LOINC、RxNorm），让不同来源系统的健康数据能被转换成统一的格式，以便使用同一套分析代码。）
  • OHDSI (Observational Health Data Sciences and Informatics) — The open international community that builds and maintains OMOP CDM and its toolchain.（中文：负责构建和维护OMOP CDM及其工具链的开放国际社区。）
  • DQD (Data Quality Dashboard) — OHDSI's rule-based check suite (2,500+ checks) that evaluates conformance, completeness, and plausibility for any OMOP CDM instance and reports a pass/fail rate per check.（中文：OHDSI的一套基于规则的检查工具（超过2500项检查），用于评估任何OMOP CDM实例的一致性、完整性和合理性，并报告每项检查的通过/未通过情况。）
  • ETL (Extract, Transform, Load) — The standard process of pulling source data, converting it into a target schema, and loading it in, with the OHDSI toolchain (White Rabbit for source profiling, Usagi for vocabulary mapping, Rabbit-In-A-Hat for schema-mapping documentation) supporting each step.（中文：抽取-转换-加载，将源数据提取、转换为目标结构并加载的标准流程；OHDSI工具链中的White Rabbit负责源数据画像，Usagi负责词汇映射，Rabbit-In-A-Hat负责记录结构映射，分别支持流程中的各个环节。）
  • Plausibility checks (e.g. plausibleValueLow/High, plausibleBeforeDeath/AfterBirth) — DQD's named rules checking whether a value falls in an expected numeric range, or whether a date is logically consistent with a person's birth and death dates.（中文：DQD中命名的规则，用于检查一个数值是否落在预期范围内，或某个日期是否在逻辑上与一个人的出生、死亡日期相符。）
  • Removed/unrunnable test — A DQD check that cannot execute at all (e.g. because a required concept mapping is missing), which is excluded from the pass-rate denominator — distinct from a check that ran and failed.（中文：一项无法执行的DQD检查（例如因为缺少必要的概念映射），会被从通过率的分母中排除——这与"运行了但未通过"的检查是两种不同的情况。）

Methods / tools to lift

  • OHDSI Data Quality Dashboard (DQD) — a reusable, named rule battery (bounds checks, temporal-logic checks, schema/conformance checks) applicable to any OMOP CDM instance.
  • White Rabbit / Usagi / Rabbit-In-A-Hat ETL toolchain — source profiling, vocabulary mapping, and schema-mapping documentation tools that precede any DQ evaluation.
  • Iterative remediate-and-rerun cycle — tracing a failed check to its root cause (ETL rule, mapping, join logic), fixing it, and rerunning the full suite to confirm the fix.

  • The persistent CONCEPT_plausibleGender gap (287/287 checks unrunnable before and after) is a reminder that "ran the dashboard" and "fixed everything the dashboard could see" are different claims — worth checking which one any pipeline's own reported pass rate is actually making.

Pipeline stage

Error types covered / not covered

Covered: out-of-range values (plausibleValueLow/High), date-logic errors (before-death/after-birth/start-before-end), referential/schema non-conformance, unmapped-vocabulary gaps. Not covered: digit transposition, decimal-shift, or carry-forward errors specifically; no statistical/trajectory-based outlier detection — purely rule-based bounds and logic checks.

ALEX Second half of today's Track C double feature, and this one's hands-on — Yankam and colleagues, Frontiers in Big Data, 2026, actually running a standardized rule battery against a real, messy, historical dataset and reporting exactly what passed and what didn't. 今天Track C连播的第二集，这一篇是动手实践型的——Yankam及其同事，发表在2026年的《Frontiers in Big Data》上，他们真正把一套标准化规则库跑在了一份真实、混乱的历史数据集上，并报告了到底哪些通过了、哪些没通过。 The dataset is a historical respiratory-disease registry from Douala General Hospital in Cameroon, originally paper-based and in French, and the paper evaluates it before and after standardizing it into the OMOP Common Data Model. 这份数据集是来自喀麦隆杜阿拉综合医院的一份历史性呼吸系统疾病登记数据，最初是纸质、法语记录的，论文评估的是它在被标准化进OMOP通用数据模型（Common Data Model）前后的数据质量。

JORDAN Let's get the acronyms sorted before anything else — OMOP, OHDSI, and DQD. 我们先把这几个缩写理清楚——OMOP、OHDSI和DQD。

ALEX OMOP is the Observational Medical Outcomes Partnership, and its Common Data Model, or CDM, is a standardized database schema plus a standardized vocabulary — think SNOMED CT for clinical concepts, LOINC for lab tests, and RxNorm for medications — that lets health data from completely different source systems get transformed into one common shape, so the same analytic code can run against data from any institution that's adopted it. OMOP是观察性医学结局合作组织（Observational Medical Outcomes Partnership），它的通用数据模型（Common Data Model，简称CDM）是一套标准化的数据库结构，再加上一套标准化词汇表——比如用SNOMED CT表示临床概念、LOINC表示检验项目、RxNorm表示药物——让来自完全不同源系统的健康数据都能被转换成同一种形状，这样同一套分析代码就能在任何采用了这套模型的机构的数据上运行。 OHDSI, the Observational Health Data Sciences and Informatics community, is the open international collaboration that builds and maintains OMOP CDM and its surrounding toolchain. OHDSI（观察性健康数据科学与信息学，Observational Health Data Sciences and Informatics）是一个开放的国际合作社区，负责构建和维护OMOP CDM及其周边工具链。 DQD, the Data Quality Dashboard, is OHDSI's own rule-based check suite — over 2,500 individual checks, organized along the same conformance/completeness/plausibility taxonomy we keep meeting on this track — that runs against any OMOP CDM instance and reports a pass/fail rate per check. DQD（数据质量仪表盘，Data Quality Dashboard）是OHDSI自己的一套基于规则的检查工具——包含2500多项独立检查，按照我们在这条赛道上反复遇到的一致性/完整性/合理性分类体系组织——可以运行在任何一个OMOP CDM实例上，并报告每一项检查的通过/未通过率。

JORDAN And the dataset itself went through a whole translation-and-digitization pipeline before any of that? 这份数据集在进入这套流程之前，经历了一整套翻译和数字化的过程？

ALEX It did, and the toolchain involved is worth naming because it's the standard OHDSI ETL path. 确实经历了，而且用到的工具链值得点名，因为这是标准的OHDSI式ETL（抽取-转换-加载，Extract-Transform-Load）路径。 White Rabbit profiles the raw source data — field names, types, the fraction of missing values, how many unique values each field has — before anything gets transformed. White Rabbit先对原始源数据进行画像分析——字段名称、数据类型、缺失值比例、每个字段有多少个不同的取值——这一步在任何转换发生之前就先完成。 Usagi then helps map local, free-text source terms to standard OMOP vocabulary concepts — the paper's worked example maps the French-derived term "asthme," translated to "asthma," to a specific OMOP concept ID — with a human reviewing and confirming each candidate match. 然后Usagi帮助把本地的、自由文本形式的源术语，映射到标准的OMOP词汇概念——论文里的示例，是把由法语翻译而来的"asthme"（译为"asthma"，哮喘）映射到一个具体的OMOP概念ID——每一个候选匹配都由人工审核确认。 Rabbit-In-A-Hat documents how source tables and columns map onto the CDM's own table structure. Rabbit-In-A-Hat则用来记录源数据表和字段是如何映射到CDM自身的表结构上的。 Only after all of that does DQD get run. 只有在这一切都完成之后，DQD才会开始运行。

JORDAN So what was the actual motivating problem here? 那这里真正的驱动问题是什么？

ALEX Standardizing data into a common model is widely treated as a prerequisite for large-scale observational research, but standardizing it doesn't automatically mean the result is good data — a clean, well-formed OMOP table full of wrong or missing values is still bad data, just bad data in a tidier shape. 把数据标准化进一个通用模型，被普遍视为大规模观察性研究的前提条件，但标准化本身并不意味着结果就是好数据——一张结构整洁、格式规范的OMOP表格，如果里面充满了错误或缺失的值，仍然是坏数据，只是换了一种更整齐的外形。 This paper treats data-quality evaluation as its own separate, necessary step after the ETL transformation, not something you get for free just by adopting the standard schema. 这篇论文把数据质量评估当作ETL转换之后一个独立且必要的步骤，而不是把它当成采用了标准模式就自动获得的东西。 The specific setting matters too: this is a historical, paper-based, French-language dataset from a sub-Saharan African hospital — 2009 to 2023, 108 variables, 2,154 records — and OMOP CDM implementations in that kind of low-resource, non-digital-native setting are still rare, so the paper is partly a feasibility demonstration for a context very different from a modern high-volume digital EHR. 具体的场景也很重要：这是一份来自撒哈拉以南非洲一家医院的历史性、纸质、法语数据集——时间跨度2009到2023年，108个变量，2154条记录——而在这种资源有限、并非原生数字化的场景下，OMOP CDM的实际应用案例仍然很少见，所以这篇论文某种程度上也是在为一个与现代高容量数字化EHR截然不同的场景，做一次可行性验证。

JORDAN Walk me through the actual decision rule DQD applies — what exactly gets flagged? 具体说说DQD到底是怎么判断、标记什么的——它的判定规则是什么？

ALEX DQD's checks are literal, named rules, and several map directly onto anthropometric-style plausibility logic. DQD的检查项都是具体命名的规则，其中好几项可以直接类比到人体测量数据的合理性判断逻辑上。 FIELD_plausibleValueLow and FIELD_plausibleValueHigh check whether a numeric value falls inside an expected range for its concept — the direct cousin of a height or weight bounds check. FIELD_plausibleValueLow和FIELD_plausibleValueHigh检查一个数值是否落在该概念预期的取值范围内——这和身高或体重的边界检查是同一类逻辑的近亲。 FIELD_plausibleAfterBirth, FIELD_plausibleBeforeDeath, and FIELD_plausibleDuringLife check temporal logic against a person's birth and death dates; FIELD_plausibleStartBeforeEnd and FIELD_plausibleTemporalAfter check that date pairs are internally consistent. FIELD_plausibleAfterBirth、FIELD_plausibleBeforeDeath和FIELD_plausibleDuringLife负责核查时间逻辑是否与一个人的出生和死亡日期相符；FIELD_plausibleStartBeforeEnd和FIELD_plausibleTemporalAfter负责核查日期对本身的内部一致性。 Conformance checks like FIELD_isForeignKey, FIELD_cdmDatatype, and FIELD_isRequired check referential integrity, data typing, and required-field completeness against the CDM's own schema. 一致性检查，比如FIELD_isForeignKey、FIELD_cdmDatatype和FIELD_isRequired，核查的是数据是否符合CDM自身模式所要求的引用完整性、数据类型，以及必填字段的完整性。 When a check fails, the remediation cycle traces it back to its root cause — a bad ETL transformation rule, a wrong vocabulary mapping, a broken join — fixes it, and reruns the whole DQD suite to confirm the fix worked. 当某项检查未通过时，修复流程会追溯其根本原因——可能是某条ETL转换规则有误、某个词汇映射错了、或者某个连接关系断了——修复之后，重新运行整套DQD检查以确认修复确实有效。

JORDAN Anything you'd push back on? 有什么你想提出质疑的地方吗？

ALEX Yes — a specific, persistent failure here is genuinely instructive. 有——这里有一个具体且持续存在的失败案例，确实很有启发性。 CONCEPT_plausibleGender was removed as unrunnable for all 287 of its checks, both before and after the ETL fix cycle, because the source gender values were never resolved to their standard OMOP concept IDs during transformation — even though the underlying Sex field itself was 100% complete in the source data. CONCEPT_plausibleGender这一项检查，在修复周期前后，287项检查全部都被判定为"无法运行"而移出，原因是源数据中的性别值在转换过程中从未被正确解析为标准的OMOP概念ID——即便底层的性别字段在源数据中其实是100%完整的。 That's a sharp distinction worth internalizing: a check that gets removed from the denominator because it can't run is not the same as a check that ran and passed, and if you're not careful, a rising "pass rate" can rise partly because more checks quietly dropped out of the count, not because the data actually got better. 这是一个值得牢记的重要区别：一项因为无法运行而被移出分母的检查，和一项真正运行并且通过的检查，完全不是一回事；如果不够小心，一个"上升的通过率"可能部分是因为有更多检查悄悄地被排除在统计之外，而不是因为数据真的变好了。 The paper itself is transparent about this, but it's exactly the trap a dashboard built on pass-rate percentages alone can fall into if nobody's watching the denominator. 论文本身对这一点是透明的，但这正是一个只盯着通过率百分比的仪表盘，在没有人盯着分母的情况下，很容易掉进去的陷阱。

JORDAN So what actually happened to the numbers? 那这些数字最终到底怎么样了？

ALEX Before the ETL remediation cycle, 2,344 checks ran, with a reported 96% corrected pass rate; after remediation, 2,374 checks ran — a few more became runnable — with a reported 100% corrected pass rate, and total failed checks dropped from 75 to 40. 在ETL修复周期之前，一共运行了2344项检查，报告的校正后通过率是96%；修复之后，运行了2374项检查——多了几项变得可以运行——报告的校正后通过率是100%，而总的未通过检查数从75降到了40。 Conformance showed the clearest improvement, failed checks dropping from 54 to 25 as the pass rate rose from 95% to 99%; plausibility improved more modestly, 16 failed down to 11; and completeness barely moved, 5 failed down to 4, which the authors attribute to upstream data-collection limitations rather than anything the ETL step itself could fix. 一致性检查的改善最明显，未通过检查数从54降到25，通过率从95%升到99%；合理性的改善则相对温和，未通过数从16降到11；而完整性几乎没有变化，未通过数从5降到4，作者将此归因于上游数据采集环节本身的局限性，而不是ETL这一步能够解决的问题。 I want to flag something honestly here: the specific raw pass/fail counts given for completeness and plausibility in the retrievable text — 454 out of 469, and 788 out of 884 — don't fully reconcile against the failed-check counts stated elsewhere in the same text, so we're reporting the paper's own headline percentages as the reliable summary and flagging the granular counts as something to double-check against the actual published tables before citing them anywhere. 我想在这里诚实地指出一点：我们能检索到的文本中，关于完整性和合理性给出的具体原始通过/未通过计数——469项中的454项、884项中的788项——和同一份文本中别处给出的未通过检查数并不完全吻合，所以我们把论文自己给出的整体百分比当作可靠的摘要来报告，而把这些细粒度的计数标记为需要在引用之前，对照正式发表的表格再核实一遍的内容。 Compared against other published DQD implementations, this study's 96% headline pass rate beats a separately reported 83.2% pass rate from 1,125 tests in one comparator study, and its roughly 3.2% pre-fix failure rate sits close to a separate Singapore feasibility study's 1.4% failure rate out of 2,622 checks — so, headline numbers aside, this result sits in a broadly plausible range next to other OMOP DQD applications. 与其他已发表的DQD实施案例相比，这项研究96%的整体通过率，高于另一项对比研究中1125项检查得到的83.2%通过率，而它修复前约3.2%的失败率，也与另一项新加坡可行性研究中2622项检查里1.4%的失败率比较接近——所以，撇开具体数字的细节，这个结果和其他OMOP DQD应用案例相比，大体落在一个合理的区间内。

JORDAN Which of the five pipeline-stage answers does this one get? 这篇属于五个流水线阶段答案里的哪一个？

ALEX Primarily (d), evaluation — DQD is fundamentally a rule-based evaluation layer you run after any transformation to check whether the result is trustworthy, which is a direct analogue for evaluating whether an anthropometric pipeline's own inputs are even well-formed — correct units, sane concept mappings, valid date logic — before any statistical flagging runs on top. 主要是(d)，评估——DQD本质上是一层基于规则的评估层，在任何转换之后运行，用来检查结果是否可信，这直接类比于在任何统计学标记流程开始运行之前，先检查一个人体测量数据流程自身的输入是否格式正确——单位对不对、概念映射是否合理、日期逻辑是否有效。 There's a real secondary touch of (a), candidate generation: the individual plausibleValueLow/High-style checks are literally simple bounds-based flaggers in their own right, and could sit upstream of, or run alongside, a spline mixed-effects model as a cheap first-pass sanity net. 这里也确实有一点(a)候选生成的味道：那些plausibleValueLow/High风格的单项检查，本身就是简单的基于边界的标记器，可以放在一个样条混合效应模型之前，或者与它并行运行，作为一道廉价的第一轮基本合理性检查。

JORDAN Buildable artifact? 可构建的工件是什么？

ALEX An OMOP DQD-style Rule Battery for Anthropometric Fields. 一个"面向人体测量字段的OMOP DQD风格规则库"（OMOP DQD-style Rule Battery for Anthropometric Fields）。 Port a small battery of DQD-style named checks — a plausibleValueLow/High equivalent for height and weight, a plausibleBeforeDeath/AfterBirth equivalent comparing a measurement date against date-of-birth and date-of-death fields, and basic schema checks like required-field and datatype conformance — as a lightweight pre-flight pass that runs before any statistical flagger, with a running pass-rate tracked over time the way DQD itself reports it, denominator and all, so a rising percentage can always be traced back to whether it's from better data or from fewer runnable checks. 把一小套DQD风格的命名检查搬过来——一个针对身高和体重的plausibleValueLow/High等价物、一个把测量日期与出生日期、死亡日期字段进行比较的plausibleBeforeDeath/AfterBirth等价物，以及诸如必填字段和数据类型一致性这类基础模式检查——作为在任何统计学标记器运行之前的一道轻量级预检关卡，并像DQD本身那样，随时间持续追踪通过率，连分母也一起追踪，这样一旦百分比上升，总能追溯清楚它究竟是因为数据真的变好了，还是因为能运行的检查变少了。 Difficulty: S to M — the individual rules are simple, but wiring up a persistent, denominator-aware tracking dashboard is the real engineering lift. 难度：S到M——单项规则很简单，但搭建一个持续追踪、并且对分母保持警觉的仪表盘，才是真正需要花功夫的工程部分。
