Track C — Registry Data Quality & Anthropometric Outlier Detection

Blurb

This episode reads Mang et al. (2022, BMC Medical Informatics and Decision Making), which describes DQAgui, an R/Shiny graphical front-end built on top of the existing DQAstats R package for the MIRACUM network of ten German university hospitals. Where this morning's ACHILLES Heel episode covered generating data-quality flags cheaply, DQAgui covers the opposite half: making flags that already exist navigable by users without programming knowledge, via side-by-side source/target comparison, one-click SQL drill-down into any flagged element, time-window and element subsetting, and a cross-site "datamap" dashboard. Two structured feedback rounds (FR1 at end 2019 surfaced 36 issues across LOGIC/ETL/MDR/GUI categories) drove iterative releases through mid-2021. The paper reports no sensitivity, specificity, or ground-truth validation anywhere — it's a usability and feasibility report, not an error-detection method being validated; the plausibility/completeness/conformance checking logic itself lives in the earlier DQAstats publication. For the CFFPR outlier pipeline, this lands primarily on the human review budget, with a secondary touch on adjudication tooling. The buildable artifact is a minimal review dashboard for CFFPR-style anthropometric flags, pairing a flagged case with the patient's full growth trajectory, a drill-down into the underlying query, and a logged adjudication decision.

Glossary

  • Conformance / completeness / plausibility — Kahn et al.'s (2016) three-category data-quality framework: whether values adhere to specified standards/formats, whether values are present, and whether values are believable — each assessable via verification (against external standards) or validation (against internal logic).（中文：Kahn等2016年提出的三分类数据质量框架——一致性、完整性、合理性，分别可通过"核验"外部标准或"验证"内部逻辑来评估）
  • DIC (Data Integration Center) — The site-level infrastructure at each MIRACUM hospital that pulls routine clinical data into a research repository.（中文：数据整合中心，各医院将日常临床数据汇入研究数据库的站点级基础设施）
  • i2b2 — A clinical-data-warehouse data model, used alongside OMOP CDM at MIRACUM sites.（中文：一种临床数据仓库数据模型，MIRACUM站点与OMOP CDM并行使用）
  • Kafka — An open-source distributed message-queue system supporting real-time, incremental data streaming, used to re-implement MIRACUM's ETL jobs from batch to continuous.（中文：支持实时增量数据流处理的开源分布式消息队列系统）
  • MDR (metadata repository) — A central registry defining every data element and its required data-quality checks, ensuring checks run identically at every site.（中文：元数据存储库，定义每个数据元素及其所需的数据质量检查，确保各站点检查方式一致）
  • MIRACUM — Medical Informatics in Research and Care in University Medicine, a German data-sharing network of ten university hospitals funded by the German Medical Informatics Initiative.（中文：德国医学信息学倡议资助的十所大学医院数据共享网络）

Methods/tools to lift

  • DQAgui (R/Shiny GUI on DQAstats) — a web-app front-end that presents an existing R package's data-quality checks without requiring R console use.
  • Side-by-side source/target comparison with color-highlighted inconsistencies — turns a long sequential PDF into a structured, scannable dashboard.
  • One-click SQL drill-down per flagged element — makes every flag its own investigation starting point.
  • Time-window and data-element subsetting — supports analyzing a date range or a subset of elements, both for speed and for real-time incremental ETL.
  • Containerized deployment with scheduled runs — Docker + Kubernetes + Argo Workflows for regular automated checks and a live cross-site datamap.
  • User-centered, two-round feedback process — issues classified by type (LOGIC/ETL/MDR/GUI) and prioritized by severity/frequency.

Where it lands + buildable artifact

Lands primarily on (c) the human review budget — the core contribution is making an already-fixed volume of findings faster to work through. Secondary touch on (b) adjudication via the side-by-side comparison and SQL drill-down.

MVP: a minimal review dashboard for CFFPR-style anthropometric flags. Input: a table of flagged encounters (patient, visit, flagged value, residual/z-score, rule fired). Output: a web app pairing each flagged case with the patient's full growth trajectory plot, a drill-down into the underlying query/derivation, and a logged adjudication tag (data error / real clinical event / uncertain) to a CSV. Difficulty: S–M.

What to verify first

  • Would a GUI-based review workflow meaningfully cut review time at CFFPR's scale, given MIRACUM built this for comparing large cross-site volumes rather than a much smaller ~0.05% adjudication slice?
  • Does the Kahn conformance/completeness/plausibility taxonomy actually cover longitudinal, trajectory-level plausibility the way anthropometric growth data would need, or is that effectively a fourth check type outside the original framework?
  • Since this paper offers no ground-truth validation, can it be used as evidence that the underlying checks it displays catch real errors at any particular rate — or only as a feasibility/adoption story?

Pipeline stage

Primary: (c) the human review budget — a workflow/UX layer that reduces time cost per already-generated finding, not a new flagging method.

Secondary: (b) adjudication — side-by-side comparison and SQL drill-down directly aid deciding whether a flagged value is a data error or something else.

Error types covered / not covered

Covered (via the underlying DQAstats checks, not new to this paper): conformance violations (value outside MDR-permitted range), completeness (missing values), atemporal and uniqueness plausibility checks (exact logic deferred to the earlier DQAstats publication).

Not covered: unit conversion, digit transposition, decimal shift, carry-forward/stale values, and no explicit real-clinical-event-vs-error discrimination logic.
