Blurb

Ferreira et al. (Journal of Medical Internet Research, 2026) introduce the Open Syndrome Definition (OSD) — a JSON Schema (draft 2020-12) that converts free-text public-health case definitions into machine-readable, executable objects with a metadata group (version, scope, provenance) and a criteria group of nested Boolean logic (AND/OR/AT LEAST, rarely deeper than three levels). Because no machine-readable dataset of case definitions existed (they searched PubMed, OpenAlex, Kaggle, Hugging Face, Harvard Dataverse and found none), they also shipped the first comprehensive dataset of 407 structured definitions, a Python 3.11 toolkit that uses LLMs (cloud APIs or fully local via Ollama; mistral-7b chosen after benchmarking) to convert prose↔JSON, and the Open Syndrome Initiative, a Hugo-based, Git-backed community platform. A data-filtering prototype maps criteria leaf-terms through JSON-LD to HPO and the Disease Ontology, so a standardized definition can be applied to any uploaded tabular health dataset with consistent semantics. Where it lands: AI-tooling / career, with a method-only assist to Liz / CFFPR phenotype & data quality. Tool sketch (episode ends here): a pheno-def-compiler that turns a registry's free-text phenotype/cohort definitions into versioned, ontology-anchored, executable JSON Schema objects plus a validator — every phenotype change becomes a reviewable diff instead of a Slack message.

Plain-English glossary

  • Case definition — the agreed criteria that decide whether a person counts as a case of a condition for surveillance; a population instrument, not a single-patient diagnosis.（中文：病例定义——判定某人在监测目的下是否算作某疾病病例的商定标准；是群体工具，不是单个病人的诊断。）
  • Disease Ontology — a standardized controlled vocabulary of diseases with defined relationships.（中文：疾病本体——带有明确关系的疾病标准化受控词表。）
  • HPO (Human Phenotype Ontology) — a standardized controlled vocabulary of clinical signs and symptoms.（中文：HPO——临床体征与症状的标准化受控词表。）
  • JSON-LD — JSON with an attached context that binds each field to a specific ontology term, giving plain data a semantic anchor.（中文：JSON-LD——附带语境的 JSON，把每个字段绑定到特定本体术语，让普通数据有语义锚点。）
  • Ontology — a controlled vocabulary plus defined relationships between its terms, so software can reason over them.（中文：本体——一个受控词表加上术语间的明确关系，好让软件能对其推理。）
  • Syndromic surveillance / syndrome definition — a case definition tuned for early warning (symptom-based) rather than laboratory confirmation.（中文：综合征监测／综合征定义——为早期预警（基于症状）而非实验室确诊调校的病例定义。）

Methods / tools to lift

  • Definition-as-JSON-Schema — encode phenotype/case logic as a self-describing, portable JSON Schema (draft 2020-12) with a metadata group and a nested-Boolean criteria group; travels through Git for version control.
  • LLM-for-structure, deterministic-lookup-for-codes — use an LLM to draft the structural hierarchy, but map leaf terms to ontology codes deterministically (their planned BioPortal integration), because precise coding is where LLM fluency becomes a liability.
  • Local-first privacy option — Ollama deployment so clinical prose never leaves the machine; cloud APIs optional (OpenAI/Anthropic/Gemini/Mistral/DeepSeek).
  • JSON-LD ontology mapping — bind leaf terms to HPO / Disease Ontology so the same criterion resolves identically across data sources.
  • Git-native contribution workflow — pull-request submission, community review, version history as first-class provenance.
  • LLM-as-a-judge (proposed) + human-in-the-loop — automated semantic-fidelity grading, hedged by community review (note the circularity risk below).

Where it lands + buildable artifact

Serves AI-tooling / career, with a method-only assist to Liz / CFFPR phenotype & data quality.

pheno-def-compiler (M) — Input: a registry's free-text phenotype/cohort definitions (data dictionary). Pipeline: LLM drafts each into an OSD-style JSON Schema with nested Boolean criteria → leaf terms mapped to HPO + SNOMED CT + LOINC → validator runs the compiled definition against a tabular extract, emitting a matched-cohort flag plus an ambiguity-and-coverage report. Payoff: every phenotype change is a reviewable diff.

What to verify first

  • LLM structuring faithfulness: compiled logic must mean exactly what the clinical author intended — require human sign-off; do not trust LLM-as-a-judge as the only gate (shared blind spots make the metric look good while both are wrong).
  • Ontology mapping errors: a leaf term mapped to a near-but-wrong concept passes validation and silently mis-selects records — human-review the mapped terms.
  • Schema fit: the dataset is symptom-forward, shallow-nesting syndromic definitions; chronic-disease phenotypes lean on labs, trajectories, and treatment history — check whether the schema needs extension for temporal/quantitative criteria.
  • Version discipline: the value is auditability — enforce that every definition change is a tracked diff.
  • External method applied to a registry's own documentation — no claim on any registry's internal data.

JORDAN Start me at the vocabulary. 先从术语开始。What is a "case definition," and what makes it a public-health object rather than just a diagnosis? 什么是"病例定义" (case definition)，是什么让它成为一个公共卫生对象，而不只是一个诊断？

ALEX A case definition is the agreed set of criteria that decides whether a given person counts as a case of some condition for surveillance purposes. 病例定义是一组商定好的标准，用来判定某个人在监测目的下是否算作某个疾病的一个"病例"。It's not the same as a clinical diagnosis for one patient — it's a population instrument, written so that different health workers in different places classify the same way. 它和给单个病人的临床诊断不一样——它是一个群体工具，写出来是为了让不同地方的不同卫生工作者以相同的方式分类。When it's tuned for early warning rather than confirmation, people call it a syndrome definition or a syndromic indicator, and this field uses those terms loosely. 当它是为早期预警而不是确诊调校时，人们把它叫做综合征定义 (syndrome definition) 或综合征指标，这个领域对这些词用得很随意。The catch is that almost all of them are written as free-text prose. 问题在于，几乎所有这些定义都是以自由文本散文的形式写成的。

JORDAN And the terms I'll need for the semantic side? 那我在语义那一侧需要哪些术语？

ALEX Two ontologies show up. 有两个本体 (ontology) 会出现。An ontology here is a controlled vocabulary with defined relationships — a fixed set of terms plus how they relate, so software can reason over them. 这里的本体指的是一个带有明确关系的受控词表——一组固定的术语，加上它们之间的关系，好让软件能对它们进行推理。The Human Phenotype Ontology, HPO, is a standardized vocabulary of clinical signs and symptoms. 人类表型本体（HPO，Human Phenotype Ontology，一个临床体征和症状的标准化词表）。The Disease Ontology is the parallel standardized vocabulary of diseases. 疾病本体 (Disease Ontology) 是与之平行的疾病标准化词表。And JSON-LD is JSON with an attached context that says "this field means this specific ontology term," so a plain data field becomes semantically anchored. 而 JSON-LD 是带有附加上下文的 JSON（JSON-LD，一种在 JSON 上附加语境、声明"这个字段对应某个特定本体术语"的格式），于是一个普通的数据字段就有了语义锚点。Hold onto those three — HPO, Disease Ontology, JSON-LD — because they're how this tool stays meaningful across different health systems. 记住这三个——HPO、疾病本体、JSON-LD——因为它们正是这个工具在不同卫生系统间保持含义一致的方式。

JORDAN So what problem were they actually solving? 那他们到底在解决什么问题？

ALEX The gap is that case definitions have almost no interoperability. 缺口在于，病例定义几乎没有互操作性。Two agencies can publish definitions for the same disease that read differently, use different criteria, and can't be compared programmatically. 两个机构可以为同一个疾病发布读起来不一样、用不同标准、且无法用程序比较的定义。When they went looking for an existing machine-readable dataset of case definitions — searching PubMed, OpenAlex, Kaggle, Hugging Face, and Harvard Dataverse — they found none. 当他们去找一个现成的、机器可读的病例定义数据集时——搜了 PubMed、OpenAlex、Kaggle、Hugging Face 和 Harvard Dataverse——一个都没找到。The searches returned 286 hits for "case definition dataset" and 12 for "syndrome definition dataset," and not one was an actual dataset. 搜索返回了 286 条"case definition dataset"和 12 条"syndrome definition dataset"的结果，但没有一条是真正的数据集。So the field had been encoding critical surveillance logic as prose that a human has to re-read and re-interpret every time. 于是这个领域一直把关键的监测逻辑编码成散文，每次都需要人重新阅读、重新解读。That's slow, error-prone, and impossible to audit at scale. 这很慢、容易出错、而且无法在规模上审计。Make the danger concrete: a prose definition can hide an ambiguous "and/or," an unstated time window, or a threshold buried in a footnote, and two competent readers will resolve those differently. 把危险讲具体：一段散文定义可以藏着一个含糊的"and/or"、一个没说清的时间窗口、或者一个埋在脚注里的阈值，而两个称职的读者会以不同方式去消化它们。When that definition drives who counts as a case during an outbreak, the ambiguity isn't cosmetic — it changes the numbers. 当这个定义决定了疫情期间谁算作病例时，这种含糊就不是表面文章了——它会改变数字。So the motivation isn't tidiness, it's that un-executable logic can't be tested, and untested logic quietly disagrees with itself across places and times. 所以动机不是为了整洁，而是：不可执行的逻辑无法被测试，而未经测试的逻辑会在不同地点和时间悄悄地自相矛盾。

ALEX Their thesis is that a case definition is really a piece of logic wearing a prose costume. 他们的论点是：一个病例定义其实是一段披着散文外衣的逻辑。Underneath the sentences there are signs, quantitative thresholds, temporal windows, and Boolean groupings — AND, OR, AT LEAST. 句子底下藏着体征、量化阈值、时间窗口，以及布尔分组——AND、OR、AT LEAST。If you can extract that logic into a fixed structure, you can execute it, compare it, and version it. 如果你能把这段逻辑抽取成一个固定结构，你就能执行它、比较它、给它做版本控制。That's the whole bet of the paper. 这就是整篇文章下的赌注。

JORDAN Why a JSON Schema specifically, rather than, say, a database table? 为什么偏偏是 JSON Schema，而不是比如说一张数据库表？

ALEX Because a JSON Schema is self-describing and portable — it carries its own rules for what a valid definition looks like, so any system can validate a definition without a shared database. 因为 JSON Schema 是自描述且可移植的——它自带"一个合法定义长什么样"的规则，所以任何系统都能在没有共享数据库的情况下验证一个定义。And a schema travels well through Git, which is what makes the whole version-control and pull-request workflow possible in the first place. 而 schema 在 Git 里流转得很顺畅，这正是让整个版本控制和拉取请求工作流成为可能的前提。A database would centralize the logic; a schema lets it live as a file anyone can fork. 数据库会把逻辑中心化；而 schema 让逻辑作为一个任何人都能 fork 的文件存在。
