Track B — i2b2-ML: a module to facilitate machine learning in the i2b2 platform

Blurb. Klann, Mendis, Visweswaran, Murphy, Estiri and Wagholikar (JAMIA Open, 2026) extend the open-source i2b2 clinical data warehouse so researchers can train and apply ML models entirely inside the platform — no patient-level export, no manual programming for the data plumbing. The workflow reuses i2b2's no-code cohort builder: define a positive patient-set and a negative patient-set as labeled data, then send a small JSON spec to a new API to create, train, and run a model whose weights and predictions live back in the i2b2 database. This dissolves two problems the export step creates: privacy (no roaming copies of PHI) and reproducibility (no idiosyncratic per-analyst preprocessing). Demonstrated on the Pima diabetes dataset and scaled on MIMIC-IV (100k-patient training in 75.8 min). Ships code (GitHub v4.1.0 + DockerHub). Where it lands: AI-tooling / career — the reusable idea is the specification-driven, leakage-guarded pipeline, prototyped as a "cohort-to-model spec" schema and runner.

Plain-English glossary

  • Cohort query — defining a group of patients by clinical criteria via i2b2's point-and-click interface, no code.（中文：队列查询——用 i2b2 的点选界面按临床标准定义一组病人，无需写代码。）
  • Concept / fact (i2b2 schema) — a concept is a coded clinical idea (e.g. a diagnosis code); a fact is one observation of that concept for one patient.（中文：概念/事实——概念是编码的临床理念（如诊断码），事实是某病人对该概念的一次观测。）
  • Data isolation / leakage buffer — excluding data points too close in time to the label event so the model can't learn from information that exists only because the outcome already happened.（中文：数据隔离/防泄露缓冲——排除时间上离标签事件太近的数据点，避免模型从"因结局已发生才存在的信息"里学习。）
  • EHR (electronic health record) — the clinical record data used as the ML input.（中文：EHR——作为机器学习输入的电子健康档案数据。）
  • i2b2 — Informatics for Integrating Biology and the Bedside; an open-source clinical data warehouse platform.（中文：i2b2——"整合生物学与临床"信息学平台，一个开源临床数据仓库。）
  • MIMIC-IV — a large, freely available, de-identified EHR dataset (364,627 patients) from PhysioNet.（中文：MIMIC-IV——PhysioNet 提供的大型、免费、去标识化电子健康档案数据集（364,627 名病人）。）
  • OMOP / OHDSI CDM — a competing, more elaborate common data model for clinical data; its PatientLevelPrediction toolkit is powerful but demands R + OMOP expertise.（中文：OMOP/OHDSI 通用数据模型——一个更精细的临床数据标准模式；其 PatientLevelPrediction 工具包强大但需要 R 与 OMOP 专业知识。）
  • PHI (protected health information) — patient-identifiable data governed by rules like HIPAA.（中文：PHI——受 HIPAA 等规则约束的可识别病人身份的健康信息。）

Methods / tools to lift

  • Bring-model-to-data pattern — train and score inside the governed warehouse; no patient-level export.
  • Specification-driven pipeline — one declarative JSON object pins down cohort, isolation buffer, features, and model, making the whole analysis reconstructable from one artifact.
  • Temporal leakage buffer — configurable exclusion window before the label event, enforced in-pipeline rather than left to the analyst.
  • In-database model repository — trained models stored alongside the data, auditable and reusable across studies.
  • i2b2-etl (Python) + Docker — the released, extensible codebase this is built on.

Where it lands + buildable artifact

Serves: AI-tooling / career (reproducibility & governance layer). MVP (paste-ready): "Cohort-to-model spec schema + runner — define a JSON/YAML spec capturing positive-cohort query, negative-cohort query, label-isolation buffer window, feature list, model type; runner reads the spec, pulls matching records, enforces the time buffer, trains, emits a scorecard + the exact spec used. Input: spec file + data connection. Output: model + metrics report + re-runnable manifest. Difficulty M; steal the leakage-buffer enforcement wholesale."

What to verify first

  • Proof-of-concept scope — only logistic regression is supported; the pattern is validated on a simple model, not deep/GBM models.
  • Concurrency untested — handled one large job, not many simultaneous ones; check multi-user load before operational trust.
  • Determinism of "reproducible" — verify the same spec on the same data reproduces the same model, including randomness in splitting/feature selection.
  • External method only — prototype on public data (MIMIC) before pointing at anything governed; no registry-internals assumptions.

ALEX Today's Track B paper is "i2b2-ML: a module to facilitate machine learning in the Informatics for Integrating Biology and the Bedside platform," by Jeffrey Klann, Michael Mendis, Shyam Visweswaran, Shawn Murphy, Hossein Estiri and Kavishwar Wagholikar, in JAMIA Open, 2026. 今天的 Track B 论文是《i2b2-ML：一个在"整合生物学与临床"信息学平台中促进机器学习的模块》，作者是 Jeffrey Klann、Michael Mendis、Shyam Visweswaran、Shawn Murphy、Hossein Estiri 和 Kavishwar Wagholikar，2026 年发表在《JAMIA Open》上。 We're reading it because it ships code and because its core idea — bring the model to the data instead of exporting the data to the model — maps directly onto how registry-scale clinical data actually has to be handled. 我们读它，是因为它附带了代码，也因为它的核心思想——把模型带到数据身边，而不是把数据导出到模型那里——直接对应了登记库规模的临床数据实际上必须被如何处理。

JORDAN This one's less about biology, so let me anchor the platform terms instead. 这一篇不太涉及生物学，所以让我把平台相关的术语先定住。 What is i2b2? 什么是 i2b2？

ALEX i2b2 is an open-source clinical data warehouse platform that's been deployed at a lot of academic medical centers for close to two decades. i2b2 是一个开源的临床数据仓库平台，近二十年来被许多学术医疗中心部署使用。 Its most-used feature is cohort querying: a researcher uses a point-and-click interface to define a group of patients by criteria — a diagnosis, a lab value, an age range — without writing any code. 它最常用的功能是队列查询：研究者用一个点选式界面，按标准——某个诊断、某个化验值、某个年龄范围——来定义一组病人，完全不用写代码。 Under the hood the data sits in a specific schema built around "facts" and "concepts," where a concept is a coded clinical idea like a diagnosis code and a fact is one observation of that concept for one patient. 在底层，数据存放在一个围绕"事实"和"概念"构建的特定模式里，其中概念 (concept) 是一个编码的临床理念，比如一个诊断码，而事实 (fact) 是某个病人对那个概念的一次观测记录。 The other name you'll hear is OMOP, the OHDSI common data model — a competing, more elaborate standard schema for clinical data. 你会听到的另一个名字是 OMOP，也就是 OHDSI 的通用数据模型 (common data model)——一个与之竞争的、更精细的临床数据标准模式。 The relevant contrast is that OHDSI's prediction toolkit is powerful but demands real R and OMOP expertise, whereas i2b2's whole selling point is the no-code cohort builder. 相关的对比是：OHDSI 的预测工具包很强大，但需要真正的 R 语言和 OMOP 专业知识，而 i2b2 的全部卖点在于那个无需写代码的队列构建器。

JORDAN So what's the actual gap they're filling? 那他们真正填补的空白是什么？

ALEX Right now, the i2b2 workflow ends at cohort export. 目前，i2b2 的工作流在"队列导出"这一步就结束了。 You define your patients, you hit download, and you get a CSV that you then carry off into R or Python to build a model. 你定义好病人，点下载，得到一个 CSV，然后你把它搬到 R 或 Python 里去建模。 That export step is where two problems are born. 那个导出步骤正是两个问题的源头。 The first is privacy. 第一个是隐私。 The moment patient-level data leaves the governed warehouse, you've created a copy sitting on a laptop or a shared drive, and every one of those copies is a breach waiting to happen and a compliance headache under rules like HIPAA. 病人级数据一旦离开受治理的仓库，你就制造了一份副本，躺在某台笔记本或共享盘上，而每一份这样的副本都是一次随时可能发生的数据泄露，也是 HIPAA 之类规则下的合规麻烦。 The second is reproducibility. 第二个是可复现性。 Once the data is out, every analyst cleans it, splits it, and engineers features their own way in their own scripts, and those idiosyncratic, undocumented steps are a well-known engine of the reproducibility crisis in clinical ML. 数据一出去，每个分析师都用自己的脚本、按自己的方式去清洗、切分、构造特征，而那些各行其是、无据可查的步骤，正是临床机器学习可复现性危机的一个众所周知的引擎。 Their thesis is that both problems dissolve if the model training happens inside the platform, next to the data, and never needs an export at all. 他们的论点是：如果模型训练发生在平台内部、紧挨着数据，且根本不需要导出，这两个问题就都会消解。

ALEX It's worth sitting with why the export step is such a durable problem, because it's not a quirk of i2b2 — it's structural. 值得停下来体会一下，为什么导出这一步是个如此顽固的问题，因为它并不是 i2b2 的怪癖——它是结构性的。 On the privacy side, governance teams can lock down the warehouse beautifully, but the instant an analyst downloads a cohort, that data escapes the perimeter into a world of laptops, email attachments and departmental shared drives that nobody is auditing. 在隐私这一侧，治理团队可以把仓库锁得漂漂亮亮，但分析师一旦下载了一个队列，那份数据就逃出了边界，进入一个由笔记本、邮件附件和部门共享盘组成、无人审计的世界。 The data-governance effort is spent on the vault while the copies pile up outside it. 数据治理的力气都花在了金库上，而副本却在金库外越堆越多。 On the reproducibility side, the problem is that the interesting decisions all happen after the export. 在可复现性这一侧，问题在于那些有意思的决定全都发生在导出之后。 How you imputed missing labs, where you drew the train/test split, which features you engineered, how you defined the outcome window — those choices live in a personal script that rarely travels with the paper. 你如何填补缺失的化验值、在哪里划分训练/测试集、构造了哪些特征、如何定义结局窗口——这些选择活在一份私人脚本里，很少随论文一起流传。 The authors' framing is that centralizing those steps inside the platform doesn't just add convenience; it removes the two places where privacy and reproducibility actually break. 作者的立场是：把这些步骤集中到平台内部不只是增加便利；它消除了隐私和可复现性真正崩坏的那两个地方。

JORDAN How does a researcher actually train a model without touching code, then? 那研究者到底怎样在不碰代码的情况下训练一个模型？

ALEX The workflow reuses the thing i2b2 users already know. 这个工作流复用了 i2b2 用户已经熟悉的东西。 You build two cohorts with the normal query interface: a positive patient-set — the patients who have the outcome you want to predict — and a negative patient-set as controls. 你用平常的查询界面构建两个队列：一个正例病人集——拥有你想预测的结局的病人——和一个作为对照的负例病人集。 Those two sets become your labeled training data. 这两个集合就成了你带标签的训练数据。 Then, instead of exporting, you send a small JSON specification to a new API to first create a "model" concept and then trigger training. 然后，你不去导出，而是把一小段 JSON 规格发送给一个新的 API，先创建一个"模型"概念，再触发训练。 The trained model is stored back inside the i2b2 database itself, and to apply it you build a third cohort — the target patients — and trigger execution, with the predictions written back into the platform. 训练好的模型被存回 i2b2 数据库本身，要应用它时，你构建第三个队列——目标病人——并触发执行，预测结果被写回平台。 They built this by extending their existing open-source i2b2-etl Python package, and it's released on GitHub at version 4.1.0 and packaged as Docker containers on DockerHub. 他们通过扩展已有的开源 i2b2-etl Python 包来实现这个功能，代码以 4.1.0 版本发布在 GitHub 上，并打包成 Docker 容器发布在 DockerHub 上。 One design choice I'd push on hard: the current model interface is JSON-and-Swagger, not the point-and-click GUI. 有一个设计选择我要重点质疑：当前的模型接口是 JSON 加 Swagger，而不是那个点选式的图形界面。 That undercuts the no-code promise — the cohort building is codeless, but the model triggering asks a clinician-researcher to hand-write JSON payloads, which is its own barrier. 这削弱了"无代码"的承诺——队列构建是免代码的，但触发模型却要求临床研究者手写 JSON 负载，这本身就是一道门槛。

ALEX There's also a deliberate contrast with the OHDSI world that's worth drawing out. 还有一处与 OHDSI 世界的刻意对比，值得展开讲。 OHDSI's PatientLevelPrediction framework, built on the OMOP common data model, is far more capable — a wide menu of algorithms, deep configurability, standardized outputs. OHDSI 的 PatientLevelPrediction 框架建立在 OMOP 通用数据模型之上，能力强得多——算法菜单很宽、可配置性很深、输出标准化。 But that power has a price: you need real fluency in R, in OMOP's conventions, and in ML workflows to use it at all. 但那种强大是有代价的：你必须真正精通 R、精通 OMOP 的约定、精通机器学习工作流，才用得起来。 i2b2-ML makes the opposite bet — it deliberately trades breadth for a low floor, so a clinician-researcher who already lives in i2b2 can build a model without leaving the environment or learning a new stack. i2b2-ML 押的是相反的赌注——它有意用广度换取一个低门槛，好让一个本就生活在 i2b2 里的临床研究者，不必离开这个环境、也不必学一套新技术栈，就能建出一个模型。 That's the right framing for us: this isn't the most powerful ML platform, it's the one that meets non-programmer researchers where they are. 对我们来说这是正确的定位：它不是最强大的机器学习平台，而是那个在非程序员研究者所在之处迎接他们的平台。 The models are also stored as reusable objects inside the warehouse, so over time the platform accumulates a shared library of algorithms rather than a graveyard of one-off scripts. 模型还作为可复用的对象存放在仓库内部，于是随着时间推移，平台积累起一个共享的算法库，而不是一堆一次性脚本的坟场。

JORDAN What did they actually measure — does it hold up at scale? 他们到底测量了什么——它在规模上撑得住吗？

ALEX They ran two demonstrations. 他们做了两个演示。 The small one used the public Pima Indians Diabetes dataset — 768 records, eight clinical measurements, a binary diabetes label — mostly to prove the end-to-end plumbing works. 小的那个用了公开的 Pima 印第安人糖尿病数据集——768 条记录、八个临床测量、一个二元糖尿病标签——主要是为了证明端到端的管道能跑通。 Training took 1.32 seconds, applying the model took 2.2 seconds. 训练花了 1.32 秒，应用模型花了 2.2 秒。 The scale test used MIMIC-IV, a large freely available de-identified EHR dataset with data on 364,627 patients. 规模测试用了 MIMIC-IV，一个大型、免费可得、去标识化的电子健康档案数据集，包含 364,627 个病人的数据。 Training on 100,000 patients finished in 75.8 minutes, and applying the model to classify 28,985 patients took 1.61 minutes, on a single AWS instance. 在 100,000 个病人上训练用了 75.8 分钟，把模型应用到 28,985 个病人上分类用了 1.61 分钟，全在单台 AWS 实例上完成。 So no accuracy leaderboard here — the paper is a systems and workflow contribution, and the numbers are about throughput, not AUC. 所以这里没有准确率排行榜——这篇论文是一个系统与工作流层面的贡献，数字讲的是吞吐量，而不是 AUC。 The one methodological guard I want to flag is data isolation. 我想特别指出的一个方法学防护是数据隔离。 The API enforces the exclusion of data points too close in time to the label event, with a configurable buffer period, so the model can't accidentally learn from information that only exists because the outcome already happened. API 强制排除了在时间上离标签事件太近的数据点，带一个可配置的缓冲期，这样模型就不会意外地从"只因为结局已经发生才存在的信息"里学习。 That's a built-in defense against temporal data leakage, baked into the pipeline rather than left to each analyst. 这是一道对抗时间性数据泄露的内建防线，被烤进了流水线里，而不是丢给每个分析师各自处理。

JORDAN Say more about why temporal leakage is such a trap in clinical data specifically. 再多说说，为什么时间性泄露在临床数据里尤其是个陷阱。

ALEX It's the single most common way a clinical prediction model looks brilliant in development and useless in deployment. 它是临床预测模型在开发时看起来惊艳、部署时却毫无用处的最常见的一种方式。 The trap is that the electronic record fills up with signals that only appear because the outcome is already unfolding. 陷阱在于，电子病历里塞满了那些"只因为结局已经在展开才出现"的信号。 If you're predicting sepsis and you let the model see the lactate lab drawn an hour before the diagnosis, or the antibiotic order that was placed because the clinician already suspected sepsis, the model isn't predicting — it's reading the clinician's mind after the fact. 如果你在预测脓毒症，却让模型看到诊断前一小时抽的乳酸化验、或那张因为医生已经怀疑脓毒症才开出的抗生素医嘱，那模型就不是在预测——它是在事后读医生的心思。 The accuracy looks spectacular and then evaporates the moment you deploy it earlier in time, when those tells don't exist yet. 准确率看起来惊人，然后在你把它部署到时间上更早的时刻时——那些破绽还不存在的时刻——瞬间蒸发。 What i2b2-ML does is make the buffer a first-class, configurable parameter of the pipeline rather than a discipline each analyst has to remember. i2b2-ML 所做的，是把这个缓冲变成流水线里一个头等的、可配置的参数，而不是每个分析师都得自己记住的一种自律。 That's the part I'd lift even if we never touch i2b2 itself. 即使我们永远不碰 i2b2 本身，那也是我会照搬的部分。

JORDAN That leakage guard sounds like the genuinely reusable idea. 那个防泄露的守卫听起来才是真正可复用的点子。 So where does the whole thing land for us? 那么整件事对我们落在哪里？

ALEX This lands on the AI-tooling / career priority — specifically the reproducibility-and-governance layer, which is exactly the open lane we keep coming back to. 这落在 AI 工具 / 职业这个优先事项上——具体是可复现性与治理这一层，正是我们反复回到的那条开放车道。 The transferable idea is not the logistic-regression model; it's the "specification-driven pipeline" pattern. 可迁移的点子不是那个逻辑回归模型；而是"由规格驱动的流水线"这一模式。 A single declarative JSON object pins down cohort definition, the data-isolation buffer, feature engineering, and training, so a whole analysis is reconstructable from one artifact instead of from someone's memory of what they did. 一个声明式的 JSON 对象把队列定义、数据隔离缓冲、特征工程和训练全都钉死，于是整个分析可以从这一份产物里重建出来，而不是靠某人对自己做过什么的记忆。 Here's the buildable artifact. 这就是可动手做的产物。 A "cohort-to-model spec" schema and runner: define a small JSON/YAML spec that captures the positive-cohort query, the negative-cohort query, the label-isolation buffer window, the feature list, and the model type; write a runner that reads the spec, pulls the matching records, enforces the time buffer, trains, and emits a scorecard plus the exact spec used. 一个"队列到模型"的规格模式加执行器：定义一个小的 JSON/YAML 规格，捕捉正例队列查询、负例队列查询、标签隔离缓冲窗口、特征清单和模型类型；再写一个执行器，读取规格、拉取匹配记录、强制执行时间缓冲、训练、并输出一张评分卡外加所用的确切规格。 Input is the spec file plus a data connection; output is a model, a metrics report, and a re-runnable manifest. 输入是规格文件加一个数据连接；输出是一个模型、一份指标报告和一个可重跑的清单。 Difficulty is medium, and the leakage-buffer enforcement is the part worth stealing wholesale. 难度是中等，而那个防泄露缓冲的强制执行是值得整段照搬的部分。 The career angle is that "reproducible, governance-friendly RWE pipeline" is precisely the portfolio piece senior real-world-evidence roles ask for. 职业角度在于，"可复现、对治理友好的真实世界证据流水线"恰恰是资深真实世界证据 (RWE) 岗位所要求的作品集。
