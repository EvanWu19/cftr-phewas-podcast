Ep2 (Track B) — NFTest: Automated Testing of Nextflow Pipelines

Patel et al. (2024, Bioinformatics) ship NFTest, an open-source Python framework (GPLv2, github.com/uclahs-cds/tool-NFTest) for automated testing of Nextflow bioinformatics pipelines. The motivating problem is a software-engineering maturity gap: computational biology pipelines get built to produce a working result first, with testing bolted on late or never, even as the tools inside them (Picard, GATK, PLINK) update every few weeks and can silently change pipeline output. NFTest structures testing as a three-step workflow — nftest init scaffolds a test directory, a YAML file defines test cases (script, config, profile, and an assertion method ranging from "just check completion" to MD5 checksum comparison to a fully custom pass/fail script), and nftest run executes them. The authors demonstrate it on two pipelines: nf-core's sarek (germline/somatic variant calling) and a custom four-caller somatic SNV pipeline, call-sSNV (Mutect2, SomaticSniper, Strelka2, MuSE, intersected via BCFtools). Benchmarked overhead was small — about 1.7% added runtime, ~1% CPU, no meaningful memory cost. The key caveat: every NFTest assertion checks reproducibility against a stored expected output, not correctness against independent ground truth — it makes regressions loud, not right answers verified.

Plain-English glossary

  • BCFtools — a standard command-line utility for manipulating VCF files (e.g. computing intersections of variant call sets). (中文：一个用于处理VCF文件的标准命令行工具，例如计算多个变异集合的交集。)
  • Germline variant — a genetic variant inherited in every cell of the body. (中文：胚系变异，遗传自身体每个细胞的变异。)
  • Nextflow — a workflow orchestration language/runtime for defining bioinformatics pipelines as a graph of steps, with automatic parallelization and environment abstraction (local/cluster/cloud). (中文：一种流程编排语言与运行时环境，用于把生物信息学流程定义为一系列步骤组成的图，并自动实现并行化和运行环境（本地/集群/云）的抽象。)
  • nf-core — a community-curated, peer-reviewed collection of standardized Nextflow pipelines. (中文：一个由社区维护、经过同行评审的标准化Nextflow流程集合。)
  • Somatic variant — a genetic variant arising after conception, typically present only in a subset of cells (e.g. a tumor). (中文：体细胞变异，受精后才出现的变异，通常只存在于部分细胞中，例如肿瘤细胞。)
  • Test-driven development (TDD) — writing tests before or alongside code, standard practice in general software engineering. (中文：测试驱动开发，即先编写测试或与代码同步编写测试，是通用软件工程中的标准实践。)
  • VCF (Variant Call Format) — the standard text file format for recording where a genome differs from a reference. (中文：变异调用格式，记录基因组与参考序列差异之处的标准文本文件格式。)

ALEX Today's Track B pick is short and practical — "NFTest: automated testing of Nextflow pipelines," by Patel and colleagues, published in Bioinformatics in 2024. 今天B轨道选的这篇论文短小但实用——《NFTest：Nextflow流程的自动化测试》，作者Patel等人，2024年发表在《Bioinformatics》期刊上。 It's a tool paper, not a discovery paper — the whole contribution is a piece of open-source software that ships on GitHub, which fits our tool-development lens exactly. 这是一篇工具论文，不是一篇发现型论文——它的全部贡献就是一个发布在GitHub上的开源软件，这正好契合我们工具开发这条视角。 The pitch is simple: as Nextflow pipelines get more complex, testing them by hand doesn't scale, so they built a dedicated testing framework for it. 论点很简单：随着Nextflow流程变得越来越复杂，靠人工测试已经不可扩展，所以他们专门为此构建了一个测试框架。

JORDAN Before that — remind me what an orchestration framework actually buys you over just chaining scripts together yourself. 在那之前——提醒我一下，一个编排框架相比自己手动串联脚本，到底能带来什么好处。

ALEX Automatic parallelization and dependency tracking, mainly. 主要是自动并行化和依赖关系追踪。 Nextflow figures out which steps depend on which inputs and runs everything that can run in parallel at the same time, resumes from the last completed step if something fails partway through, and abstracts away whether a given step runs locally, on a cluster scheduler, or in the cloud, so the same pipeline definition works across environments without rewriting it. Nextflow能自动判断哪些步骤依赖哪些输入，把所有能并行的步骤同时并行运行，如果中途某一步失败了还能从上一个成功完成的步骤续跑，并且把某个步骤到底是在本地运行、在集群调度器上运行还是在云端运行这件事抽象掉，这样同一份流程定义就能在不同环境下直接使用，而不需要重写。 That's the layer NFTest has to test against — not just "did the science come out right," but "did the orchestration itself behave correctly under all these configuration options."这正是NFTest需要去测试的那一层——不只是"科学结果是否正确"，还有"编排本身在所有这些配置选项下是否表现正确"。

JORDAN Let's start with Nextflow itself — I know it as "the thing bioinformatics pipelines are written in," but not much more. 我们先从Nextflow本身说起——我对它的了解仅限于"生物信息学流程都是用它写的"，别的就不太清楚了。

ALEX Nextflow is a workflow orchestration language and runtime — you write a pipeline as a graph of processing steps, each step wrapped in its own script and container, and Nextflow handles running them in the right order, in parallel where possible, on a laptop, a cluster, or the cloud, without you managing that scheduling by hand. Nextflow是一种流程编排语言和运行时环境——你把一个流程写成一系列处理步骤组成的图，每个步骤都包裹在自己的脚本和容器里，Nextflow负责按正确的顺序运行它们，能并行的地方就并行，可以在笔记本电脑、集群或云端上运行，而你不需要手动管理这种调度。 It sits alongside similar frameworks like Snakemake, Common Workflow Language, and Galaxy, but has become the dominant choice in genomics partly because of nf-core, a community-curated collection of standardized, peer-reviewed Nextflow pipelines. Nextflow与Snakemake、通用工作流语言（Common Workflow Language）、Galaxy等类似框架并列存在，但在基因组学领域已经成为主流选择，部分原因是nf-core——一个由社区维护、经过同行评审的标准化Nextflow流程集合。 The paper's two demo pipelines both come from that world: nf-core's sarek, a germline and somatic variant-calling pipeline, and a custom pipeline called call-sSNV that runs four different somatic single-nucleotide-variant callers — Mutect2, SomaticSniper, Strelka2, and MuSE — and then intersects their results. 论文中的两个演示流程都来自这个生态：nf-core的sarek流程，一个用于胚系和体细胞变异检测（germline and somatic variant calling）的流程，以及一个自建的call-sSNV流程，它运行四种不同的体细胞单核苷酸变异（sSNV）检测工具——Mutect2、SomaticSniper、Strelka2和MuSE——然后对它们的结果取交集。 A germline variant is one inherited in every cell of the body; a somatic variant is one that arose later, typically only present in a subset of cells such as a tumor. 胚系变异（germline variant）是遗传自身体每一个细胞的变异；体细胞变异（somatic variant）是后来才出现的，通常只存在于部分细胞中，比如肿瘤细胞。 The pipelines' outputs are VCF files, Variant Call Format, the standard text format for recording where a genome differs from a reference. 这些流程的输出是VCF文件，也就是变异调用格式（Variant Call Format），是记录基因组与参考序列差异之处的标准文本格式。

JORDAN So what specifically was missing before NFTest — people weren't testing these pipelines at all? 那在NFTest出现之前具体缺了什么——难道大家根本不测试这些流程吗？

ALEX Some testing happened, but it was fragmented and manual. 确实有一些测试，但都是零散且手动的。 The paper frames this as a software-engineering maturity gap: fields like general software development treat test-driven development, where you write the test before or alongside the code, as standard practice, but computational biology pipelines were mostly built by researchers focused on getting a working result, with testing added late if at all. 论文把这个问题定性为软件工程成熟度的差距：像通用软件开发领域，测试驱动开发（test-driven development，先写测试或与代码同步编写测试）已经是标准做法，但计算生物学流程大多是由专注于得到可用结果的研究者搭建的，测试往往是后加的，甚至根本没有。 The tools inside these pipelines also change constantly — Picard and GATK, two widely used toolkits for sequencing data and genome analysis, get new releases every couple of months, and PLINK, used for genome-wide association analysis, updates even faster — so a pipeline that worked last month can silently break or silently change its output this month. 这些流程内部所用的工具也在不断变化——Picard和GATK，两个广泛使用的测序数据和基因组分析工具包，每隔几个月就发布新版本，而用于全基因组关联分析的PLINK更新得更频繁——所以一个上个月还能正常运行的流程，这个月可能会悄无声息地出错，或者悄无声息地改变输出结果。 Before NFTest, researchers mostly fell back on ad hoc scripts in Perl, Python, or Bash, which are hard to adapt to a new pipeline and don't generalize across projects, so the actual scope of testing tended to shrink rather than grow as pipelines got more complex. 在NFTest出现之前，研究者大多依赖用Perl、Python或Bash写的临时脚本，这些脚本很难适配到新的流程上，也无法跨项目通用，所以随着流程变得越来越复杂，实际的测试覆盖范围往往是在缩小而不是扩大。

JORDAN You mentioned four different somatic variant callers running side by side in call-sSNV — why would you want four tools finding the same thing? 你提到call-sSNV里并排跑了四种不同的体细胞变异检测工具——为什么要用四个工具去找同一个东西？

ALEX Because somatic variant callers disagree with each other more than you'd like, especially at low variant-allele fractions where a mutation is only present in a small percentage of sequencing reads. 因为体细胞变异检测工具之间的分歧，比我们希望的要多，尤其是在变异等位基因比例（variant-allele fraction）很低、也就是一个突变只出现在一小部分测序读段中的情况下。 Running Mutect2, SomaticSniper, Strelka2, and MuSE in parallel and then intersecting the calls with a tool called BCFtools — a standard utility for manipulating VCF files — is a common consensus strategy to reduce false positives from any single caller's blind spots. 并行运行Mutect2、SomaticSniper、Strelka2和MuSE，然后用BCFtools——一个用于处理VCF文件的标准工具——对结果取交集，是一种常见的共识策略，用来减少任何单一检测工具盲点导致的假阳性。 That intersection step is exactly the kind of multi-tool stitching the paper's introduction warns is fragile: more moving parts, more places for a silent break to hide, which is precisely why call-sSNV needed a battery of test cases rather than one. 而这个取交集的步骤，正是论文引言中警告的那种脆弱的多工具拼接：环节越多，出现无声故障的地方就越多，这也正是为什么call-sSNV需要一整套测试用例，而不是只有一个。

JORDAN How does NFTest actually structure a test, then? 那NFTest到底是怎么组织一个测试的？

ALEX It's a three-step workflow, and it's deliberately simple. 这是一个三步流程，而且是刻意设计得很简单。 Step one, `nftest init`, scaffolds a testing directory and generates template files — a global config and a YAML file where test cases get defined. 第一步，运行`nftest init`，会搭建一个测试目录并生成模板文件——一个全局配置文件和一个用来定义测试用例的YAML文件。 Step two is filling in that YAML: for each test case you specify the Nextflow script to run — which can be a single process, a sub-workflow, or the entire pipeline — along with which config files and Nextflow profiles to use, and what assertion method determines pass or fail. 第二步是填写那个YAML文件：对每个测试用例，你要指定要运行的Nextflow脚本——可以是单个处理步骤、一个子流程，也可以是整个流程——还要指定使用哪些配置文件和Nextflow配置模式（profile），以及用什么断言方法来判定测试通过还是失败。 Assertion options range from "no assertion, just confirm the pipeline completed" to MD5 checksum comparison against a known-good output file, to a fully custom script that takes the actual and expected output files as arguments and returns pass or fail — which is what let the authors write a custom comparator for the sarek demo that ignores file headers and only checks the actual variant calls. 断言方式的选项从"不做断言，只确认流程能跑完"，到用MD5校验和与已知正确的输出文件做比较，再到一个完全自定义的脚本——接收实际输出和预期输出两个文件作为参数，返回通过或失败——正是靠这个功能，作者才能为sarek演示编写一个自定义比较器，忽略文件头部信息，只检查实际的变异调用结果。 Step three is `nftest run`, which auto-detects the defined cases and executes them, with the option to target specific named cases from the command line. 第三步是运行`nftest run`，它会自动检测已定义的用例并执行，也可以从命令行指定运行某些具体命名的用例。 The design is hierarchical — global settings for things like the temp directory and cleanup behavior, with case-specific settings that can override them — which is what lets it scale from one quick smoke test up to the sSNV pipeline's four-caller, multi-mode test suite. 整体设计是分层的——全局设置负责临时目录和清理行为之类的内容，具体用例的设置可以覆盖全局设置——正是这种设计让它能从一个简单的冒烟测试，扩展到sSNV流程那种四种检测工具、多种运行模式的完整测试套件。 One thing worth flagging: every assertion NFTest supports checks reproducibility — does this run produce the same output as a previous known-good run — not biological correctness in any independent sense; if the "expected" file itself encodes a wrong answer, NFTest will happily confirm the pipeline keeps reproducing that wrong answer. 有一点值得指出：NFTest支持的每一种断言方式检查的都是可复现性——这次运行的结果是否和之前一个已知正确的运行结果一致——而不是任何独立意义上的生物学正确性；如果"预期"文件本身就编码了一个错误答案，NFTest只会愉快地确认流程一直在重复产生这个错误答案。

JORDAN How thorough was the test suite they actually built for call-sSNV? 他们为call-sSNV实际构建的测试套件到底有多全面？

ALEX Reasonably thorough for a demo. 作为一个演示来说相当全面。 They defined a test with all four tools running together, a separate test for each individual caller in isolation, a test for Mutect2's tumor-only mode — where there's no matched normal sample for comparison — and a test for Mutect2's multi-sample mode. 他们定义了一个四个工具一起运行的测试，一个针对每个检测工具单独运行的测试，一个针对Mutect2肿瘤单样本模式（tumor-only mode，即没有配对的正常样本可供比较）的测试，还有一个针对Mutect2多样本模式的测试。 Each test compared both the individual VCF outputs from each caller and the final intersected call set along with its accompanying Venn diagram, so a break anywhere in that pipeline — a single caller, or the intersection logic itself — would surface as a specific failing test rather than one opaque "something's wrong" signal. 每个测试都会比较每个检测工具各自输出的VCF文件，以及最终取交集后的变异集合和配套的维恩图，所以流程中任何一处出错——不管是某一个检测工具，还是取交集的逻辑本身——都会表现为一个具体的失败测试，而不是一个含糊的"哪里出错了"的信号。 That granularity is the actual payoff of defining several small test cases instead of one end-to-end smoke test. 这种细粒度正是定义多个小测试用例而不是一个端到端冒烟测试所带来的真正收益。

JORDAN Fair — so it's a regression-detection tool, not a validation tool. 有道理——所以它是一个回归检测工具，而不是一个验证工具。

ALEX Exactly the right framing, and the authors are upfront about that scope. 这个定位完全正确，作者对这一点也很坦诚。 It's the same distinction as unit testing in general software engineering — a passing test tells you behavior hasn't silently changed since the last known-good state, not that the known-good state was itself the right answer, and that distinction matters more in bioinformatics than in most software because "the right answer" often isn't independently knowable without a wet-lab experiment or an orthogonal method. 这和通用软件工程里单元测试的区别是一样的——测试通过只能告诉你行为相对于上一个已知正确的状态没有悄悄改变，而不能告诉你那个"已知正确的状态"本身就是正确答案，这个区别在生物信息学里比在大多数软件领域都更重要，因为"正确答案"往往没有办法脱离湿实验或正交方法独立验证。 On performance, they benchmarked call-sSNV with and without NFTest, ten runs each, on a 16-CPU, 32-gigabyte-RAM system, using a subsampled tumor dataset — about 0.01% of the genome — from the SMC-Het somatic mutation calling challenge. 在性能方面，他们对有和没有NFTest两种情况下的call-sSNV流程分别跑了十次，测试系统配置为16核CPU、32GB内存，使用的是来自SMC-Het体细胞突变检测挑战赛的一个二次抽样肿瘤数据集——大约占基因组的0.01%。 CPU usage went from a median peak of 84.78% without NFTest to 85.68% with it; memory usage showed no meaningful difference, both around 35%; and runtime went from 14 minutes 37 seconds to 14 minutes 52 seconds — about 15 extra seconds, or 1.7% overhead. CPU使用率的中位数峰值，从不用NFTest时的84.78%，变为使用NFTest时的85.68%；内存使用没有出现明显差异，两者都在35%左右；运行时间从14分37秒变为14分52秒——大约多出15秒，即1.7%的开销。 Disk usage added a single-digit-megabyte log file and nothing more. 磁盘占用只是多了一个几兆字节大小的日志文件，别的没有增加。 So the headline claim — that NFTest is genuinely light-weight — holds up under their own numbers, at least at this small test-data scale. 所以NFTest真正轻量这个核心主张，在他们自己给出的数据下是站得住脚的，至少在这种小规模测试数据下是这样。 They also note a competing tool, nf-test, with overlapping features including snapshot testing, though at time of writing nf-test hadn't been formally published — worth knowing that the testing-framework space for Nextflow already had more than one entrant even at NFTest's launch. 他们还提到了一个功能有所重叠的竞品工具nf-test，同样支持快照测试，不过在论文撰写时nf-test还没有正式发表——值得知道的是，早在NFTest推出的时候，Nextflow测试框架这个领域就已经不止一个参与者了。

JORDAN Where does this land for you, practically? 这对你来说，实际上能用在哪里？
