Ep2 — Track B — Improving automated deep phenotyping through LLMs using retrieval-augmented generation (Garcia 2025)

RAG-HPO is an open-source Python tool (github.com/PoseyPod/RAG-HPO) that pairs a large language model with a curated retrieval database to convert free-text clinical notes into standardized Human Phenotype Ontology (HPO) terms. The core architecture is a three-step loop: an LLM extracts candidate phenotype phrases from text, each phrase is embedded and matched via similarity search (FAISS) against a vector database of >54,000 curated clinical phrase-to-HPO mappings, and the top 20 retrieved candidates are handed back to the LLM to make the final, constrained selection. That constrained-choice step is the mechanism that suppresses hallucination: with the strongest backend (LLaMa-3.1 70B), RAG-HPO reached precision 0.81 / recall 0.76 / F1 0.78 on a self-built 112-case clinical case-report cohort, more than doubling the true positives of existing rule-based tools (ClinPhen, Doc2HPO), with only 1 of 315 false positives a genuine hallucination — the rest were broader-but-related ancestor terms. This lands on the AI-tooling/career track: the transferable pattern (extract → retrieve-ground → constrained-select) generalizes to any structured-vocabulary extraction task. Buildable: registry-term-rag-extractor (M) — port the same architecture to a different structured clinical vocabulary, with a curated retrieval database and a rule-based-baseline benchmark including an explicit hallucination-vs-near-miss error tally.

Plain-English glossary

Human Phenotype Ontology (HPO) — A standardized, hierarchically structured vocabulary of clinical abnormality terms, each with a stable ID, enabling computational comparison of patient phenotypes described in different words.（中文:一套标准化、层级结构化的临床异常表现词汇表,每个概念都有稳定编号,使不同措辞描述的患者表型能够在计算机层面进行比对。）

Deep phenotyping — Building a detailed, structured picture of a patient's clinical presentation (typically as a list of HPO terms) so it can be matched against candidate genetic diagnoses.（中文:为患者的临床表现构建详细、结构化的画像(通常表现为一份HPO术语列表),以便与候选遗传学诊断进行匹配。）

Concept recognition — The dictionary-based approach to phenotype extraction: scanning text for known phrases and matching them against an HPO synonym dictionary; fast and interpretable but blind to negation and context.（中文:表型提取的词典匹配方法:在文本中扫描已知短语并与HPO同义词词典匹配;速度快、可解释性强,但无法识别否定表述和上下文。）

Nodal depth — How many levels down the HPO hierarchy a given term sits; deeper terms are more specific, and extraction accuracy tends to fall as depth increases.（中文:某个HPO术语在层级结构中所处的深度;深度越深术语越具体,提取准确率通常随深度增加而下降。）

Hallucination (in LLM output) — A model-generated HPO code that is either nonexistent or has no ontological relationship to the intended clinical concept, as opposed to a related-but-imprecise term.（中文:模型生成的、不存在或与目标临床概念没有本体学关联的HPO编码,区别于相关但不够精确的术语。）

Gold standard corpus (GSC) vs. case study cohort (CSC) — Two evaluation datasets used in this paper: the GSC is derived from OMIM disease summaries and reads like citation abstracts; the CSC is 112 real published case reports the authors manually annotated because the GSC is organ-system-skewed and less representative of actual clinical notes.（中文:本文使用的两个评估数据集:GSC源自OMIM疾病摘要,读起来像文献摘要;CSC是作者手动标注的112篇真实已发表病例报告,因为GSC存在器官系统分布偏倚,不够贴近真实病历。）

Methods / tools to lift

  • RAG-HPO (github.com/PoseyPod/RAG-HPO) — the open-source Python RAG pipeline itself, model-agnostic via any OpenAI-API-compatible LLM.
  • FAISS (Facebook AI Similarity Search) — nearest-neighbor vector search used for the retrieval step.
  • Doc2HPO / ClinPhen / FastHPOCR — the rule-based concept-recognition baselines benchmarked against, useful as comparison points for any new extraction tool.

Where it lands + buildable artifact

Serves the AI-tooling / career priority. Buildable: registry-term-rag-extractor (M) — extract → retrieve-ground → constrained-select architecture ported to a different structured clinical vocabulary, curated retrieval database, benchmarked against a rule-based baseline with explicit hallucination-vs-ancestor-term error tallies.

What to verify first

  • How much curation effort a new retrieval database actually requires relative to the modeling work, since precision depends entirely on database quality/coverage per the authors' own discussion.
  • Real throughput requirements against the paper's reported per-note processing time (up to 45 seconds), before assuming this scales to a large text corpus.
  • Whether any new evaluation set is independent of whoever built the tool being evaluated — the paper's own FastHPOCR-vs-GSC result is flagged by the authors as a possible benchmark-familiarity effect.

ALEX The clinical workflow this feeds is called deep phenotyping — building a detailed, structured picture of a patient's presentation so it can be matched against candidate genetic diagnoses, the way a tool like Exomiser ranks candidate variants by how well a patient's HPO profile fits known disease-gene phenotype patterns. 这项工作所服务的临床流程叫做深度表型分析(deep phenotyping)——为患者的临床表现构建详细、结构化的画像,以便与候选的遗传学诊断进行匹配,就像Exomiser这类工具会根据患者的HPO特征与已知疾病基因表型模式的契合程度,对候选变异进行排序。 The bottleneck is getting from a free-text clinical note to that structured HPO list in the first place. 而瓶颈就在于:如何从一份自由文本的临床病历,首先转化为那份结构化的HPO列表。 The existing approach is called concept recognition — dictionary-based tools that scan text for known phrases and match them to HPO terms — which is fast and interpretable but blind to context: it can't reliably tell "no family history of short stature" from "short stature." 现有的方法叫做概念识别(concept recognition)——基于词典的工具,扫描文本中已知的短语并与HPO术语匹配——速度快、可解释性强,但对上下文视而不见:它无法可靠地区分"无身材矮小家族史"和"身材矮小"这两种表述。

ALEX So here's the setup. 背景是这样的。 Concept recognition tools like Doc2HPO, ClinPhen, and FastHPOCR have been the default for years, and they work by pattern-matching text against an HPO synonym dictionary — solid, but they systematically under-extract, because clinical language varies so much and negation or family-history context routinely trips them up, which means significant manual review is still needed downstream. Doc2HPO、ClinPhen和FastHPOCR这类概念识别工具多年来一直是默认选择,它们通过将文本与HPO同义词词典做模式匹配来工作——稳定可靠,但系统性地提取不足,因为临床语言变化太大,否定表述或家族史上下文经常让它们出错,这意味着下游仍需要大量人工审核。 Large language models look like an obvious fix, since they actually parse context — but used alone, they're unreliable for this specific job: they hallucinate, inventing HPO codes that don't exist or don't match the clinical phrase, and they're inconsistent without expensive fine-tuning. 大语言模型看起来是显而易见的解决方案,因为它们确实能解析上下文——但单独使用时,它们在这项具体任务上并不可靠:会产生幻觉(hallucinate),编造出不存在或与临床短语不匹配的HPO编码,而且如果不经过昂贵的微调,表现也不稳定。 Fine-tuning itself is the standard fix for LLM unreliability, but it's a real cost — GPU time, retraining every time the underlying ontology updates, and specialized expertise most clinical teams don't have sitting around. 微调本身是解决LLM不可靠性的标准方法,但代价不小——需要GPU算力,每次底层本体更新都要重新训练,还需要大多数临床团队并不具备的专业技术能力。

JORDAN So the pitch is retrieval-augmented generation as the middle path — get the LLM's contextual understanding without paying the fine-tuning tax. 所以这里的主张是把检索增强生成(RAG)作为中间路线——既获得LLM的上下文理解能力,又不必付出微调的代价。

ALEX RAG-HPO's architecture: a vector database of clinical phrases mapped to HPO IDs, seeded from the HPO database itself and then expanded with LLM-generated synonyms, each validated against Doc2HPO/ClinPhen before being kept. RAG-HPO的架构是这样的:一个把临床短语映射到HPO编号的向量数据库,最初由HPO数据库本身填充,再用LLM生成的同义词扩展,每个新增条目都要先用Doc2HPO/ClinPhen验证过才会保留。 At inference time, an LLM first pulls candidate phenotype phrases out of the clinical text, each phrase gets embedded and compared against the vector database via similarity search — using Facebook AI Similarity Search, or FAISS, for the nearest-neighbor lookup, with exact fuzzy matches short-circuiting straight through — and the top 20 candidate HPO terms per phrase get handed back to the LLM, which picks the single best, most specific match. 在推理阶段,LLM首先从临床文本中提取候选表型短语,每个短语被向量化后通过相似度搜索与数据库比对——使用Facebook AI相似度搜索(FAISS)进行最近邻检索,精确的模糊匹配可以直接跳过后续步骤——每个短语排名前20的候选HPO术语会被送回LLM,由它挑选出最合适、最具体的那一个。 It's model-agnostic — any OpenAI-API-compatible LLM works, including locally hosted models for HIPAA-sensitive deployments — and the authors benchmarked six different backends from LLaMa-3 70B up through DeepSeek-R1. 它不依赖特定模型——任何兼容OpenAI API的LLM都能用,包括为符合HIPAA要求而本地部署的模型——作者一共测试了六种不同的后端模型,从LLaMa-3 70B到DeepSeek-R1。
