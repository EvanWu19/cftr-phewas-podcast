Track C — Registry Data Quality & Anthropometric Outlier Detection

Blurb

This episode reads Huser et al. (2016, EGEMS), the first multisite comparison of outputs from ACHILLES Heel, a free, open-source, rule-based data-quality tool built by the OHDSI community for OMOP common-data-model datasets. Evaluated across 24 datasets at seven organizations (claims, EHR, pharmacy dispensing, and combinations), the tool's two-step SQL process — 177 precomputed analyses feeding 71 static-threshold rules — found a median of 19 errors per dataset (17 excluding one outlier site), with 12 rules firing across at least 10 of 24 datasets. A structured questionnaire found near-universal value: most sites turned ACHILLES Heel findings into ETL tickets. The paper reports zero sensitivity, specificity, or ground-truth validation anywhere — it's purely descriptive. For the CFFPR outlier pipeline, the paper lands mainly as vocabulary (the ETL-error/mapping-error/source-error taxonomy, the DQC 20-item scope) with a secondary, indirect touch on candidate generation, since many of its 71 rules are literally the simplest possible static out-of-range check. The buildable artifact is a small ACHILLES-Heel-style baseline rule library for anthropometric fields, meant to sit alongside — not replace — a smarter residual-based flag.

Glossary

  • CDM (common data model) — A standardized schema that different organizations' data is mapped into, enabling the same analytic code and the same quality checks to run across sites.（中文：通用数据模型，统一结构使同一套分析与质量检查代码可跨站点运行）
  • DQC (Data Quality Collaborative) — A group that published a 20-item list of data-quality reporting recommendations across four areas: capture documentation, processing/provenance documentation, data-element profiling, and analysis-specific documentation.（中文：数据质量协作组，发布了涵盖四方面的二十项数据质量报告建议清单）
  • ETL (extract, transform, load) — The pipeline moving data from a source system into a target CDM's structure and terminology.（中文：提取、转换、加载，数据从源系统到目标通用数据模型的搬运流程）
  • ETL error / mapping error / source data error — Three distinguishable but often hard-to-separate error origins: a bug in the transformation pipeline itself; a specific mistranslation of source terminology into the target vocabulary; or an error already present in the source data before any transformation.（中文：三种可区分但往往难以分辨的错误来源——流水线代码本身的错误、术语转换错误、以及转换前就已存在于源数据中的错误）
  • OHDSI / OMOP CDM — Observational Health Data Sciences and Informatics, the multi-stakeholder collaborative maintaining the OMOP common data model used by ACHILLES.（中文：观察性健康数据科学与信息学协作组织，维护ACHILLES所使用的OMOP通用数据模型）
  • Static-threshold rule — A fixed, dataset-independent plausibility check (e.g. "days_supply should not exceed 180") that treats every context identically rather than adapting to a specific population's own distribution.（中文：固定的、不依赖具体数据集的合理性检查，不随人群自身分布而调整）

Methods/tools to lift

  • ACHILLES / ACHILLES Heel — OHDSI's open-source, GitHub-published CDM data-profiling tool and its data-quality-rule subcomponent (71 rules in the evaluated v1.1, since expanded past 100).
  • Two-step SQL architecture — a precomputation stage (177 analyses, visualization-driven) feeding a separate rule-evaluation stage, so new rules can be added by editing one SQL file without touching the display layer.
  • Error/warning severity split with analysis-ID tagging — every finding is tagged with an analysis ID and a violation count, enabling cross-site, cross-dataset comparison.
  • DQC 20-item framework — a scope checklist for what any data-quality report should cover, useful for naming what a given tool does and doesn't address.

What to verify first

  • Does the ETL/mapping/source-error taxonomy map cleanly onto how CFFPR's own encounter-level height/weight data is captured and processed?
  • Would a cheap static-rule baseline layer meaningfully complement a spline or mixed-model residual flag, or mostly duplicate what it already catches?
  • Since this paper reports no sensitivity, specificity, or ground-truth validation anywhere, can "a rule fired across many sites" be used as evidence that a rule "catches real errors at a known rate" — or are those different claims this paper can't support?

Pipeline stage

Primary: (e) nothing directly — framework/vocabulary (ETL/mapping/source-error taxonomy; DQC scope boundary).

Secondary: (a) candidate generation — indirectly, since many of ACHILLES Heel's 71 rules are literally static out-of-range checks, the simplest possible flagging mechanism and a useful baseline contrast to a smarter residual-based approach.

Error types covered / not covered

Covered (at a conceptual level): out-of-range/implausible numeric values, logical contradictions (e.g. date ordering), terminology non-conformance.

Not covered: unit conversion, digit transposition, decimal shift, carry-forward/stale values, and real-clinical-event-vs-error discrimination — ACHILLES Heel runs purely cross-sectional distribution checks with no longitudinal/trajectory awareness.
