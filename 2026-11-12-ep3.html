Ep3 (Track C — registry QC, slot 1/2): Auto-generating data quality rules from openEHR archetypes

Tian and colleagues (BMC Medical Informatics and Decision Making, 2021) automatically derive data quality rules (DQRs) directly from openEHR archetypes at a Chinese hospital, rather than having experts hand-write each one. Three experts mapped keywords in the archetype definition language (ADL) to Kahn's 2016 data quality framework, built SQL templates for each mapped keyword, then parsed every archetype's actual constraints (ranges, mandatory fields, code sets) and auto-filled the templates. Using 27 archetypes mapped to 253 data elements from China's CARSES EHR-ranking standard, the automatic method generated 359 rules, 311 of which agreed with 366 expert-written rules — an overall 84.97% coverage, with near-perfect coverage of consistency (100%) and completeness (98.11%) but much weaker coverage of conformity (54.02%) and timeliness (50%), the dimensions that need logic spanning multiple elements rather than a single attribute. No rule set was validated against real patient data with known errors — this is a rule-coverage comparison against a second, non-independent hand-written rule set, not a detection-accuracy study. The buildable artifact is a Schema-to-Rule Generator that parses a registry's own data-dictionary metadata into the cheap conformance/completeness layer of a flagging pipeline, explicitly scoped away from the plausibility-style statistical checks a spline mixed-effects model is built for.

Plain-English glossary

  • Clinical information model (CIM) — A formal, computer-readable specification of how a piece of clinical content should be structured and what it means.（中文：对电子健康系统中某类临床内容的结构和含义进行正式描述的、机器可读的规范。）
  • openEHR archetype — A computer-readable specification constraining a specific clinical concept (e.g. a blood pressure reading) within the openEHR clinical information model framework.（中文：openEHR临床信息模型框架下，用来约束某个具体临床概念（如一次血压读数）的机器可读规范。）
  • Archetype definition language (ADL) — The language openEHR uses to define and describe constraints on clinical concepts within archetypes.（中文：openEHR用来在原型中定义和描述临床概念约束的语言。）
  • Kahn data quality framework — A 2016 harmonized terminology defining conformance, completeness, and plausibility as the major dimensions for assessing EHR data quality.（中文：2016年提出的一套协调术语体系，把一致性、完整性和可信度定义为评估EHR数据质量的主要维度。）
  • CARSES — The Chinese Application-Level Ranking Standard for EHR Systems, an official Chinese National Health Commission standard specifying data quality requirements for EHR data elements.（中文：中国电子病历系统应用水平分级标准，由中国国家卫生健康委员会发布，规定了EHR数据元素的质量要求。）
  • Archetype relational mapping (ARM) — A specific scheme for persisting openEHR archetypes into a relational database, tying generated rules to that particular database structure.（中文：一种把openEHR原型持久化到关系型数据库的具体方案，使生成的规则与该特定数据库结构绑定。）

Full citation

Tian Q, et al. "Application of openEHR archetypes to automate data quality rules for electronic health records: a case study." BMC Medical Informatics and Decision Making. 2021. PMID: 33812388 | PMCID: PMC8019503 | DOI: 10.1186/s12911-021-01481-2

Methods / tools to lift

  • Keyword-to-framework mapping — map a schema language's own constraint keywords (range, cardinality, code set) to a standard data-quality framework's sub-dimensions, expert-reviewed, as a reusable translation layer.
  • Constraint-string parsing into SQL templates — automatically parse a schema's native constraint syntax into filled SQL templates rather than hand-writing each rule.
  • Coverage comparison against an independently-written rule set — a cheap feasibility check, with the caveat that two rule sets drawn from the same source requirements aren't fully independent ground truth.

Where it lands + buildable artifact

Pipeline stage: (a) candidate generation, primary (a schema-to-rule generator for the cheap structural layer); (e) vocabulary/framework, secondary (the mapping exercise is built on Kahn's terminology). Buildable artifact — Schema-to-Rule Generator: parse whatever constraint metadata a registry's own data dictionary already carries (ranges, required-field flags, code sets) into simple SQL bound/null/code-set rules automatically, scoped explicitly to conformance-and-completeness checks. Difficulty: S-M (small to medium).

What to verify first

  • Whether the registry's own schema or data-dictionary metadata is actually rich enough to parse this way (machine-readable ranges/code sets/required-field flags, not just prose documentation) — unverified for any registry outside this paper's own case study.
  • Whether any auto-generated bound rule would simply duplicate a hard-bound rule that may already exist elsewhere in a pipeline.
  • How far an 84.97% coverage number computed against a China-specific national standard and one hospital's archetype design generalizes to a different country's registry and schema conventions.

Pipeline stage

(a) candidate generation, primary; (e) vocabulary/framework, secondary.

Error types covered / not covered

Covered: schema-expressible single-attribute errors — out-of-range values, missing mandatory fields, invalid codes, duplicate/cardinality violations. Not covered: multi-element logic errors (a computed value not matching a formula, a timestamp out of sequence), free-text/semantic content errors requiring NLP, and any statistical plausibility check — all of which need methods beyond what an archetype's own constraint syntax can express.

JORDAN Start with the vocabulary — what's an openEHR archetype, and what's a clinical information model more broadly? 先从词汇讲起——openEHR原型（archetype）是什么？更广泛地说，临床信息模型（clinical information model）又是什么？

ALEX A clinical information model (CIM, 临床信息模型，一种对电子健康系统中临床内容的结构和语义进行正式描述的规范) is a formal, computer-readable specification of how a piece of clinical content should be structured and what it means — think of it as a machine-readable contract for what a "blood pressure reading" or a "lab order" is allowed to look like. 临床信息模型（CIM，clinical information model，一种对电子健康系统中临床内容的结构和语义进行正式描述的规范）是对某一类临床内容应如何被组织、其含义是什么的一份正式、机器可读的说明——可以把它理解为一份机器可读的"契约"，规定"血压读数"或"检验申请"这类内容允许呈现成什么样子。 openEHR is one such open-source CIM framework, splitting its approach into two layers — a reference model (RM) defining generic data types and structures, and the archetype model, which uses the archetype definition language (ADL, 一种用来在原型中定义和描述临床概念约束的语言) to constrain a specific clinical concept, for example setting that a blood pressure value must fall between 0 and 1000, or that a patient-name field is mandatory. openEHR是这样一种开源CIM框架，它把方法分成两层——一个参考模型（reference model, RM）定义通用的数据类型和结构，以及原型模型（archetype model），后者使用原型定义语言（archetype definition language, ADL，一种用来在原型中定义和描述临床概念约束的语言）来约束某个具体的临床概念，比如规定血压值必须落在0到1000之间，或者患者姓名字段是必填的。 The hospital in this study, Shanxi Dayi Hospital, had already built its clinical data repository on 64 such archetypes mapped onto its relational database — so the quality constraints this paper extracts were already sitting there, just never systematically turned into executable rules. 这项研究中的医院，山西大医医院，早已基于64个这样的原型，把它们映射到自己的关系型数据库上，构建了自己的临床数据仓库——所以这篇论文所提取的那些质量约束，本来就已经存在，只是从未被系统性地转化为可执行的规则。

JORDAN What problem was open before this — hadn't people already been generating data quality rules for a while? 在这篇论文之前，到底有什么问题是悬而未决的——人们不是早就已经在生成数据质量规则了吗？

ALEX Manual rule creation is the norm, and it's genuinely a bottleneck — EHR data routinely spans hundreds of fields, and because the people writing rules differ in experience and judgment, the resulting rule sets aren't standard or comparable across institutions or even across evaluators at the same institution. 手工创建规则是常态，而这确实是一个瓶颈——EHR数据通常涉及数百个字段，而由于编写规则的人在经验和判断力上各不相同，最终得到的规则集在不同机构之间、甚至同一机构内不同评估者之间，都不具有标准性和可比性。 Kahn's 2016 harmonized data quality framework — which this episode's catalog has already encountered, defining conformance, completeness, and plausibility as the major dimensions of EHR data quality — gave the field a shared vocabulary, but a shared vocabulary for describing quality problems is different from an automated way to generate the rules that detect them. Kahn 2016年提出的协调数据质量框架——本节目已经接触过，它把一致性（conformance）、完整性（completeness）和可信度（plausibility）定义为EHR数据质量的主要维度——为这个领域提供了一套共享词汇，但描述质量问题的共享词汇，和自动生成检测这些问题的规则的方法，是两件不同的事。 Clinical information models in general had been proposed as a bridge — because they're already computer-readable, in principle a machine could parse their constraints directly into rules — but the paper is explicit that, to the authors' knowledge, nobody had actually published that pipeline before this case study. 一般而言，临床信息模型已被提议作为连接两者的桥梁——因为它们本来就是机器可读的，原则上一台机器可以直接把它们的约束解析成规则——但论文明确指出，就作者所知，在这项案例研究之前，还没有人真正发表过这样一条完整的流水线。

JORDAN Walk me through the decision rule — what exactly gets flagged, and on what basis? 带我过一下具体的决策规则——到底什么会被标记出来，依据又是什么？ Can you make that concrete with one actual example first? 能先用一个具体例子说明一下吗？ 在讲完整决策规则之前，能先用一个具体例子说明一下吗？

ALEX Sure — the blood pressure archetype constrains its magnitude attribute with the ADL expression "matches {|0.0.1000|}," which the parser reads as "value greater than 0, value less than 1000," and once the pipeline maps "magnitude" to the database column diastolic_blood_pressure_value via the archetype-to-table mapping, the auto-generated rule becomes a plain SQL statement flagging any row where that column falls outside 0 to 1000. 可以——血压原型用ADL表达式"matches {|0.0.1000|}"约束了它的magnitude（量值）属性，解析器把它读作"值大于0，值小于1000"，一旦流水线通过原型-数据表映射，把"magnitude"对应到数据库列diastolic_blood_pressure_value，自动生成的规则就变成了一条普通的SQL语句，标记出该列数值落在0到1000范围之外的任何一行。 Every one of the 359 auto-created rules in this study was produced the same mechanical way — parse the constraint string, map the attribute to a column, drop both into the matching template — which is exactly why it scales to hundreds of rules without a human writing each one by hand, but also exactly why it can't express anything the archetype's own per-attribute constraint syntax doesn't already carry. 这项研究中359条自动创建的规则，每一条都是用同样的机械方式生成的——解析约束字符串、把属性映射到列、把两者填入匹配的模板——这正是它能够扩展到数百条规则、而不需要人工逐条手写的原因，但也正是它无法表达任何原型自身逐属性约束语法本来就不携带的内容的原因。

ALEX Three experts first mapped keywords and constraint descriptions in openEHR's archetype definition language to Kahn's framework sub-dimensions — for example, the ADL keyword "matches" with a numeric range maps to value conformance, "cardinality" with an occurrence limit maps to completeness or uniqueness — and a fourth expert reviewed the mapping. 三位专家首先把openEHR原型定义语言（ADL）中的关键词和约束描述，映射到Kahn框架的各个子维度上——举例来说，带有数值范围的ADL关键词"matches"对应的是值一致性（value conformance），带有出现次数限制的"cardinality"对应的是完整性或唯一性——第四位专家又对这个映射结果进行了复核。 Each mapped keyword became a SQL complete, runnable SQL rule for every constraint found. 每一个映射好的关键词都变成了一个带有空位的SQL模板，空位留给具体的列名、表名和约束值，随后一个ADL解析器会遍历每个原型的节点结构，提取出实际的约束内容——比如"0到1000"这样的范围、一个必填字段标记、一个术语代码集——并自动把这些空位填上，利用原型属性和数据库列之间预先建立好的映射关系，为发现的每一个约束生成一条完整、可直接运行的SQL规则。 So the flag itself is nothing exotic — it's still a null check, a range check, a code-set check, or a cardinality check — the contribution is entirely in deriving those checks automatically from schema metadata that already encodes them, rather than a human re-deriving the same constraint by hand from documentation. 所以标记本身并没有什么特别之处——它仍然只是一次空值检查、范围检查、代码集检查或出现次数检查——这篇论文的贡献完全在于，这些检查是直接从本来就编码了这些约束的模式元数据中自动推导出来的，而不是由人类从文档中重新手动推导出同样的约束。 Here's where I'd push on the evaluation design, though — the "gold standard" they compare against is a second set of DQRs hand-written by two experts from the same CARSES (Chinese Application-Level Ranking Standard for EHR Systems, 中国电子病历系统应用水平分级标准，一份由中国国家卫生健康委员会发布的官方标准) requirements and the same database schema, which means a high agreement score partly measures whether the archetypes were well-designed enough to already encode what a human would write by hand from the same source material, not whether either rule set actually catches real errors in real patient data. 不过这里我想对评估设计提出一点不同看法——他们用来比较的"黄金标准"，是两位专家依据同一份CARSES（中国电子病历系统应用水平分级标准，中国国家卫生健康委员会发布的官方标准）要求和同一个数据库模式手写出的第二套DQR，这意味着高一致性得分，一部分衡量的是原型设计是否足够完善、本来就已经编码了人类依据同一份源材料会手写出的内容，而不是衡量这两套规则中任何一套是否真的能在真实患者数据中捕捉到真实的错误。 Neither rule set was actually run against real data with known injected errors or adjudicated cases — this is a rule-coverage comparison, not a detection-accuracy study.

JORDAN And what did the results actually show? 那结果具体显示了什么？

ALEX Using 27 archetypes mapped to CARSES's 253 data elements, the automatic method generated 359 rules against the experts' 366, and 311 of those auto-generated rules matched the expert rules both in execution result and semantic expression, giving an overall coverage of 84.97%. 利用27个映射到CARSES 253个数据元素上的原型，自动方法生成了359条规则，对照专家的366条，其中311条自动生成的规则在执行结果和语义表达上都与专家规则相符，总体覆盖率达到84.97%。 Coverage was uneven across the four CARSES dimensions: a perfect 100% on consistency and 98.11% on completeness, since those map cleanly onto single-attribute code-set and null checks that archetypes represent well, but only 54.02% on conformity and 50% on timeliness, because those dimensions often require logic spanning multiple elements — a computed value matching a formula, or one timestamp preceding another — which the archetype definition language the authors used doesn't natively express. 四个CARSES维度上的覆盖率并不均衡：一致性（consistency）达到完美的100%，完整性（completeness）达到98.11%，因为这两者能干净地对应到原型表达得很好的单属性代码集和空值检查，但一致性（conformity，原文此处为符合性/conformity维度）只有54.02%，及时性（timeliness）只有50%，因为这些维度常常需要跨越多个元素的逻辑——比如一个计算值要符合某个公式，或某个时间戳要早于另一个时间戳——而作者所使用的那个版本的原型定义语言本身并不能直接表达这类逻辑。 This null result is itself informative: automatic rule generation from a CIM is strong exactly where constraints are single-attribute and structural, and weak exactly where a check needs multi-element computation — which maps closely onto the gap between a simple bound check and the kind of statistical plausibility check a spline mixed-effects flagging model is actually built to catch. 这个"未达标"的结果本身也颇具信息量：从CIM自动生成规则，恰恰在约束是单属性、结构性的地方表现强劲，又恰恰在检查需要跨多元素计算的地方表现薄弱——这正好对应了简单范围检查，和一个样条混合效应（spline mixed-effects）标记模型真正要捕捉的那类统计可信度检查之间的差距。

JORDAN What else did the paper flag as a limitation, beyond the conformity and timeliness gap? 除了一致性和及时性方面的差距之外，论文还指出了哪些其他局限？

ALEX Three of the expert-created rules required checking that a plain-text field — specifically the first page of the electronic medical record — actually contained certain required content, and none of those three were covered by the automatic method at all, because determining whether free text satisfies a semantic requirement needs natural language processing (NLP, 自然语言处理，一种让计算机理解和处理人类语言文本的技术), not a structural constraint an archetype can express. 专家创建的规则中有三条，要求检查某个纯文本字段——具体是电子病历的首页——是否真的包含了某些必需的内容，而这三条规则自动方法完全没有覆盖到，因为判断自由文本是否满足某项语义要求，需要用到自然语言处理（NLP，natural language processing，一种让计算机理解和处理人类语言文本的技术），而不是原型能够表达的结构性约束。 The authors are also upfront that the whole approach is only as good as the archetypes themselves — a poorly designed clinical information model will produce poorly covering auto-created rules, so this isn't a free lunch independent of how much care went into the underlying schema design. 作者们也坦率地承认，整套方法的好坏完全取决于原型本身的质量——一个设计不良的临床信息模型，会产生覆盖率不佳的自动创建规则，所以这并不是一顿与底层模式设计用心程度无关的"免费午餐"。 And separately, the specific SQL-based rules they generated are tied to this hospital's particular archetype-relational-mapping (ARM, 原型关系映射，一种把openEHR原型持久化到关系型数据库的具体方案) database persistence choice, so the generated rules themselves wouldn't port directly to a differently-structured database even if the underlying archetypes were identical — only the general methodology would transfer. 另外，他们生成的那些具体SQL规则，是和这家医院特定的原型关系映射（ARM，archetype relational mapping，一种把openEHR原型持久化到关系型数据库的具体方案）数据库持久化方案绑定在一起的，所以即便底层原型完全相同，生成出来的规则本身也无法直接迁移到结构不同的数据库上——只有背后的通用方法论才能迁移。

JORDAN So which part of a flagging pipeline does this actually touch? 那它到底触及了标记流水线中的哪个环节？
