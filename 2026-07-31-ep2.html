Track B — Carrot: map sensitive data to OMOP without ever touching the data

Blurb. Cox et al. (JMIR Research Protocols, 2025) describe Carrot, an open-source (MIT, GitHub) toolset from Nottingham/Dundee that converts sensitive health datasets to the OMOP Common Data Model while the mapping team never accesses the underlying data. The architecture splits the job into two packages that never share data: Carrot-Mapper (Django + React + PostgreSQL + Azure Functions) where OMOP experts build mapping rules from metadata only — a White Rabbit "scan report" listing tables, fields, and values with a minimum cell count of 5 — and Carrot-CDM (portable Python ETL) which runs inside the data owner's network and applies the rules to real data. Every rule is provenance-tagged M (manual) / V (vocabulary-based) / R (reuse), and a reusable rule corpus compounds across datasets. Evidence (as of July 2024): 60,269 completed mappings (6,159 manual, 45,316 vocabulary-automatic, 8,794 reuse) across 39 scan reports / 129 datasets / 13 projects; the CO-CONNECT deployment created 45,000+ rules and converted 5M+ patient records. Honest limits: reuse matching is exact-string only (typos/languages break it; LLMs flagged as future work), and no head-to-head efficiency benchmark was run. Ships code → satisfies Track-B code test. Buildable: registry-mapping-corpus — a metadata-only, provenance-tagged, reusable rule store for registry→OMOP mapping.

Plain-English glossary

  • Common Data Model (CDM) — a shared schema + vocabulary that different datasets are mapped onto so one analysis runs everywhere.（中文：把不同数据集映射到同一套结构和词表，使一次分析能到处运行。）
  • ETL (extract, transform, load) — the process of pulling source data, reshaping it, and loading it into the target model.（中文：提取源数据、重塑、再加载到目标模型的过程。）
  • GDPR / data protection — European/UK law governing use of personal data; drives the "no data access" design.（中文：欧盟/英国关于个人数据使用的法规，促成了“不访问数据”的设计。）
  • ICD / SNOMED-CT / LOINC — clinical vocabularies (diagnoses, rich clinical terms, lab tests) that OMOP maps between.（中文：临床词表——诊断、丰富临床术语、实验室检测——OMOP 在它们之间建立映射。）
  • OMOP — Observational Medical Outcomes Partnership Common Data Model, maintained by OHDSI.（中文：由 OHDSI 维护的观察性医疗结果合作组织通用数据模型。）
  • Scan report — a White Rabbit metadata profile (tables/fields/values) with rare values suppressed; the only thing that leaves the data owner's network.（中文：White Rabbit 生成的元数据画像，罕见取值被抑制；唯一离开数据方网络的东西。）
  • Splice site — n/a this episode.
  • Vocabulary automation (V-rule) — automatic OMOP mapping when a field is already coded in a recognized vocabulary; a deterministic lookup, not a judgment.（中文：字段已用已识别词表编码时的自动 OMOP 映射；是确定性查表而非判断。）

Full citation

Methods / tools to lift

  • Separation of concerns — rule authoring (metadata-only, central) fully decoupled from rule application (data-side, local); only metadata out + rules back cross the boundary.
  • Provenance-tagged rules (M/V/R) — every mapping records whether it was manual, vocabulary-derived, or reused; auditability for free.
  • Reusable rule corpus — verified rules auto-apply to new datasets on exact column+value match; efficiency compounds with corpus size.
  • Vocabulary automation — deterministic OMOP concept lookup for fields flagged as SNOMED/ICD/LOINC (>75% of completed mappings here).
  • Concept-drift feedback — surfaces when target concepts are ancestor/descendant of each other in the OMOP hierarchy, nudging convergence.
  • Incremental + streaming ETL (Carrot-CDM) — author rules once; apply to each new data cut, memory-independent — fits longitudinal/growing registries.
  • Privacy-by-design scan report — minimum cell count ≥5 + manual review ensures no re-identifying values leave the network.

Where it lands + buildable artifact

Serves AI-tooling / career (secondary: Liz / registry data quality, method only). Ends on the tool sketch — paste-ready MVP:

registry-mapping-corpus (M) — Input: a White-Rabbit-style scan report of a registry extract (metadata only: table/field names + value lists, no rows). Auto-apply (1) any previously human-verified rule whose column+value matches exactly, and (2) vocabulary lookups for fields flagged SNOMED/ICD/LOINC. Flag only novel/unmatched values for human mapping; tag every rule M/V/R; export a versioned JSON rules file. Never touches row-level data. Output: reusable, Git-tracked, reproducible mapping corpus + a per-field coverage report.

What to verify first

  • Reuse hit-rate — free-text or inconsistent local coding gives low exact-match reuse; measure honestly before promising efficiency.
  • V-rule safety — a mislabeled vocabulary tag makes the tool confidently emit wrong mappings; keep human sign-off on V-rules.
  • Privacy is load-bearing on the scan report — minimum-cell-count suppression + manual scan-report review must be verified, not assumed.
  • Governance lag — metadata-only requests may still hit institutions with no approval process for them (a real CO-CONNECT delay).
  • External data-modeling method; no claim about or access to any registry's internal structure.

ALEX Today's Track B paper is "Conversion of Sensitive Data to the OMOP Common Data Model: Protocol for the Development and Use of Carrot," by Samuel Cox and a large team out of the University of Nottingham and the University of Dundee. 今天 Track B 的论文是 Samuel Cox 与诺丁汉大学、邓迪大学的一个大团队发表的《把敏感数据转换到 OMOP 通用数据模型：Carrot 的开发与使用方案》。 It's in JMIR Research Protocols, 2025, open access, and — importantly for this track — it ships open-source code under an MIT license on GitHub. 它 2025 年发表在《JMIR Research Protocols》，开放获取，而且——对本 Track 很重要的一点——它以 MIT 许可在 GitHub 上发布了开源代码。 We're reading it because it solves a very specific, very real bottleneck: how do you standardize a sensitive health dataset without ever letting the standardizing team touch the data? 我们读它，是因为它解决了一个非常具体、非常真实的瓶颈：你如何在从不让标准化团队接触数据的前提下，把一个敏感的健康数据集标准化？

JORDAN Let me get the ground concepts first. 先让我把基础概念弄清楚。 What is OMOP, and what does "converting to a common data model" actually mean? 什么是 OMOP，“转换到通用数据模型”到底是什么意思？

ALEX OMOP is the Observational Medical Outcomes Partnership Common Data Model — a shared schema for health data, maintained by the OHDSI community. OMOP 是观察性医疗结果合作组织通用数据模型（一个由 OHDSI 社区维护的、健康数据的共享结构规范）。 The idea is that everyone's messy source data — different column names, different codes, different local conventions — gets mapped onto one standardized set of tables and one standardized vocabulary. 它的思路是把每个人杂乱的源数据——不同的列名、不同的编码、不同的本地习惯——映射到一套标准化的表和一套标准化的词表上。 So a diagnosis recorded as an ICD code in one hospital and a SNOMED-CT term in another both land on the same OMOP concept. 于是在一家医院记为 ICD 编码、在另一家记为 SNOMED-CT 术语的同一个诊断，最终都落到同一个 OMOP 概念上。 ICD is the International Classification of Diseases; SNOMED-CT is a much richer clinical terminology — both are vocabularies, and OMOP maps between them. ICD 是国际疾病分类；SNOMED-CT 是一套丰富得多的临床术语——两者都是词表，而 OMOP 在它们之间建立映射。 Once your data is in OMOP, an analysis written once runs against any OMOP database anywhere. 一旦你的数据变成 OMOP 格式，一个只写一次的分析就能在任何地方的任意 OMOP 数据库上运行。

JORDAN That sounds like pure upside. 这听起来全是好处。 Where's the catch? 那障碍在哪里？

ALEX The catch is the mapping itself. 障碍就在映射本身。 Converting source data to OMOP is what the authors call an "art form" — different curators make different, defensible choices, and it takes deep OMOP expertise. 把源数据转换到 OMOP 被作者称为一种“手艺活”——不同的审校者会做出不同但都说得通的选择，而且它需要深厚的 OMOP 专业知识。 The extract-transform-load process, ETL, is the technical heart of it. 提取-转换-加载的过程，即 ETL，是它技术上的核心。 OHDSI already ships tools: White Rabbit profiles a dataset and produces a metadata report, and Rabbit-in-a-Hat lets an engineer note down the intended transformations. OHDSI 已经提供了工具：White Rabbit 对数据集做画像并生成一份元数据报告，Rabbit-in-a-Hat 让工程师把打算做的转换记录下来。 But there's a "final mile" gap — turning those notes into runnable code still needs a local expert writing SQL or scripts. 但存在一个“最后一公里”的缺口——把那些笔记变成能运行的代码，仍然需要一个本地专家去写 SQL 或脚本。 And here's the real friction: the person doing the mapping traditionally needs to see the data, which under GDPR and the UK Data Protection Act drags in heavy governance. 而真正的摩擦在这里：做映射的人传统上需要看到数据，而根据 GDPR（通用数据保护条例）和英国《数据保护法》，这会牵扯出繁重的治理流程。

JORDAN So the expensive, scarce resource is OMOP expertise, and the legal blocker is that expertise usually requires data access. 所以昂贵而稀缺的资源是 OMOP 专业知识，而法律上的障碍是这种专业知识通常需要数据访问权限。 Carrot's trick is to break that link? Carrot 的招数就是切断这个联系？

ALEX Precisely, and that's the whole architecture. 正是如此，而这就是整个架构。 They split the problem into two separate software packages that never share the data. 他们把问题拆成两个从不共享数据的独立软件包。 The first, Carrot-Mapper, is a web application where OMOP experts build mapping rules — but they only ever see metadata, never a single row of patient data. 第一个是 Carrot-Mapper，一个网页应用，OMOP 专家在里面构建映射规则——但他们只看得到元数据，从不接触任何一行患者数据。 The second, Carrot-CDM, is a Python ETL tool that lives inside the data owner's own network and applies those rules to the actual data. 第二个是 Carrot-CDM，一个 Python 的 ETL 工具，它驻留在数据所有者自己的网络内，把那些规则应用到真实数据上。 Carrot-Mapper is built on Django and React with a PostgreSQL database and serverless Azure Functions; Carrot-CDM is a portable Python package the data partner installs locally. Carrot-Mapper 用 Django 和 React 构建，配 PostgreSQL 数据库和无服务器的 Azure Functions；Carrot-CDM 则是数据合作方在本地安装的一个可移植 Python 包。 The separation is the whole point — rules flow out, data never does. 这个分离就是核心所在——规则流出去，数据永远不出去。

JORDAN Walk me through what actually moves between the two sides. 带我看看两边之间实际传递的是什么。

ALEX There's a clean six-step pipeline. 有一个清晰的六步流水线。 One, the data partner preprocesses and de-identifies their data locally. 第一，数据合作方在本地对数据做预处理和去标识化。 Two, they run White Rabbit to produce a scan report — an Excel file listing every table, field, and the values present, with a minimum cell count of five so rare, possibly re-identifying values are suppressed. 第二，他们运行 White Rabbit 生成一份扫描报告——一个 Excel 文件，列出每张表、每个字段和其中出现的取值，并设最小单元计数为五，从而抑制掉罕见的、可能导致重新识别的取值。 Three, only that metadata scan report leaves their network. 第三，只有那份元数据扫描报告离开他们的网络。 Four, the OMOP experts upload it to Carrot-Mapper and build rules against the metadata. 第四，OMOP 专家把它上传到 Carrot-Mapper，针对元数据构建规则。 Five, the finished rules — a JSON file — go back to the data partner. 第五，做好的规则——一个 JSON 文件——回传给数据合作方。 Six, Carrot-CDM applies those rules locally to transform the real data into OMOP. 第六，Carrot-CDM 在本地应用这些规则，把真实数据转换成 OMOP。 The only two things that ever cross the boundary are a de-identified metadata report going out and a rules file coming back. 唯一跨越边界的两样东西，是出去的一份去标识化元数据报告，和回来的一个规则文件。

JORDAN And the rules — how much of that is a human clicking through by hand? 那这些规则——有多少是人工一条条点出来的？

ALEX Less than you'd fear, and this is the part I like most. 比你担心的要少，而这是我最喜欢的部分。 Every rule is tagged by how it was generated: M for manual, V for vocabulary-based, and R for reuse. 每条规则都按生成方式打了标签：M 表示手动，V 表示基于词表，R 表示复用。 Vocabulary-based means that when the metadata says a field is encoded in a recognized vocabulary like SNOMED, the system automatically emits the correct OMOP concept mappings — which for a field with thousands of unique values can save days of error-prone work. 基于词表的意思是：当元数据表明某字段用了像 SNOMED 这样被识别的词表时，系统会自动生成正确的 OMOP 概念映射——对于一个有成千上万个唯一取值的字段，这能省下好几天容易出错的工作。 Reuse means a previously human-approved rule gets automatically applied to a new dataset when the column name and value match. 复用的意思是：当列名和取值都匹配时，一条此前经人工批准的规则会被自动应用到新数据集上。 So the mapping corpus compounds — the more you map, the less new manual work each dataset needs. 于是映射的语料库会累积复利——你映射得越多，每个新数据集需要的新手动工作就越少。 The provenance tags mean you can always see exactly how any given rule came to be. 这些溯源标签意味着你随时能看清任何一条规则是怎么来的。

JORDAN Does the applying tool handle data that keeps growing? 那个应用规则的工具能处理不断增长的数据吗？ Registries aren't static — new patients and new visits arrive constantly. 注册库不是静态的——新患者和新就诊在持续到来。

ALEX It does, and that's a detail worth flagging for longitudinal work. 能处理，而这是一个对纵向工作值得标注的细节。 Carrot-CDM handles both a one-time conversion and incremental transformation of an expanding dataset using the same rules. Carrot-CDM 既能做一次性转换，也能用同一套规则对不断扩展的数据集做增量转换。 It can watch for new data and transform it immediately, or run on a schedule, and it supports streaming, so working memory isn't the limit on dataset size. 它可以监视新数据并立即转换，也可以按计划运行，而且支持流式处理，所以内存不是数据集规模的上限。 For a registry that grows year over year, that means you author the mapping rules once and they keep applying to each new cut of data. 对一个逐年增长的注册库来说，这意味着你只需编写一次映射规则，它们就会持续应用到每一批新数据上。 That "author once, apply forever" property is what makes the rule corpus worth investing in. 这种“一次编写、永久应用”的特性，正是让规则语料库值得投入的原因。

JORDAN You mentioned the corpus compounds. 你提到语料库会产生复利。 Is there anything that keeps all those independently-built rules from drifting apart into inconsistency? 有没有什么机制防止那些独立构建的规则各自漂移、变得不一致？

ALEX There's a nice quiet feature for exactly that. 恰好有一个不动声色的小功能。 Carrot-Mapper has an internal tool that flags when the target concepts chosen across a dataset corpus are misaligned — specifically when one mapping targets a concept that is an ancestor or descendant of another target in OMOP's hierarchy. Carrot-Mapper 有一个内部工具，会在整个数据集语料库所选的目标概念出现错位时给出提示——具体来说，是当一个映射指向的概念，在 OMOP 的层级结构中是另一个目标的上位或下位概念时。 In plain terms, if one curator mapped a value to "asthma" and another to "childhood asthma," the tool surfaces that inconsistency so the team can converge. 说白了，如果一个审校者把某个取值映射到“哮喘”，另一个映射到“儿童哮喘”，工具会把这个不一致暴露出来，让团队去收敛统一。 It doesn't force a choice — it just puts the potential inconsistency in front of the user for free. 它不强制做选择——只是免费地把潜在的不一致摆到用户面前。 That's a cheap, high-value pattern: surface drift as feedback rather than trying to prevent it up front. 这是一个廉价而高价值的模式：把漂移作为反馈暴露出来，而不是试图事前防止它。

ALEX I want to push on one design choice, though. 不过我想质疑一个设计选择。 The reuse-matching algorithm is deliberately simple — it only fires on an exact match of both column name and value. 这个复用匹配算法是有意做得很简单——它只在列名和取值都完全一致时才触发。 A single typo, "Gendar" instead of "Gender," or a different language, and the match silently fails and a human has to redo the work. 一个拼写错误，把 "Gender" 写成 "Gendar"，或者换一种语言，匹配就会悄无声息地失败，然后人得重做这份工作。 The authors are honest about this and flag large language models as future work for smarter matching. 作者对此很坦诚，并把大语言模型标为未来工作，用于更智能的匹配。 I think that's the right instinct but also the risky one — fuzzy or LLM matching would raise reuse rates but reintroduces the exact silent-error problem the exact-match rule was avoiding. 我认为这个方向是对的，但也是有风险的——模糊匹配或 LLM 匹配会提高复用率，但会重新引入那个精确匹配本来在规避的“悄无声息的错误”问题。

JORDAN What does the evidence look like — has anyone actually run this at scale? 证据长什么样——真的有人大规模跑过吗？

ALEX Yes, and the numbers are the paper's spine. 有，而这些数字是整篇文章的支柱。 As of July 2024, the central Carrot-Mapper instance had produced mappings for 39 scan reports across 129 dataset objects and 13 projects. 截至 2024 年 7 月，中央的 Carrot-Mapper 实例已为 129 个数据集对象、13 个项目中的 39 份扫描报告生成了映射。 That's 60,269 completed mappings, broken down as 6,159 manual, 45,316 automatic from vocabularies, and 8,794 from reuse — with another 92,071 in progress. 这是 60,269 条已完成的映射，其中 6,159 条手动、45,316 条来自词表自动生成、8,794 条来自复用——另有 92,071 条正在进行中。 So over 75% of finished mappings came from vocabulary automation, and nearly 60% of the non-automatic ones came from reuse rather than fresh manual work. 也就是说，超过 75% 的已完成映射来自词表自动化，而在非自动的那部分里，将近 60% 来自复用而非全新手动工作。 The flagship deployment, the CO-CONNECT COVID data platform, used Carrot to create over 45,000 rules and convert more than five million patient records — all without the mapping team ever accessing the underlying data. 旗舰部署是 CO-CONNECT 这个新冠数据平台，它用 Carrot 创建了 4.5 万多条规则、转换了 500 多万条患者记录——而且映射团队自始至终没有接触过底层数据。

JORDAN Is there anything they're careful not to claim? 有没有什么是他们谨慎地不去声称的？

ALEX Two honest limits. 两个诚实的界限。 First, they explicitly did not run a head-to-head comparison against the conventional data-access approach, so they make no claim that Carrot is faster or cheaper — only that it works and preserves privacy. 第一，他们明确没有和传统的“给数据访问权限”方法做正面对比，所以他们不声称 Carrot 更快或更便宜——只声称它能用且保护隐私。 Second, the metadata-only model created its own governance friction, because many organizations had no existing process for approving even low-risk metadata requests, which delayed some work. 第二，这种“只看元数据”的模式制造了它自己的治理摩擦，因为许多机构根本没有审批哪怕是低风险元数据请求的现成流程，这拖慢了部分工作。 That second point is a genuinely useful warning — a technically elegant privacy boundary can still hit an institutional wall that hasn't caught up to it. 第二点是一个真正有用的提醒——一个技术上优雅的隐私边界，仍然可能撞上一堵尚未跟上它的制度之墙。

JORDAN One thing before we map it over. 在我们把它迁移过来之前先问一件事。 Why is the vocabulary-automation share so high — over 75%? 为什么词表自动化的占比这么高——超过 75%？ Is that a fluke of these particular datasets? 这是这些特定数据集的偶然吗？

ALEX It's not a fluke, and it tells you where the leverage is. 这不是偶然，而它告诉你杠杆在哪里。 When source fields are already coded in a standard vocabulary — SNOMED, ICD, LOINC — the mapping to OMOP is a deterministic lookup, not a judgment call. 当源字段已经用标准词表编码时——SNOMED、ICD、LOINC——到 OMOP 的映射就是一次确定性的查表，而不是一个需要判断的决定。 So the more of your data that arrives already coded, the more of the conversion collapses into free automation. 所以你的数据里已经编码的部分越多，转换过程中就有越多环节坍缩成免费的自动化。 The expensive human judgment concentrates on the free-text and locally-coded fields — which, for a clinical registry, is exactly where the hard, interesting phenotype definitions live. 昂贵的人工判断集中在自由文本和本地编码的字段上——而对一个临床注册库来说，这恰恰是那些困难又有趣的表型定义所在之处。 That split — deterministic lookup for coded data, human effort for the messy remainder — is the same separation-of-concerns philosophy running one level down. 这种切分——对已编码数据做确定性查表、对杂乱的其余部分投入人力——是同一个“关注点分离”哲学在下一个层级上的体现。
