Show Notes — Track B — 2026-07-02

Blurb

Henke et al. (BMC Med Inform Decis Mak 2024, open access) turn OHDSI's coarse four-step OMOP onboarding into a followable nine-step data-harmonization process, derived from a structured literature review of 23 papers (162 hits → 23 included; three reviewers, Fleiss κ = 0.764). The nine steps, in generic order: dataset specification, data profiling, vocabulary identification, coverage analysis of vocabularies, semantic mapping, structural mapping, ETL-process, qualitative data quality analysis, quantitative data quality analysis. Three steps are mandatory (present in all 23 papers): semantic mapping, structural mapping, ETL. Seven OHDSI tools are mapped to steps (WhiteRabbit, Athena, Usagi, RabbitInAHat, Achilles, Data Quality Dashboard, Atlas) but each appeared in <half the papers — tooling is helpful, not required. Ordering varied by source type (clinical vs claims vs combined); only dataset specification (step 1) and ETL (step 7) never moved, and the process is explicitly iterative. Where it lands: AI-tooling / career (secondary: Liz / data quality) — a harmonization-process linter that checks a project config against the nine-step template. Read full text (OA via BioC PMC-OA).

Plain-English glossary

  • Claims data — billing records from insurers; shallow in clinical detail but longitudinal across a person's encounters.（中文：理赔数据——保险方的账单记录，临床细节浅，但能纵向覆盖一个人的多次就诊。）
  • Common Data Model (CDM) — a fixed database schema plus standard vocabulary that many institutions reshape their data into, so one analysis runs everywhere.（中文：通用数据模型——一套固定表结构加标准词表，各机构把数据重塑成它，从而让同一个分析到处都能跑。）
  • ETL (Extract-Transform-Load) — the pipeline that reads source data, reshapes it, and writes it into the target database.（中文：ETL——读入源数据、重塑、再写入目标数据库的管道。）
  • FHIR — Fast Healthcare Interoperability Resources; a standard for exchanging a patient's clinical data between systems.（中文：FHIR——快速医疗互操作性资源，一个在系统间"交换"患者临床数据的标准。）
  • OHDSI — Observational Health Data Sciences and Informatics; the open community that maintains OMOP and its tools.（中文：OHDSI——观察性健康数据科学与信息学社区，维护OMOP及其工具。）
  • OMOP CDM — OHDSI's common data model for observational health data.（中文：OMOP CDM——OHDSI用于观察性健康数据的通用数据模型。）
  • Semantic mapping — mapping local codes to OMOP standard concepts so meaning is shared (via Usagi + the Athena vocabulary).（中文：语义映射——把本地代码映射到OMOP标准概念以共享含义（借助Usagi和Athena词表）。）
  • Structural mapping — reshaping source data into OMOP's table/field layout (via RabbitInAHat).（中文：结构映射——把源数据重塑成OMOP的表/字段布局（借助RabbitInAHat）。）
  • Syntactic vs semantic interoperability — syntactic = same shape (tables, formats); semantic = same meaning (shared concept codes).（中文：句法互操作性=形状相同（表、格式）；语义互操作性=含义相同（共享概念代码）。）
  • Data quality: qualitative vs quantitative — qualitative checks plausibility/conformance/completeness (Kahn framework; Achilles, DQD); quantitative checks that record counts survived the transform.（中文：定性质量检查合理性/符合性/完整性（Kahn框架；Achilles、DQD）；定量质量检查记录数在转换中是否守恒。）

Full citation

Henke E, Zoch M, Peng Y, Reinecke I, Sedlmayr M, Bathelt F. Conceptual design of a generic data harmonization process for OMOP common data model. BMC Med Inform Decis Mak. 2024;24(1):58. PMID: 38408983 · PMC: PMC10895818 · DOI: 10.1186/s12911-024-02458-7

Methods / tools to lift

  • Nine-step harmonization template — dataset specification → data profiling → vocabulary identification → coverage analysis → semantic mapping → structural mapping → ETL → qualitative DQ → quantitative DQ; mandatory core = semantic mapping + structural mapping + ETL.
  • Count-reconciliation (quantitative DQ) — verify source record counts match OMOP record counts per variable, over time, and against null counts — the most portable habit for any schema-to-schema move.
  • Coverage analysis — before transform, check which source coding systems even exist in the target vocabulary, to avoid silently dropping unmapped data.
  • OHDSI toolchain — WhiteRabbit (profiling), Athena (vocab repo), Usagi (semantic mapping), RabbitInAHat (structural mapping), Achilles + Data Quality Dashboard (qualitative DQ), Atlas (cohort/quantitative checks).
  • Structured review rigor — Fleiss kappa on a 20% double-screened sample before splitting reviewer workload.

Where it lands + buildable artifact

  • Priority: AI-tooling / career (secondary: Liz / data quality).
  • Artifact — harmonization-process linter (S): input a harmonization project's config or pipeline manifest; check it against the nine-step template; flag present/missing steps, confirm the three mandatory steps (semantic mapping, structural mapping, ETL) exist, and verify the two DQ steps run after ETL rather than being skipped. Output a compliance report. Tool list configurable, not hard-coded. External method only — no registry internals.

What to verify first

  • Generalization — derived from 23 papers, only 5 with claims data; registry data was excluded entirely. Check the steps/order hold for a registry source before treating the template as authoritative.
  • Descriptive ≠ optimal — the order is the most-frequent-in-literature, not a proven-best order; the authors' own FHIR structural-vs-semantic counterexample shows it can be locally wrong.
  • Tool snapshot — tool-to-step mapping reflects a 2023 search; keep the tool list configurable.
  • No registry internals asserted or required anywhere.

ALEX OHDSI is the Observational Health Data Sciences and Informatics community — an open collaborative that maintains standards and tools for analyzing real-world health data.
