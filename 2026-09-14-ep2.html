How did this episode land for you?

Ep2 (Track B) — Kineret: transforming Israel's largest government hospital network into the OMOP common data model

Blurb. Kineret is a national-scale case study of converting a heterogeneous, multi-institution clinical data landscape — 25 government hospitals in Israel, running a mix of legacy EHR systems, much of it Hebrew-language documentation with no standard vocabulary mapping — into the OMOP Common Data Model, using the open-source OHDSI toolchain (ATLAS, USAGI, Achilles, DQD). The paper is a pure infrastructure-and-governance story with zero genetic content: an on-premise de-identification and hashed-ID pipeline feeds AWS-based ETL orchestrated with Airflow, terminology mapping combines an automated model (>0.9 accuracy on ~85% of terms) with expert manual review (USAGI) for the rest, and a full-refresh update strategy keeps historical data consistent as vocabularies and source records change. As of 2025, six of 25 institutions are fully integrated (a seventh in final stages), with over 64,000 source codes mapped to ~33,000 standard concepts across a database with 1.36 billion measurement rows and 6.8 million persons. Governance took as long as the engineering: a two-forum structure (Economic Regulation Committee, Research Forum) and roughly 18 months of trust-building preceded cross-institutional data access. It lands on the AI-tooling/career-aligned track: the buildable artifact is a small, portfolio-scale demonstration of OHDSI's Data Quality Dashboard against a CF-registry-shaped synthetic dataset, not a proposal to convert CFFPR itself to OMOP.

Plain-English glossary

  • OMOP CDM (Observational Medical Outcomes Partnership Common Data Model) — a standardized relational schema for storing clinical data, so records from different source systems and hospitals share the same table structure, field names, and coding conventions.（中文：观察性医疗结局伙伴关系通用数据模型，一种标准化的关系型数据架构，使来自不同源系统和医院的记录共享相同的表结构、字段名和编码规范。）
  • OHDSI (Observational Health Data Sciences and Informatics) — the international open-source collaborative that maintains the OMOP CDM standard and its supporting tool ecosystem.（中文：观察性健康数据科学与信息学，维护OMOP CDM标准及其配套工具生态的国际开源协作组织。）
  • ATLAS — OHDSI's web-based tool for defining patient cohorts and running exploratory characterization against an OMOP database without hand-written SQL.（中文：OHDSI提供的网页端工具，用于定义患者队列并对OMOP数据库进行探索性特征分析，无需手写SQL。）
  • USAGI — OHDSI's terminology-mapping tool, used by domain experts to match local codes/descriptions to standardized OMOP concepts.（中文：OHDSI的术语映射工具，供领域专家将本地编码/描述匹配到标准化OMOP概念。）
  • Achilles — an OHDSI tool that automatically characterizes a loaded OMOP database (patient counts, age distributions, concept frequencies).（中文：OHDSI的自动化工具，用于对已加载的OMOP数据库进行特征描述，如患者数量、年龄分布、概念出现频率等。）
  • Data Quality Dashboard (DQD) — an OHDSI tool that runs a standard battery of plausibility and conformance checks against an OMOP database and reports pass/fail rates.（中文：OHDSI的数据质量仪表盘，对OMOP数据库运行一整套标准化的合理性与一致性检查，并报告通过/失败率。）
  • ETL (extract, transform, load) — the pipeline pattern of pulling data from a source system, restructuring/recoding it, and loading it into a target schema.（中文：提取-转换-加载，指从源系统提取数据、进行重构/重新编码，再加载到目标架构中的流程模式。）
  • Airflow — an open-source workflow orchestration tool used to schedule and chain together the steps of a data pipeline.（中文：一款开源工作流编排工具，用于调度并串联数据管道中的各个处理步骤。）

Methods / tools to lift

  • ATLAS / USAGI / Achilles / DQD (OHDSI toolchain) — a complete, open-source, already-built stack for cohort definition, terminology mapping, characterization, and automated data-quality auditing on any OMOP-shaped dataset.
  • Hashed, de-identified patient ID generated on-premise — a reusable pattern for cross-table record linkage without exposing a national ID or other direct identifier.
  • Full-refresh (rather than incremental delta) update strategy — periodically re-running the entire ETL to keep historical records consistent as vocabularies and source data are retrospectively corrected.
  • Separate non-OMOP data pipeline — extracting unstructured data (images, ECGs, PDFs) only on a per-study basis, linked to de-identified visits, stored in the study's own virtual research room rather than centrally.
  • Two-forum governance structure — an Economic Regulation Committee (financial) and Research Forum (clinical/scientific), each with cross-institutional representation, as a reusable pattern for multi-site data-sharing governance.

Where it lands + buildable artifact

Serves AI-tooling / bioinformatics infrastructure, career-aligned. Tool sketch: a standalone script that runs OHDSI's open-source Data Quality Dashboard (DQD) against a small synthetic or public-sample OMOP-shaped dataset constructed to mimic CF-registry-style variables (height, weight, FEV1, encounter dates), producing a completeness-and-plausibility report as a demonstrable, portfolio-ready artifact. This does not propose converting CFFPR to OMOP or make any claim about CFFPR's current structure. Difficulty: S (DQD is open-source and documented; the work is shaping a representative synthetic dataset and writing up what the output would mean for a registry-QC use case).

What to verify first

  • How OHDSI's DQD/Achilles checks are actually configured and thresholded in this paper's deployment — the authors mention "many more tests" including a source-vs-target quantity comparison, without fully enumerating them.
  • Whether the reported >0.9 automated terminology-mapping accuracy was validated against a held-out expert-labeled sample or only spot-checked — the true error rate on the "automated" 85% could be higher than reported if the latter.
  • That an LLM- or embedding-based mapping approach's performance on Hebrew hospital-specific vocabulary is not necessarily representative of how it would perform on a different registry's own variable definitions.
  • Nothing here implies any decision about whether or when CFFPR might adopt OMOP or any particular common data model — that is an institutional question outside this episode's scope.

JORDAN What are the headline numbers? 主要数字是什么？
