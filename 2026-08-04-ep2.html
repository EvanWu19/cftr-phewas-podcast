Show notes — Track B — 2026-08-04

The AIR·MS data platform for artificial intelligence in healthcare — Guerrero P, Ernebjerg M, Holst T, Weese D, DiBello H, Ibing S, Schmidt L, Ungaro R, Renard B, Lippert C, Alleva E, Quinn TD, Kovatch P, Antao EM, Heyneke E, Rasheed A, Kalabakov S, Arnrich B, Charney A, Wieler LH, Nadkarni G. JAMIA Open, 2025.

Blurb

AIR·MS is Mount Sinai's AI-ready clinical data platform, built by the Hasso Plattner Institute for Digital Health at Mount Sinai (a three-way US/Germany/nonprofit collaboration): a daily ETL pipeline maps Epic EHR data onto OMOP-CDM and OHDSI standard vocabularies into an in-memory SAP HANA database (>12M patients, 2TB compressed in RAM), with unstructured pathology, radiology, ECG, and genomic metadata linked in and raw files kept on the Minerva HPC cluster (2 petaflops). An Azure-based application tier hosts Data2Evidence (interactive cohort exploration), Visian (image annotation), and TURTLE, an LLM-powered natural-language-to-SQL query assistant. Query benchmarks against 11 OHDSI Phenotype Library cohort definitions showed 9/11 completing under a 10-second UX threshold, and three research use cases — Crohn's phenotyping, a 56,799-patient dysmenorrhea cohort linking it to previously unrecognized ischemic heart disease risk, and an ongoing federated cardiovascular-risk model — demonstrate the platform in production. For us this lands on AI-tooling/career: it's the clearest published reference architecture for registry-scale AI-ready infrastructure, but TURTLE's LLM-to-SQL layer reports no accuracy/validation metric — exactly the gap a buildable registry query assistant, with its own validated-benchmark check, should fill.

Plain-English glossary

  • OMOP-CDM — Observational Medical Outcomes Partnership Common Data Model; a standardized schema (maintained by the OHDSI consortium) that maps any hospital's local codes into one fixed set of tables and vocabularies (SNOMED-CT, LOINC, RxNorm) so the same query can run against any mapped database.（中文：观察性医疗结果合作项目通用数据模型——由 OHDSI 联盟维护的标准化模式，把任何医院的本地编码映射进一套固定的表结构和词表（SNOMED-CT、LOINC、RxNorm），使同一查询可跑在任何已映射的数据库上。）
  • OHDSI — Observational Health Data Sciences and Informatics; the international consortium behind OMOP-CDM and the federated research-network model built on it.（中文：观察性健康数据科学与信息学联盟——OMOP-CDM 及其上联邦式研究网络模式背后的国际联盟。）
  • ETL (extract-transform-load) — the pipeline that pulls raw source data, reshapes it, and loads it into a target database/schema.（中文：抽取—转换—加载——把原始源数据抽取出来、重塑格式、再载入目标数据库或模式的流程。）
  • De-identification (Safe Harbor / shift-and-truncate) — HIPAA-compliant method used here: per-patient random salt + SHA-256 hashing of identifiers, plus a random 1–366 day timestamp shift applied uniformly to a patient's whole record.（中文：去标识化（安全港／平移—截断法）——本文使用的符合 HIPAA 的方法：每位患者随机加盐并用 SHA-256 哈希其标识符，并对该患者全部记录统一施加 1 到 366 天的随机时间偏移。）
  • In-memory columnar database — a database (here, SAP HANA) that keeps compressed data in RAM organized by column rather than row, enabling fast interactive analytical queries.（中文：内存列式数据库——本文中的 SAP HANA，将压缩数据按列而非按行组织并保存在内存中，支持快速的交互式分析查询。）
  • DICOM — the standard file format and metadata schema for medical imaging (radiology).（中文：医学影像（放射科）标准文件格式与元数据规范。）
  • Federated learning — training a shared model across multiple institutions' data without moving the raw data itself between them.（中文：联邦学习——在多个机构的数据上训练一个共享模型，而无需在机构间移动原始数据本身。）

Methods / tools to lift

  • OMOP-CDM + OHDSI standard vocabularies — the mapping layer that makes cross-site, cross-database queries portable.
  • datapilot — custom ETL orchestration tool built on open-source Apache Airflow + NiFi.
  • OHDSI Data Quality Dashboard (DQD) — standardized data-quality checks run on top of OMOP-CDM tables.
  • OHDSI Phenotype Library — 500+ standardized, pre-validated cohort definitions, used here both as a query-performance benchmark and (in our buildable artifact) as ground truth for validating LLM-generated SQL.
  • TURTLE — LLM-based conversational natural-language-to-SQL interface for OMOP cohort queries (no reported accuracy metric — a gap, not a template to copy as-is).

Where it lands + buildable artifact

Serves: AI-tooling/career (+ Liz data-quality, method only). MVP (paste-ready): A registry query assistant — LLM generates SQL from a natural-language cohort question against an OMOP schema (schema-grounded few-shot prompting, strictly read-only execution); before any generated query is trusted, check it against a small curated set of standardized cohort definitions with known-correct answers (OHDSI Phenotype Library-style ground truth); flag anything that can't be benchmarked for manual review. Input: NL question + OMOP schema. Output: generated SQL + plain-English restatement + confidence flag vs. nearest validated reference query. Difficulty: M.

What to verify first

  • LLM-to-SQL accuracy — TURTLE reports no accuracy/validation metric; don't assume "LLM writes correct SQL for a clinical database" is solved just because a demo works.
  • Data completeness skew — even in a 12M-patient platform, only 43% of patients have any measurement and 29% any medication record; any registry-tooling analog needs its own completeness audit, not an assumption of uniform depth.
  • Vendor-specific architecture — SAP HANA/Azure/datapilot are proprietary/enterprise-scale choices; the transferable value is the architecture pattern (unified metadata-linked multimodal DB + compute tier + app tier + governance), not the literal tooling.

ALEX OMOP-CDM stands for the Observational Medical Outcomes Partnership Common Data Model — it's a standardized schema maintained by the OHDSI consortium, short for Observational Health Data Sciences and Informatics, and its whole job is to take every hospital's messy, locally-coded data and force it into one fixed set of tables using one shared vocabulary. OMOP-CDM 全称是观察性医疗结果合作项目通用数据模型 (Observational Medical Outcomes Partnership Common Data Model)——这是由 OHDSI 联盟（观察性健康数据科学与信息学，Observational Health Data Sciences and Informatics）维护的一套标准化模式 (schema)，它的全部工作就是把每家医院杂乱的、本地编码的数据，硬塞进一套固定的表结构里，并统一使用同一套词表。 So a diagnosis gets mapped to a standard SNOMED-CT code, a lab result to LOINC, a medication to RxNorm, regardless of what the original hospital system called it — which means the exact same SQL query can, in principle, run unmodified against any OMOP-mapped database, whether it's in New York or Berlin. 于是一个诊断会被映射为标准的 SNOMED-CT 编码，一项检验结果映射为 LOINC，一种药物映射为 RxNorm，无论原始医院系统里叫什么名字——这意味着，原则上同一段 SQL 查询无需修改，就可以直接跑在任何经过 OMOP 映射的数据库上，不管它在纽约还是柏林。 That's the technical foundation the whole OHDSI federated-network model depends on. 这正是整个 OHDSI 联邦式网络模型所依赖的技术基础。 "Structured" data just means anything already sitting in a discrete, queryable field — a diagnosis code, a lab value, a medication order — while "unstructured" data, like a free-text clinical note or a radiology image, needs natural language processing or computer vision before a computer can search inside it at all. “结构化 (structured)”数据指的就是已经躺在离散、可查询字段里的东西——一个诊断编码、一个检验值、一条用药医嘱——而“非结构化 (unstructured)”数据，比如一段自由文本的临床记录或一张放射影像，则需要先经过自然语言处理 (NLP) 或计算机视觉处理，计算机才能在其中进行检索。 And de-identification here isn't just deleting a name — the paper describes a specific method: every patient gets a random salt, their identifiers are hashed with SHA-256, and every timestamp in their record is shifted by the same random offset of one to three hundred sixty-six days, calibrated to satisfy HIPAA's Safe Harbor standard while still allowing new data to be added incrementally without breaking the shift. 而这里的去标识化并不只是删掉姓名——论文描述了一套具体方法：每位患者分配一个随机盐值 (salt)，其标识符用 SHA-256 哈希，患者记录中的每一个时间戳都按同一个一到三百六十六天之间的随机偏移量整体平移，这一设计既满足 HIPAA 的“安全港 (Safe Harbor)”标准，又能在不破坏这一偏移的前提下持续增量添加新数据。
