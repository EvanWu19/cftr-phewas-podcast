Ep4 (Track C, paper 2 of 2) — Using a Data Quality Framework to Clean Data Extracted from the Electronic Health Record: A Case Study

Blurb. Direct companion to ep3: Dziadkowiec and colleagues (2016) take Kahn et al.'s (2012) five data-quality concepts -- attribute domain constraints, relational integrity, historical data, state-dependent objects, attribute dependency -- and run them as actual SPSS syntax against two real EPIC-extracted emergency-department datasets (70,061 adult-ED visits; 2,815,550 pediatric-ED visits). The state-dependent object rule check alone found 2,519 encounters with incorrect internal time sequences. To show this mattered, not just existed, the authors ran a Kruskal-Wallis ANOVA comparing medication-order-to-administration time across five ED sites before and after correcting those encounters: both versions found an overall significant difference, but the pairwise, Bonferroni-adjusted site comparisons changed substantially -- several differences significant in the uncorrected data disappeared after correction. The lesson: in large EHR extracts, uncorrected sequence errors don't just add noise, they can manufacture or erase specific findings a reader would treat as real. No gold standard was used (flags are internal-logic violations, not confirmed against ground truth), and the authors candidly note their source hospital had stronger-than-average validation protocols, so error counts here are likely a floor for less-validated sources.

Plain-English glossary

  • EPIC — one of the dominant commercial electronic health record systems used across US hospital systems; its internal data model doesn't map one-to-one onto a clean relational-database structure.（中文：EPIC——美国医院系统中广泛使用的主流商业电子健康记录系统之一；其内部数据模型不能一对一映射到干净的关系型数据库结构上。）
  • Primary key — the variable (e.g. patient ID) that should uniquely and consistently identify the same entity across every linked table in a database, used to merge/join records and verify consistency.（中文：主键——应在数据库中每一张关联表里唯一、一致地标识同一实体的变量（例如患者ID），用于合并/连接记录并核实一致性。）
  • MAR / MNAR (missing at random / missing not at random) — whether the probability a value is missing depends only on observed data (MAR) or also on the missing value itself (MNAR); the distinction determines which missing-data method is appropriate.（中文：随机缺失/非随机缺失——数值缺失的概率是否仅取决于已观测数据（随机缺失），还是也取决于缺失值本身（非随机缺失）；这一区分决定了应采用哪种缺失数据处理方法。）
  • Multiple imputation (chained equations) — a missing-data method that generates several plausible replacement values per missing entry using iterative prediction from other variables, rather than a single mean/mode replacement.（中文：链式方程多重插补——一种缺失数据处理方法，通过其他变量的迭代预测，为每个缺失项生成多个合理的替代值，而不是用单一的均值或众数替代。）
  • Kruskal-Wallis ANOVA (with Bonferroni-adjusted pairwise comparisons) — a non-parametric test for whether a continuous outcome differs across more than two groups, followed by adjusted pairwise tests identifying which specific group pairs differ.（中文：Kruskal-Wallis方差分析（带Bonferroni校正的成对比较）——一种非参数检验，用于判断连续型结局变量在两个以上分组间是否存在差异，随后通过校正后的成对检验确定具体是哪些组之间存在差异。）
  • Omnibus vs. pairwise comparison — an omnibus test asks whether any group differs from any other overall; a pairwise comparison asks which specific pair(s) differ, and can change even when the omnibus result stays significant.（中文：总体检验与成对比较——总体检验回答"是否存在任何组间总体差异"，成对比较回答"具体是哪一对（或几对）组存在差异"，即使总体检验结果保持显著，成对比较的结论也可能发生变化。）

Methods / tools to lift

  • State-dependent object rule as a runnable check — verify a patient's own event sequence (DOB before any subsequent event, visit steps in expected order) is internally logical; flag violations independent of whether any single value looks implausible alone.
  • Primary-key-as-checked-construct — treat patient-ID consistency as step one of relational-integrity checking, corroborated via other linked tables, rather than assumed clean.
  • Pairwise-not-just-omnibus evaluation design — demonstrating a cleaning step's impact by checking whether specific pairwise comparisons shift, not just whether an aggregate test statistic changes.
  • Attribute-dependency-as-imputation-aid — using known variable dependencies (e.g. chief-complaint implies an ED-event record) to help fill specific missing values from a related dataset.

Where it lands + buildable artifact

Pipeline stage: (a) candidate generation, primary — the most concrete, ready-to-port implementation of Kahn's state-dependent object rule seen yet, directly analogous to checking that a patient's height/weight measurements occur in a logically sane sequence relative to visit history and age. (d) evaluation, secondary — a citable demonstration that an overall significance test can hide exactly where a data-quality error changes a conclusion; argues for evaluating any future cleaning step at the level of specific comparisons, not just an aggregate statistic.

MVP: a small demonstration harness — apply a candidate flagging rule (state-dependent sequence checks as the natural first target) to a synthetic or public anthropometric dataset, run a downstream comparison both with and without the correction, and report whether pairwise (not just overall) comparisons shift. Difficulty: S-M (the check logic is simple; the effort is choosing a realistic downstream comparison).

What to verify first

  • No gold standard: the 2,519 flagged encounters are internal-logic violations caught by the rule, not confirmed against an independent source of truth — this demonstrates the rule changes conclusions, not that it achieves any specific sensitivity/precision against real errors.
  • The source hospital had stronger-than-average data validation protocols per the authors' own account — their error count is likely a floor, not a ceiling, for what a differently-validated source might show.
  • This is single-encounter, short-time-horizon ED visit data (medication-order-to-administration) — whether these specific state-dependent checks translate cleanly to a much longer, slower-moving longitudinal registry time series is untested here.
  • No claims made about CFFPR's current cleaning rules, flag rates, or data-quality process — this paper's numbers and findings are specific to its own two ED datasets.

Pipeline stage

(a) candidate generation, primary / (d) evaluation, secondary.

Error types covered / not covered

Covered: duplicate/multi-step timestamp ambiguity, cross-table/primary-key inconsistency, temporal coding-interval validity, event-sequence ordering violations, and cross-variable dependency violations usable for imputation. Not covered: no digit-transposition or decimal-shift-specific detection; no carry-forward (stale value repeated) detection; real-clinical-event vs. data-error discrimination beyond the sequence-logic check itself; no gold-standard-based sensitivity/PPV of any kind.
