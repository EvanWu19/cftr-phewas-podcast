How did this episode land for you?

Blurb

This episode benchmarks two ways to pull structured clinical facts out of messy free-text notes, using neurofibromatosis type 1 (NF1) — a rare, clinically heterogeneous genetic disease — as the test case. A Washington University team built four extraction pipelines targeting 32 NF1-related phenotypes from pediatric progress notes: one rule-based system (MedSpaCy + PyRuSH, with hand-written target and context rules) and three LLM pipelines (GPT-4, and two locally-hosted open models, Gemma3-27B and DeepSeek-R1-14B). After full refinement, the rule-based system had the highest accuracy in both development and generalizability testing. But when notes shifted to a second, previously-unseen physician's documentation style, the rule-based pipeline's accuracy dropped nearly twice as much as any of the LLMs before it was re-tuned — a concrete illustration of the accuracy-vs-generalizability trade-off that anyone building phenotype-extraction tooling for a registry-adjacent project needs to reason about explicitly, rather than assuming one paradigm just wins.

Methods/tools to lift

  • MedSpaCy + PyRuSH as a lightweight, no-GPU stack for rule-based clinical/registry-note phenotype extraction.
  • The target-rule / context-rule separation pattern (detect mention, then modify for negation/hypothetical/severity) as a reusable design for any custom extractor.
  • The refinement-iteration workflow: identical prompt skeleton (role + definitions + format example + full text) refined across versions, rather than redesigning prompts from scratch each round.
  • The Phase 1 → Phase 2 generalizability test design: hold out a second annotator/documentation-style batch specifically to measure transfer, not just raw accuracy.
  • Explicit cost/resource framing (free-but-labor-intensive rules vs. upfront-GPU-but-zero-marginal-cost local LLMs vs. no-hardware-but-per-query-fee hosted LLM) as a template for build-or-buy write-ups.

Where it lands + buildable artifact

Priority: AI-tooling / career. This is a method-transfer point about how to benchmark rule-based vs. LLM phenotype extraction — not a claim about CFFPR's registry internals or current phenotyping approach.

Buildable artifact: "phenotype-extraction generalization harness." MVP: build a minimal rule-based extractor and a minimal LLM-prompted extractor targeting ~5 phenotypes on ~20-30 synthetic or public clinical-note-style texts, score F1 for both, then swap in a second batch written in a deliberately different documentation style and measure each pipeline's generalization drop (the Phase 1 → Phase 2 comparison this paper runs). Difficulty: S (a few days, no CFF-owned data required).

What to verify first

  • Generalizability was tested at only one institution with two physicians — real cross-institution transfer (different EHR, different specialty mix) is unverified.
  • The gold-standard annotation set is small (147 notes total), limiting statistical confidence in smaller F1 differences between pipelines.
  • No external-institution replication has been done yet; treat this as a strong first study, not a confirmed general result.
  • LLM run-to-run consistency (prompt sensitivity, temperature-driven variation) was not formally stress-tested in this paper.
  • Nothing in this paper or episode should be read as a statement about CFFPR's current phenotyping methods or as settling any research-design question for Runyu's own project.
