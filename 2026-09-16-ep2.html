How did this episode land for you?

Ep2 (Track B) — Using OMOP CDM for a Multi-Registry ICU Benchmarking Federated Analysis: Lessons Learned

Blurb. A frank, numbered account of what broke when two real ICU quality registries -- NICE (Netherlands, 243,346 admissions, 74 ICUs) and CCAA (Critical Care Asia-Africa, 147,495 admissions, 186 ICUs) -- were converted to the OMOP Common Data Model and benchmarked against each other using APACHE II-derived standardized mortality ratios (0.7-2.4 across 13 registries). The authors deliberately ran a naive implementation first, letting problems surface organically, then fixed them: seven challenges total, four traceable to OMOP/ETL implementation decisions (SQL dialect mismatch, base-vocabulary variation, table-placement variation, missing vocabulary mappings for admission reasons), two to the analysis plan (stripped hospital identifiers, divergent missingness mechanisms), one to interpretation. OHDSI's own ATLAS tool didn't help -- at the time it only supported three study designs, none matching this benchmarking design -- and the standard OHDSI network-study playbook (write once, run everywhere) proved infeasible given real cross-source discrepancies. The recommended fix isn't technical: publish data dictionaries and ETL metadata up front. The buildable artifact is a pre-mortem checklist, method only, with zero claims about CFF Patient Registry's current structure or any plans to adopt a shared CDM.

Plain-English glossary

  • OMOP CDM (Observational Medical Outcomes Partnership Common Data Model) — a fixed table structure and standardized vocabulary that different clinical data sources can be mapped into so shared analysis code can run across them.（中文：观察性医疗结局伙伴关系通用数据模型——一套固定的表结构和标准化词汇表，不同的临床数据来源可以被映射进去，从而让共享的分析代码能够跨数据源运行。）
  • ETL (extract-transform-load) — the process of mapping a source database into a target structure like OMOP CDM.（中文：抽取-转换-加载——将源数据库映射进OMOP CDM等目标结构的过程。）
  • OHDSI (Observational Health Data Sciences and Informatics) — the open collaborative that maintains OMOP CDM and its associated open-source tooling (ATLAS, SQLRender, etc.).（中文：观察性健康数据科学与信息学协作组织——维护OMOP CDM及其配套开源工具（如ATLAS、SQLRender）的开放协作组织。）
  • Federated analysis — running an analysis script locally at each data holder's site against their own database, with only aggregated results (never patient-level data) leaving the site.（中文：联邦化分析——在每个数据持有方本地运行分析脚本，仅将汇总结果（而非患者层面数据）传出该机构。）
  • SNOMED CT — a large standardized clinical terminology (controlled vocabulary of codes for diagnoses, findings, and procedures); one of several source vocabularies OMOP concept codes can be built from.（中文：一套庞大的标准化临床术语体系，用于诊断、临床发现和操作的受控代码词汇表；是OMOP概念代码可基于其构建的若干源词汇表之一。）
  • APACHE II (Acute Physiology and Chronic Health Evaluation II) — a long-established ICU severity-of-illness scoring system used to predict expected mortality risk.（中文：一套历史悠久的重症监护病房疾病严重程度评分系统，用于预测预期死亡风险。）
  • Standardized mortality ratio (SMR) — observed mortality divided by severity-score-predicted (expected) mortality; near 1.0 means outcomes track the prediction.（中文：标准化死亡比——观察到的死亡率除以严重程度评分预测的预期死亡率；接近1.0意味着实际结局与预测相符。）
  • ATLAS — OHDSI's web application for building OMOP cohort/analysis definitions without writing raw SQL, limited (at the time of this study) to clinical characterization, population-level estimation, and patient-level prediction study designs.（中文：OHDSI开发的网页应用，用于在不写原始SQL的情况下构建OMOP队列/分析定义，在本研究进行时仅支持临床特征描述、人群层面效应估计和患者层面预测三种研究设计。）

Methods / tools to lift

  • Naive-then-solved two-step implementation — deliberately run the unfixed version first to let undocumented ETL-era decisions surface, rather than trying to guess them upfront.
  • Customizable configuration file for concept codes/tables — replaces hardcoded SQL concept codes with a per-source-data lookup, isolating vocabulary variation from analysis logic.
  • OHDSI SQLRender — translates T-SQL to other SQL dialects (e.g. PostgreSQL), but only if the source query is originally written in T-SQL.
  • Seven-category challenge taxonomy (data preparation / analysis plan / data interpretation, further split by whether OMOP-CDM-specific) — a reusable structure for documenting any multi-source data harmonization effort's pitfalls.

Where it lands + buildable artifact

Serves: AI-tooling / career positioning. Method only — no claim about CFF Patient Registry's current structure or any plan/timeline to adopt a shared CDM.

MVP: a pre-mortem document modeled directly on this paper's seven-challenge table -- for a hypothetical registry-to-OMOP conversion, walk through each challenge category (SQL dialect mismatch, base-vocabulary variation, table-placement variation, missing vocabulary mapping for a specific field, identifier-stripping vs. anonymity tradeoffs, divergent missingness mechanisms) and pre-draft the question each raises, without assuming a specific answer for any real registry. Difficulty: S (a structured question list, not code).

What to verify first

  • This is a two-source, two-country ICU comparison computing one severity-adjusted mortality metric — whether the same seven-challenge taxonomy generalizes to a registry with different variable types (e.g. longitudinal anthropometrics vs. point-in-time severity scores) is untested here.
  • Several fixes (e.g. the customizable concept-code configuration file) assume full write access to and understanding of both source OMOP databases' ETL history — a real precondition, not automatically available.
  • ATLAS's design-type limitations were current as of this study's implementation date — OHDSI tooling moves, so recheck against the current ATLAS release rather than assume the gap still holds.
  • No claims made about CFFPR's current data structure, cleaning rules, or any CDM adoption plans — this paper's findings are specific to NICE and CCAA's OMOP implementations.

JORDAN Set up the vocabulary first -- what's OMOP CDM, and what does "federated analysis" actually mean here? 先讲讲术语——OMOP CDM是什么？这里说的"联邦化分析"到底是什么意思？

ALEX OMOP, the Observational Medical Outcomes Partnership, publishes a Common Data Model, or CDM -- a fixed table structure and a standardized vocabulary that any source of clinical data, an EHR, a registry, a claims database, can be mapped into, so that the same analysis code can in principle run against data that started out in completely different formats. OMOP，全称Observational Medical Outcomes Partnership，发布了一套通用数据模型（Common Data Model，简称CDM）——一套固定的表结构和标准化词汇表，任何临床数据来源，无论是电子病历、登记库还是理赔数据库，理论上都可以被映射进去，这样原本格式完全不同的数据，理论上就可以用同一套分析代码来处理。 The process of mapping a source database into that structure is called ETL, extract-transform-load, and OHDSI, the Observational Health Data Sciences and Informatics collaborative, maintains OMOP CDM along with a set of open-source tools around it. 把源数据库映射进该结构的过程叫做ETL（抽取-转换-加载，extract-transform-load），而OHDSI，即Observational Health Data Sciences and Informatics协作组织，负责维护OMOP CDM及其配套的一系列开源工具。 Federated analysis means the analysis script travels to each data holder and runs locally against their own OMOP database, and only the aggregated, already-computed results travel back out -- no patient-level data ever leaves the originating site, which is what makes cross-border or cross-institution collaboration legally and practically feasible under strict privacy laws. 联邦化分析的意思是，分析脚本被发送到每一个数据持有方，并在其本地的OMOP数据库上运行，只有汇总后、已经计算完成的结果才会被传回——患者层面的数据永远不会离开原始机构，这正是在严格隐私法规下实现跨国或跨机构合作在法律和实际操作上可行的关键。 SNOMED CT, which comes up later, is a large standardized clinical terminology -- a controlled vocabulary of codes for diagnoses, findings, and procedures -- and it's one of several source vocabularies OMOP concept codes can be built from. 后面会提到的SNOMED CT，是一套庞大的标准化临床术语体系——一套用于诊断、临床发现和操作的受控代码词汇表——它是OMOP概念代码可以基于其构建的若干源词汇表之一。

JORDAN And the actual study they ran -- what were they benchmarking? 他们实际开展的研究——具体在对比什么？

ALEX Two data sources: NICE, the National Intensive Care Evaluation registry in the Netherlands, 243,346 admissions across 74 ICUs, and CCAA, Critical Care Asia-Africa, 147,495 admissions across 186 ICUs representing 13 separate quality registries, both covering adult ICU encounters from July 2019 through December 2022. 两个数据来源：荷兰的NICE，即National Intensive Care Evaluation登记库，涵盖74个ICU共243,346例入院记录；以及CCAA，即Critical Care Asia-Africa，涵盖186个ICU、代表13个独立质量登记库共147,495例入院记录，两者都涵盖2019年7月至2022年12月期间的成人ICU诊疗记录。 They applied the APACHE II model, Acute Physiology and Chronic Health Evaluation II, a long-established severity-of-illness scoring system, to the OMOP-formatted data from both sources to calculate expected mortality risk, then compared that to observed mortality to compute a standardized mortality ratio, or SMR, at the registry level -- essentially an observed-over-expected ratio, where a value near 1.0 means outcomes track what the severity score would predict. 他们将APACHE II模型——Acute Physiology and Chronic Health Evaluation II，一套历史悠久的疾病严重程度评分系统——应用于两个数据来源的OMOP格式数据，计算预期死亡风险，再将其与观察到的实际死亡率对比，得出登记库层面的标准化死亡比（standardized mortality ratio，SMR）——本质上是一个"观察值除以预期值"的比率，接近1.0意味着实际结局与严重程度评分的预测相符。 They deliberately used a two-step approach: step one was a naive implementation, letting real challenges surface organically rather than guessing at them in advance, and step two developed solutions once those challenges were catalogued. 他们特意采用了两步走的方法：第一步是一次"天真"的初次实现，让真实的问题自然暴露出来，而不是提前去猜测；第二步则是在这些问题被系统归类之后，再针对性地开发解决方案。 That's a deliberately different posture from most tooling papers, which usually present the polished solution and skip the messy first attempt. 这和大多数工具类论文的姿态是刻意不同的——大多数论文通常只展示打磨过的最终解决方案，跳过混乱的第一次尝试。

JORDAN I'd push back a little on that framing -- isn't "let the naive version fail first" just a slower way to find bugs you'd find anyway? 我想对这个框架提出一点质疑——"先让天真版本失败"，难道不就是一种更慢的、迟早都能发现同样bug的方式吗？

ALEX Fair pushback, but I'd defend it here, because the failures they were looking for aren't bugs in the usual sense -- they're implicit decisions baked into the ETL process by people who built the OMOP databases years before this study, decisions about which vocabulary to map a field to, or which table a concept lives in, that nobody documented as a decision at all. 这个质疑有道理，但我在这里会为这种做法辩护，因为他们要找的那些问题并不是通常意义上的bug——而是隐藏在ETL过程中的隐性决策，是几年前构建这些OMOP数据库的人做出的决策，比如某个字段该映射到哪个词汇表、某个概念该存在哪张表里，而这些决策从来没有被当作"决策"记录下来过。 You genuinely can't predict most of those in advance without already having lived through a federated analysis on this exact pair of databases -- that's the whole point of a lessons-learned paper instead of a design document. 如果没有真正在这一对具体数据库上经历过一次联邦化分析，你确实无法提前预测大多数这类问题——这正是"经验教训"论文而不是"设计文档"的意义所在。

JORDAN Walk me through the actual challenges they hit. 带我过一遍他们实际遇到的问题。

ALEX Seven challenges total, four in data preparation, two in the analysis plan, one in interpretation, and four of the seven trace back specifically to decisions made during OMOP implementation rather than the underlying clinical data itself. 总共七个问题，四个属于数据准备阶段，两个属于分析计划阶段，一个属于结果解读阶段，其中七个里有四个可以直接追溯到OMOP实现过程中做出的决策，而不是底层临床数据本身。 C1: the two OMOP databases ran on different SQL server types, T-SQL and PostgreSQL, so a shared query couldn't run against both -- they used OHDSI's own SQLRender package to translate, but the fix only works if you write your original query in T-SQL to begin with, which is a gotcha worth knowing before you start. C1：两个OMOP数据库运行在不同类型的SQL服务器上，一个是T-SQL，一个是PostgreSQL，共享查询无法同时在两边运行——他们使用OHDSI自己的SQLRender包来做转换，但这个解决方法只有在你一开始就用T-SQL写查询时才有效，这是一个值得提前知道的坑。 C2 and C3: the two sources occasionally used different base vocabularies for the same concept, and stored equivalent concepts like comorbidities in different OMOP tables -- the fix was replacing hardcoded concept codes in the SQL with a customizable configuration file specifying, per data source, which code and which table applied. C2和C3：两个数据源有时对同一个概念使用不同的基础词汇表，并且把诸如合并症这样的等价概念存放在不同的OMOP表里——解决方法是把SQL里硬编码的概念代码替换成一个可自定义的配置文件，针对每个数据源分别指定应使用哪个代码、哪张表。 C4 and C6: there was simply no standardized vocabulary mapping for reasons-for-ICU-admission -- NICE used APACHE IV diagnosis codes, CCAA used SNOMED CT terms -- so a shared extraction and mapping script was impossible, and they had to write source-specific mapping scripts instead. C4和C6：入院原因根本没有标准化的词汇映射——NICE使用APACHE IV诊断代码，CCAA使用SNOMED CT术语——因此共享的抽取与映射脚本根本不可能实现，他们只能为每个数据源分别编写专属的映射脚本。 C5: NICE had stripped hospital identifiers during OMOP loading to protect patient anonymity, which meant ICU-level SMR reporting wasn't possible for that source, only registry-level aggregation. C5：NICE在加载进OMOP时已经剥离了医院标识符以保护患者匿名性，这意味着该数据源无法进行ICU层级的SMR报告，只能做登记库层级的汇总。 C7: the two sources had genuinely different causes of missingness -- NICE treated missing physiological values as implicitly within the normal range, following convention from the original APACHE II paper, while CCAA used multiple imputation because missingness there more plausibly reflected resource-constrained access to testing -- so the same statistical fix couldn't be applied uniformly to both. C7：两个数据源的缺失原因确实不同——NICE按照原始APACHE II论文的惯例，将缺失的生理指标隐含地视为处于正常范围内，而CCAA则使用多重插补，因为那里的数据缺失更可能反映的是资源受限导致的检测可及性问题——因此同一种统计处理方法无法统一套用于两个数据源。

JORDAN Did their own tooling, ATLAS, actually help here? ATLAS这个他们自己的工具，在这里真的有帮上忙吗？

ALEX Not much, and that's one of the more useful negative results in the paper. 帮助不大，而这恰恰是这篇论文里比较有价值的一个负面结果。 ATLAS is OHDSI's web application for grouping concept codes into a single clinical entity without writing raw SQL, but at the time of this study it only supported three study designs -- clinical characterization, population-level estimation, and patient-level prediction -- none of which is the benchmarking design this study needed, so the team fell back to custom scripts instead. ATLAS是OHDSI开发的一个网页应用，用于在不写原始SQL的情况下把概念代码归组为单一临床实体，但在这项研究开展时，它只支持三种研究设计——临床特征描述、人群层面效应估计和患者层面预测——都不是这项研究所需要的基准对比设计，因此团队还是退回去用了自定义脚本。 They also flag that installing and running ATLAS requires real technical expertise, often beyond what a typical clinical research team has in-house, which is a resourcing point as much as a technical one. 他们还指出，安装和运行ATLAS需要真正的技术专业能力，这往往超出了一个典型临床研究团队自身的能力范围，这既是一个技术问题，也是一个资源配置问题。 And OHDSI's standard recommendation for network studies -- write one script on one OMOP database, then run it unchanged across the rest of the network -- turned out to be infeasible here, because of exactly the discrepancies in data generation processes documented in C1 through C7; the two-step naive-then-fixed approach was necessary precisely because the standard playbook didn't hold. 而OHDSI对于网络研究的标准建议——在一个OMOP数据库上写好一个脚本，然后原样运行到网络中其余数据库——在这里被证明是不可行的，原因正是C1到C7所记录的数据生成过程之间的差异；两步走、先天真实现再修复的方法之所以必要，恰恰是因为标准的操作手册在这里行不通。

JORDAN So does the study actually deliver its stated aim -- feasibility of federated benchmarking? 那这项研究最终是否实现了它宣称的目标——联邦化基准分析的可行性？

ALEX Yes, with real caveats. 是的，但有实实在在的前提条件。 APACHE II SMRs across all 13 quality registries ranged from 0.7 to 2.4, and the analysis scripts, once adapted to handle the challenges above, were successfully shared and run across both databases -- so federated benchmarking on OMOP-converted registries is demonstrated as feasible, not just theoretically possible. 所有13个质量登记库的APACHE II标准化死亡比范围为0.7到2.4，而分析脚本在针对上述问题做出调整后，成功地在两个数据库之间共享并运行——因此，基于OMOP转换后的登记库进行联邦化基准分析被证明是可行的，而不仅仅是理论上可能。 The demographic contrast between the two sources is itself informative for interpreting that spread: CCAA skewed younger, median age 55 versus NICE's 66, but had much higher ICU mortality, 20.8% versus 10.5%, and much longer stays, 2.3 days versus 1.1 -- differences plausibly reflecting genuine variation in case mix, resource availability, and admission thresholds across the CCAA network's 186 mostly resource-varied ICUs versus NICE's more uniform Dutch national system, rather than purely a data-quality artifact. 两个数据源之间的人口学差异本身也有助于解读这种离散程度：CCAA的患者更年轻，中位年龄55岁，相比之下NICE为66岁，但CCAA的ICU死亡率却高得多，20.8%对10.5%，住院时长也长得多，2.3天对1.1天——这些差异很可能反映的是CCAA网络中186个资源条件各异的ICU与NICE更为统一的荷兰全国体系之间，在病例构成、资源可及性和入院门槛方面的真实差异，而不仅仅是数据质量的假象。 But the authors are explicit that future analyses remain shaped by decisions made during CDM implementation, and they recommend prior publication of data dictionaries and metadata describing data handling and classification choices as the fix going forward. 但作者明确指出，未来的分析仍然会受到CDM实现过程中所做决策的影响，他们建议的应对方法是提前发布数据字典，以及描述数据处理和分类选择的元数据。
