Blurb

The Data Quality Dashboard (DQD) is an open-source R package that audits a database in the OMOP common data model by running 3,300+ configurable checks, organized by the Kahn framework (conformance / completeness / plausibility) and split by verification vs validation. Its core trick: 20 high-level "data quality ideas" are written as parameterized SQL templates and rotated across the known OMOP schema, auto-expanding into 3,300+ concrete checks (396 completeness, 779 conformance, 2,126 plausibility). Every check carries an editable failure threshold and exposes the exact SQL behind its result — the three things the older ACHILLES Heel report couldn't do. A real run on a 700GB Medicaid database produced 3,124 checks in ~7 hours and rendered an interactive R Shiny report. Where it lands: the AI-tooling / career priority (with a method-only nod to Liz / phenotype-and-data-quality). Buildable artifact: a schema-driven data-quality harness for a longitudinal registry.

Plain-English glossary

  • ACHILLES / Heel report — OHDSI's older characterization tool; ran rules over pre-aggregated summaries, with no editable checks, no exposed SQL, no extensibility.
  • Common data model (CDM) — a fixed schema (tables, fields, relationships) everyone converts data into so the same analysis code runs anywhere.
  • Conformance / completeness / plausibility — the three Kahn data-quality categories: structural-rule adherence / presence of expected data (incl. vocabulary mapping) / believability of values.
  • Concept ID zero — OMOP's "no matching standard concept"; records mapped to zero are invisible to standardized analytics.
  • ETL (extract, transform, load) — the pipeline that reshapes source data into the CDM and maps codes to standard concepts.
  • OMOP — the OHDSI-maintained CDM; standardizes both structure and content (SNOMED for conditions, RxNorm for drugs).
  • SCRC / SVC — standardConceptRecordCompleteness (count of records mapped to zero) and sourceValueCompleteness (count of distinct source values mapped to zero); read together they diagnose mapping problems.
  • Verification vs validation — conformance to the model's own rules vs agreement with external knowledge of the world.

ALEX Today's Track B paper is "Increasing trust in real-world evidence through evaluation of observational data quality," Clair Blacketer and colleagues from the OHDSI community, JAMIA, 2021. It's the paper behind the Data Quality Dashboard — DQD — an open-source R package that runs over 3,300 configurable quality checks against a database in the OMOP common data model. We're reading it because it's a ships-code paper, it's directly about the unglamorous layer that decides whether any downstream model is trustworthy, and the abstraction it uses to generate thousands of checks from twenty ideas is genuinely worth stealing.

JORDAN Before the tooling, set the genomics-adjacent vocabulary for me. What's OMOP, and what's a common data model?

ALEX Sure — this is the bioinformatics-infrastructure layer you're still ramping on, so let's be precise. A common data model, CDM, is an agreed-upon schema: a fixed set of tables, columns, and relationships that everyone converts their data into, so that the same analysis code runs anywhere. OMOP — Observational Medical Outcomes Partnership — is the specific CDM that the OHDSI community maintains for health data. The thing that makes OMOP more than a table layout is that it standardizes content, not just structure: conditions get mapped to the SNOMED vocabulary, drugs to RxNorm. So "type 2 diabetes" recorded a dozen different ways at a dozen sites all collapse to the same standard concept ID. That semantic harmonization is what lets a study run across databases on three continents without sharing a single patient record.

JORDAN And the act of getting your data into that shape — that's the ETL they keep mentioning?

ALEX Right. ETL is extract, transform, load — the pipeline that pulls your source data, reshapes it to the CDM, and maps every code to a standard concept. The problem the paper attacks is what happens after ETL. Observational data — EHR, claims — was collected for billing or care, not research. Time stamps may not mean what you think, clinical ideas hide in free text, and the same lab test gets written "WBC," "White Blood Cell," and "White BC." If you don't catch that, you get misclassification and measurement error baked silently into every analysis. Their thesis is simple and, I think, correct: before you trust evidence from a database, you have to trust the database, and that requires a standardized, transparent way to measure quality — not a one-off script per site.

JORDAN Wasn't there already a tool for this? They mention ACHILLES.

ALEX They did, and the contrast is the whole motivation. ACHILLES characterized a database — age and gender distributions, follow-up time, diagnosis-code frequencies — and ran a set of "Heel" rules over those summaries to flag obvious problems, like patients with negative age. But the Heel report was a black box in three ways the authors call out: you couldn't change how a check passed or failed, you couldn't see the SQL that produced a result, and you couldn't extend it with new checks or attach a note explaining why a flagged issue might be legitimate. DQD was built to fix exactly those three gaps. And I'll push on one design choice here: ACHILLES assessed quality on pre-aggregated summaries, whereas DQD runs against the actual CDM instance. That's more faithful, but it's also why DQD is heavy to run — we'll get to the seven-hour number.

JORDAN So what did they actually build? What's the architecture?

ALEX This is the clever part. They organized everything around the Kahn framework — a data-quality taxonomy from Michael Kahn that sorts checks into three categories: conformance, completeness, and plausibility. Conformance is "does the data obey the schema's structural rules" — required fields present, primary keys unique, foreign keys valid. Completeness is "is data present where expected" — and in OMOP that includes vocabulary-mapping completeness, not just missing rows. Plausibility is "are the values believable" — no encounters before birth, no zero-kilogram weights. They also cross-cut each check with verification versus validation — verification meaning conformance to the model's own rules, validation meaning agreement with external knowledge about the world.

JORDAN And where do 3,300 checks come from? That sounds like a lot to hand-write.

ALEX They don't hand-write them, and this is the idea worth lifting. They separated the "data quality idea" from the individual check. There are only 20 high-level check types — 5 completeness, 8 conformance, 7 plausibility. Each one is a parameterized SQL template. Because OMOP's schema is known in advance, a single idea like "how many persons have no record in this clinical fact table" can be rotated across every fact table that has a foreign key to the Person table. One idea with 15 applicable tables becomes 15 concrete checks automatically. Resolve all 20 templates against the full schema and you get over 3,300 individual checks — 396 completeness, 779 conformance, 2,126 plausibility. The SQL parameter-swapping is done with their SqlRender package, and crucially every check carries a configurable failure threshold the user can edit, plus the exact SQL is exposed so you can pull the failing rows.

JORDAN Before the example — I want to make sure I see why the rotation actually saves work, versus just writing 3,300 SQL queries by hand once.

ALEX Two reasons, and they're both about maintenance, not the initial write. First, when the schema changes — OMOP ships new CDM versions — you don't rewrite thousands of queries; you update the control files that describe tables and fields, and the same 20 templates re-expand against the new schema automatically. The check logic and the schema description are decoupled. Second, when someone invents a 21st quality idea, they write one template and it instantly applies everywhere it's relevant across the whole model. Hand-writing 3,300 queries gives you 3,300 things to maintain; this gives you 20 templates plus a schema description. That's the difference between a script and a framework, and it's the single most reusable thing in the paper. The cost you pay is indirection — debugging a failing check means tracing back through the parameter substitution to see which template and which schema row produced it, which is why exposing the resolved SQL per check isn't a nicety, it's what makes the abstraction debuggable at all.

JORDAN Give me a concrete example of a check earning its keep.

ALEX The best one in the paper is a pair: standardConceptRecordCompleteness — SCRC — and sourceValueCompleteness — SVC. When ETL can't map a source code to a standard concept, it assigns concept ID zero, meaning "no matching concept," and those records are invisible to standardized analytics. SCRC counts how many records mapped to zero; SVC counts how many distinct source values mapped to zero. Reading them together is a genuinely nice diagnostic. High SCRC and high SVC means a whole proprietary coding system is unmapped — big problem. High SCRC but low SVC means a few catch-all values like "UNK" are eating a lot of records — usually safe to ignore. Low SCRC and low SVC is the healthy state. That's the kind of two-number signal that tells you what's actually wrong with a mapping, not just that something is wrong.

JORDAN Does it run at real scale, and what does the output look like?

ALEX It does, and they're honest about the cost. Running DQD on IBM MarketScan Multi-State Medicaid — MDCD, about 700 gigabytes — produced 3,124 checks rather than the full 3,300 because three tables weren't populated, and it took seven hours in a cloud parallel environment. Output is a text file or a database table feeding an interactive R Shiny dashboard: an overview tab with pass/fail counts by Kahn category, and a results tab with one line per check, filterable by pass/fail, table, and context, where you can expand any row to see the SQL that produced it. In their example run the database had 13 conformance failures, 5 completeness, 12 plausibility. The package is on GitHub, supports OMOP CDM 5.2.2 and 5.3.1, and runs on PostgreSQL, SQL Server, and Redshift.

JORDAN One thing I want to make sure I follow — the verification-versus-validation split. How is that different from the three Kahn categories?

ALEX It's an orthogonal axis, and worth being precise about because the words get used loosely. Verification asks "does the data conform to the model's own internal rules" — the constraints you can check without any outside knowledge, like a foreign key pointing at a real primary key. Validation asks "does the data agree with what we know about the real world" — knowledge that lives outside the schema, like the fact that humans don't weigh zero kilograms or that an encounter can't precede a birth. So every check sits at an intersection: a conformance check is almost always verification, a plausibility check is usually validation, and completeness can be either depending on whether "expected" is defined by the schema or by domain knowledge. The reason that matters operationally is that verification checks are portable — they're true for any OMOP instance — whereas validation checks encode assumptions you may need to tune per source. That distinction is exactly what you'd carry into a registry harness.

JORDAN They also make an argument about how this should change publishing, right?

ALEX They do, and it's the part most relevant to your career framing. Their pitch is that a DQD result file should ship as supplementary material with any real-world-evidence paper — every check, pass or fail, attached to the study so reviewers and regulators can see the data the evidence rests on. They note, pointedly, that recent papers from major networks either don't describe data-quality assessment or barely mention it. They contrast OHDSI's fully distributed model — no central coordinator, each site owns its data and ETL, you share code not data — with the more centralized review loops of PEDSnet, PCORnet, and Sentinel. The distributed model trades central control for reach, and DQD is how you keep quality legible without a coordinating center.

JORDAN One more thing before we land it — you flagged the seven-hour runtime as a pushback. Is that a dealbreaker?

ALEX Not a dealbreaker, but a real design constraint worth naming, and it shapes how you'd adopt the idea. Seven hours on a 700-gigabyte database, in a parallelized cloud environment, means the full check suite is not something you run casually in a tight feedback loop. That's exactly why the authors land on the two-phase pattern I mentioned — conformance and completeness once when the data is first mapped, then plausibility on every incremental load. The deeper point for a builder is that a quality harness has to be designed around the cadence of your data, not run as a monolith. If your registry updates quarterly, a multi-hour full sweep per release is fine; if it updates nightly, you need the incremental split or you'll never keep up. The other thing I'd push on is that 3,300 checks produce a lot of output, and a wall of green-and-red is its own failure mode — you need the threshold tuning and the per-check notes precisely so the report surfaces the dozen failures that matter rather than burying them. Volume of checks is not the same as usefulness of the report.

ALEX Right, and that balance — generate exhaustively, but report selectively with editable thresholds — is the part most worth copying.
