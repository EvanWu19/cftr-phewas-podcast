Ep1 (Track A — variant interpretation): One variant, five representations, one toolkit

Sun, Wang, and Yang (2026, Human Mutation) present VarSim, a lightweight Python toolkit that chains together the full set of interdependent tasks practical HGVS (Human Genome Variation Society) variant-description processing requires: parsing, syntactic and semantic validation, normalization, coordinate transformation, protein-consequence inference, genome-assembly liftover, and conversion between HGVS, VCF, and SPDI representations — all version-pinned to MANE (Matched Annotation from NCBI and EMBL-EBI) transcripts so every step is checked against one reconciled reference rather than whichever transcript happened to be a tool's default. Benchmarked against 1,458 HGVS descriptions across five MANE transcripts (500 coding SNVs, 250 frameshift indels, 708 intronic splice-site substitutions), VarSim passed its own syntactic and semantic validation on everything tested, agreed with Mutalyzer's normalization on all 750 coding variants and with VariantValidator on 749 of 750, matched VariantValidator's protein-consequence calls on all 500 coding SNVs, and converted formats exactly — but showed substantial discrepancies against VariantValidator on transcript-to-genome projection, a limitation the authors flag explicitly rather than paper over. Only the abstract is retrievable for this paper; every number above is abstract-only and flagged as such on-air. The transferable idea for Karen's CFTR variant-notation harmonization work isn't VarSim's exact code, but its architecture: pin everything to one version-dated transcript, validate before trusting, normalize before comparing.

Plain-English glossary

  • HGVS nomenclature — the Human Genome Variation Society's standardized text-string convention for describing a variant (e.g. c.1521_1523delCTT for CFTR ΔF508), anchored to a genomic, coding-DNA, or protein coordinate system.（中文：HGVS命名法，人类基因组变异学会制定的标准化变异描述文本规范，锚定在基因组、编码DNA或蛋白质坐标体系之一上。）
  • MANE (Matched Annotation from NCBI and EMBL-EBI) — a reconciliation project in which NCBI and Ensembl jointly agree on one "MANE Select" representative transcript per gene, with identical exon structure on both sides, eliminating a long-standing source of annotation disagreement.（中文：MANE（NCBI与EMBL-EBI匹配注释），一个协调项目，NCBI和Ensembl为每个基因共同约定一个"MANE Select"代表转录本，双方外显子结构完全一致，消除了长期存在的注释分歧。）
  • SPDI (Sequence, Position, Deletion, Insertion) — NCBI's internal variant representation describing a change purely by reference accession, zero-based position, deleted bases, and inserted bases, without HGVS's transcript-relative ambiguity.（中文：SPDI（序列、位置、删除、插入），NCBI内部使用的变异表示法，仅通过参考序列编号、从零开始的位置、被删除碱基和被插入碱基来描述变异，不涉及HGVS那种依赖转录本参照的歧义。）
  • VCF (Variant Call Format) — the tab-delimited standard file format sequencing pipelines output, organized around chromosome position plus reference and alternate alleles.（中文：VCF（变异调用格式），测序流程输出的标准制表符分隔文件格式，围绕染色体位置及参考/变异等位基因组织。）
  • Backtranslation — inferring a plausible underlying coding-DNA change from a stated protein-level change, the reverse of the usual translation step.（中文：反向翻译，从一个声明的蛋白质层面变化反推出一个合理的底层编码DNA变化，方向与通常的翻译步骤相反。）
  • Liftover — carrying a variant's coordinate from one reference genome assembly (e.g. GRCh37) to another (e.g. GRCh38).（中文：基因组组装坐标转换，把变异坐标从一个参考基因组组装版本（如GRCh37）转移到另一个版本（如GRCh38）。）
  • Splice-site substitution — a variant sitting at an exon-intron boundary, in the sequence that signals the splicing machinery where to cut.（中文：剪接位点替换变异，位于外显子-内含子边界上、告诉剪接机制该在哪里"剪切"的那段序列中的变异。）
  • Syntactic vs. semantic validation — syntactic checks whether a string conforms to HGVS grammar; semantic checks whether the claimed reference base actually matches the real sequence at that position.（中文：语法校验与语义校验，语法校验检查字符串是否符合HGVS语法规则；语义校验检查声明的参考碱基是否真的与该位置的实际序列相符。）

JORDAN Before the numbers, let's get the vocabulary straight. 在看数字之前，我们先把词汇理清楚。 What is HGVS, exactly, and why does a single variant need so many different "representations" in the first place? HGVS到底是什么，为什么同一个变异一开始就需要这么多不同的"表示形式（representation）"？

ALEX HGVS stands for the Human Genome Variation Society, and HGVS nomenclature is the text-string convention clinical genetics has standardized on for writing down a variant — something like c.1521_1523delCTT for the CFTR ΔF508 deletion, where the "c." tells you the coordinate is counted along a coding-DNA reference sequence rather than the raw chromosome. HGVS指的是人类基因组变异学会（Human Genome Variation Society），HGVS命名法是临床遗传学用来书写变异的标准化文本字符串约定——比如CFTR ΔF508缺失写作c.1521_1523delCTT，其中"c."表示这个坐标是沿着一个编码DNA参考序列计数的，而不是直接按染色体位置计数。 The reason one variant ends up with multiple representations is that genomics works with several coordinate systems at once — genomic (g.), coding-DNA (c.), protein (p.) — plus file formats built for different jobs: VCF, the Variant Call Format, is the tab-delimited standard sequencing pipelines actually output, built around a chromosome position plus reference and alternate alleles. 一个变异会出现多种表示形式的原因是，基因组学同时使用好几套坐标体系——基因组坐标（g.）、编码DNA坐标（c.）、蛋白质坐标（p.）——再加上为不同用途设计的文件格式：VCF，即变异调用格式（Variant Call Format），是测序流程实际输出的那种以制表符分隔的标准格式，围绕染色体位置加上参考等位基因和变异等位基因来组织。 And SPDI — Sequence, Position, Deletion, Insertion — is a newer representation NCBI's own variation services use internally, describing a variant purely by a reference sequence accession, a zero-based position, the deleted bases, and the inserted bases, with none of HGVS's transcript-relative ambiguity. SPDI——序列、位置、删除、插入（Sequence, Position, Deletion, Insertion）——是NCBI自家变异服务内部使用的一种更新的表示方式，它完全通过一个参考序列编号、一个从零开始计数的位置、被删除的碱基和被插入的碱基来描述变异，不存在HGVS那种依赖转录本参照而带来的歧义。 Every one of these is a legitimate, standards-compliant way to describe the exact same underlying change, which is precisely the problem: a human curator, or worse, an automated pipeline, can silently drift between them without anyone noticing a mismatch. 这几种方式每一种都是完全合规、符合标准的描述同一个底层变化的方法，而这恰恰就是问题所在：一个人工审核者，或者更糟的是，一个自动化流程，可能在不知不觉中在这些表示形式之间漂移，而没有人注意到其中的不一致。

JORDAN And "MANE transcripts" — that's new vocabulary too. "MANE transcripts"——这也是个新词。 What problem is that solving? 它解决的是什么问题？

ALEX For most of the last two decades, the two major transcript annotation systems — RefSeq, maintained by NCBI, and Ensembl, maintained by EMBL-EBI — disagreed with each other for a meaningful fraction of genes: different exon boundaries, different choices of which transcript counts as the "main" one, different numbering. 过去二十年里的大部分时间，两大主流转录本注释系统——NCBI维护的RefSeq和EMBL-EBI维护的Ensembl——在相当一部分基因上互相不一致：外显子边界不同，选作"主要"转录本的那一个不同，编号方式也不同。 MANE, Matched Annotation from NCBI and EMBL-EBI, is the reconciliation project: for each protein-coding gene, NCBI and Ensembl jointly agree on one "MANE Select" transcript as the universal representative, with identical exon structure and coordinates on both sides. MANE，即NCBI和EMBL-EBI匹配注释（Matched Annotation from NCBI and EMBL-EBI），就是那个调和项目：对每一个编码蛋白质的基因，NCBI和Ensembl共同约定一个"MANE Select"转录本作为通用的代表转录本，双方的外显子结构和坐标完全一致。 Version-pinning to MANE, which is exactly what VarSim does, means a variant description is always anchored to one specific, dated, cross-database-agreed transcript rather than whatever transcript happened to be the default in whichever tool generated the original description. 像VarSim所做的那样，把版本固定（version-pinning）到MANE上，意味着一个变异描述始终锚定在某一个具体的、有版本日期的、跨数据库一致认可的转录本上，而不是锚定在生成最初那条描述时，某个工具恰好默认使用的转录本上。 For CFTR specifically, that matters because CFTR1, CFTR2, ClinVar, and biobank VCF annotations have each accumulated their own transcript conventions over the years, and reconciling them by hand is exactly the kind of tedious, error-prone work a reference-pinned toolkit is built to eliminate. 对CFTR来说，这一点格外重要，因为CFTR1、CFTR2、ClinVar和生物样本库的VCF注释多年来各自积累了自己的转录本惯例，靠人工去协调它们正是那种繁琐、容易出错、而一个锁定参考序列的工具包正是为了消除的工作。

JORDAN So what exactly motivated this paper — haven't people already built HGVS tools? 那这篇论文到底是出于什么动机——不是已经有人做过HGVS相关工具了吗？

ALEX Right, and the abstract is upfront that practical HGVS processing isn't one task, it's several interdependent ones stacked on top of each other: parsing the string, validating it syntactically and then semantically against the actual reference sequence, normalizing it to a canonical form, transforming coordinates between systems, inferring the protein consequence, mapping between genome assemblies, and converting between HGVS, VCF, and SPDI. 没错，而摘要开篇就说得很清楚：实际的HGVS处理不是一件单一的任务，而是好几个相互依赖、层层叠加的任务：解析字符串，先做语法校验再对照实际参考序列做语义校验，归一化为标准形式，在不同坐标体系之间做坐标转换，推断蛋白质后果，在不同基因组组装版本之间做映射，以及在HGVS、VCF、SPDI之间做转换。 Several existing tools already handle pieces of this — VariantValidator and the Mutalyzer normalization endpoint are the two this paper benchmarks against — but each has grown up around a slightly different scope and interface, and a lightweight, reference-aware, fully programmatic toolkit that chains all of these steps together, version-pinned to MANE, is the gap VarSim is aiming at. 已经有几个现有工具分别处理了其中的部分环节——这篇论文用来做基准对比的是VariantValidator和Mutalyzer的归一化接口——但每一个工具都是围绕各自略有不同的范围和接口发展起来的，而一个轻量级、参照意识强、完全可编程、并且版本固定到MANE的工具包，把所有这些步骤串联起来，正是VarSim想要填补的空白。 One design choice worth pushing on here: building everything around a single pinned MANE transcript per gene is clean and reproducible, but CFTR, like plenty of genes, has biologically relevant alternative splicing and minor transcripts outside the MANE Select — so a question this abstract leaves open is what happens to a variant description anchored to one of those non-Select transcripts. 这里有一个设计选择值得追问：围绕每个基因固定的单一MANE转录本来搭建整套系统，干净又可复现，但CFTR和很多基因一样，存在具有生物学意义的可变剪接和MANE Select之外的次要转录本——这篇摘要留下的一个问题是，如果一个变异描述锚定在这些非Select转录本之一上，会发生什么。 That's not a flaw so much as a scope boundary, but it's exactly the kind of boundary that matters once you try to apply this to a real gene's full variant catalog rather than a clean benchmark set. 这与其说是一个缺陷，不如说是一个范围边界，但正是这种边界，一旦你试图把它应用到一个真实基因的完整变异目录上，而不是一个干净的基准测试集上，就会变得至关重要。

JORDAN What does VarSim actually do, function by function? 那VarSim到底具体做了什么，一项一项地说？

ALEX The function list in the abstract reads like a checklist of every HGVS headache in one place: HGVS parsing; syntactic validation, meaning does the string even conform to the grammar; semantic validation, meaning does the claimed reference base actually match the real sequence at that position; normalization to a canonical form; sequence extraction; backtranslation, which is inferring a plausible underlying coding-DNA change from a stated protein-level change, the reverse direction of the usual translation step; coordinate mapping between genomic, coding, and protein systems; protein consequence prediction; genome-assembly liftover, meaning carrying a variant's coordinate from one reference assembly, say GRCh37, over to another, say GRCh38; and conversion between HGVS, VCF, and SPDI. 摘要里的功能清单几乎把每一种HGVS相关的麻烦事都集中罗列了出来：HGVS解析；语法校验，也就是这个字符串是否符合语法规则；语义校验，也就是声明的参考碱基是否真的和那个位置上的实际序列相符；归一化为标准形式；序列提取；反向翻译（backtranslation），也就是从一个声明的蛋白质层面的变化反推出一个合理的、底层编码DNA层面的变化，方向正好和通常的翻译步骤相反；在基因组、编码DNA和蛋白质坐标体系之间做坐标映射；蛋白质后果预测；基因组组装坐标转换（liftover），也就是把一个变异的坐标从一个参考基因组组装版本（比如GRCh37）转移到另一个版本（比如GRCh38）；以及在HGVS、VCF、SPDI之间做转换。 It's a reference-aware workflow, meaning every one of these steps is checked against the actual pinned MANE sequence rather than trusting the input string at face value — which is the architectural choice that lets it catch semantic errors a purely syntactic parser would wave through. 这是一个参照意识很强的工作流程，意味着上面每一步都会对照实际锁定的MANE序列进行核查，而不是单纯信任输入字符串本身——正是这个架构选择，让它能够抓出那些纯语法解析器会放过的语义错误。

JORDAN And how did they actually test it? 那他们具体是怎么测试的？

ALEX They benchmarked VarSim against 1,458 HGVS descriptions drawn from five MANE transcripts, split into 500 coding single-nucleotide variants, 250 frameshift insertions or deletions, and 708 intronic splice-site substitutions — a splice-site substitution being a variant sitting right at an exon-intron boundary, in the sequence that signals the splicing machinery where to cut, which is a category this podcast has touched before as one of CFTR's own harder-to-classify VUS buckets. 他们用从五个MANE转录本中抽取的1458条HGVS描述做基准测试，分为500个编码单核苷酸变异、250个移码插入或缺失，以及708个内含子剪接位点替换变异——所谓剪接位点替换变异，指的是正好落在外显子-内含子边界上的变异，位于告诉剪接机制该在哪里"剪切"的那段序列里，这个类别这个节目之前提到过，是CFTR自身较难分类的VUS类别之一。 Every single one of the 1,458 descriptions passed VarSim's own syntactic validation, and all 750 coding descriptions — the SNVs plus the frameshift indels — passed semantic validation against their reference sequences. 这1458条描述全部通过了VarSim自身的语法校验，而全部750条编码类描述——单核苷酸变异加上移码插入缺失——都通过了对照参考序列的语义校验。 For comparison, VariantValidator accepted all 1,458 descriptions too, while the Mutalyzer normalization endpoint only processed the 750 coding descriptions — notably not the 708 intronic splice-site variants, a gap in the comparator itself worth noting rather than a VarSim failure. 作为对比，VariantValidator同样接受了全部1458条描述，而Mutalyzer的归一化接口只处理了那750条编码类描述——明显没有处理那708个内含子剪接位点变异，这是对比工具自身的一个缺口，值得指出，而不是VarSim的问题。
